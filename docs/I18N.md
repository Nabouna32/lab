# Loculary — Internationalization

French and English are the two supported initial languages. Adding another language or introducing right-to-left (RTL) support is a separate product decision, not a commitment implied by the architecture.

## Langue de travail du dépôt

Le français est la langue par défaut de la communication et de la documentation du projet Loculary : documentation interne, spécifications, décisions, GitHub Issues et pull requests, y compris leurs titres, descriptions et échanges. Cette convention facilite le travail quotidien et ne détermine pas la langue de l'application.

Le code et ses conventions techniques restent en anglais : identifiants, noms de variables, fonctions, types, interfaces et autres éléments techniques suivent les usages de l'écosystème. Les noms officiels des technologies, API, commandes et références externes ne sont pas traduits. Les commentaires intégrés au code suivent les conventions pertinentes ; les explications des règles métier et décisions propres à Loculary peuvent être rédigées en français lorsqu'elles sont plus claires ainsi.

Cette règle de langue de travail est distincte de la stratégie de localisation produit décrite dans le reste de ce document : l'application continue de prendre en charge le français et l'anglais conformément à ses exigences produit.

Global UI strings belong in locale files. Tool-specific names, descriptions and metadata are separate structured content. Larger editorial/documentation content can use structured Markdown/MDX or an equivalent content layer. User-facing strings must not be hard-coded in tool logic.

Use a language registry with enabled state, locale metadata, text direction and translation status. `translationStatus` is a product readiness signal, not an automatic structural check: `complete` means the locale's currently supported user-facing translation scope has been reviewed and declared complete; `partial` means the locale is usable but that review has not established completeness or at least one translation domain is intentionally incomplete. Matching keys or content structure alone never changes the status. Partial translations may be published with a clear indicator. English is the product fallback language when a translation is missing; French is the other supported initial language. Keep locale direction explicit for the currently supported languages. Localized SEO requires deliberate URL and metadata design.

## Public URL localization

English is the reference and default locale for the initial launch, with French as the second complete launch locale. Tool URLs and category URLs use separate namespaces to keep each resource addressable without a category-dependent tool path:

- Tools: `/en/tools/<tool-slug>` and `/fr/outils/<outil>`.
- Categories: `/en/categories/<category-slug>` and `/fr/categories/<categorie>`.

A tool's public URL is independent of its category and remains the same if its category associations change. A tool may belong to multiple categories; no primary category is required to construct its URL.

Internal identifiers remain English and language-neutral. Tool and category slugs are localized routing data. Language switching must resolve the same resource in the target locale, and canonical URLs, hreflang alternates, internal links, breadcrumbs and sitemaps must use the localized route. The current pre-launch route migration does not preserve the old category-bearing URL shape merely for historical continuity; future public URL changes after launch should be evaluated when a concrete change is planned.

## Initial locale detection

When a public URL has no explicit locale prefix, the edge proxy negotiates the initial locale from the browser's `Accept-Language` header. French preferences select `/fr`, English preferences select `/en`, and unsupported languages fall back to the default English locale. Explicit `/fr` and `/en` URLs are never overridden by browser language preferences.
