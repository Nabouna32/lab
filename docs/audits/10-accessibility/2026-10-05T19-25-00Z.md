## 6. Résultats observés

### A10-01 — Fondations sémantiques et focus globalement solides

**INFO / OBSERVÉ**

Plusieurs primitives partagées ont de bonnes bases :

- `Button` est un vrai `<button>`.
- `TextField`, `TextArea` et `Select` associent explicitement leur label au contrôle.
- Les contrôles utilisent des styles `focus-visible`.
- Les cibles interactives communes ont généralement au moins 40px de hauteur.
- Les liens de navigation et cartes utilisent des focus rings visibles.
- Les breadcrumbs exposent `aria-label` et `aria-current="page"` pour l'élément courant.
- Les sections importantes utilisent `aria-labelledby` ou `aria-label` lorsque nécessaire.
- Les icônes purement décoratives sont fréquemment marquées `aria-hidden`.

**À PRÉSERVER**

Cette stratégie de primitives partagées est nettement préférable à une correction accessibilité dispersée composant par composant.

### A10-02 — Reduced motion correctement traité au niveau global

**INFO / OBSERVÉ**

`src/app/globals.css` contient une règle `@media (prefers-reduced-motion: reduce)` qui réduit animations et transitions et désactive le smooth scrolling.

**MEASURED**

La présence du mécanisme est directement vérifiée dans le CSS ; aucune animation spécifique hors de ce mécanisme global n'a été retenue comme exception critique pendant l'inspection.

**À PRÉSERVER**

Le choix global est simple et robuste pour l'état actuel du produit.

### A10-04 — Cibles interactives communes correctement dimensionnées

**MEASURED / OBSERVÉ**

Les primitives `Button`, `TextField`, `TextArea` et `Select` utilisent typiquement `min-h-10` ou `min-h-11`, soit environ 40–44px. Les boutons d'icône du header sont également autour de 36–40px.

**DEDUIT**

Le produit est largement au-dessus du minimum WCAG 2.2 de 24×24 CSS px pour les contrôles courants. Les exceptions éventuelles doivent être vérifiées sur les composants non centralisés.

### A10-05 — Mobile search : gestion du focus incomplète

**MEDIUM / OBSERVÉ**

`src/components/layout/MobileHeaderSearch.tsx` :

- place le focus sur le champ à l'ouverture ;
- permet de fermer la recherche ;
- n'effectue pas de retour de focus vers le bouton qui a ouvert la recherche ;
- ne gère pas explicitement Escape au niveau de l'overlay ;
- ne transforme pas la zone ouverte en véritable dialogue ou surface modale ;
- laisse donc potentiellement le parcours clavier traverser le header et le contenu sous-jacent alors que la recherche est visuellement ouverte.

**IMPACT**

Un utilisateur clavier ou lecteur d'écran peut perdre le contexte de la recherche et devoir retrouver manuellement le point d'entrée après fermeture.

**REPRODUCTION STATIQUE**

Inspecter `MobileHeaderSearch.tsx`, puis ouvrir la recherche à une largeur mobile et parcourir Tab/Shift+Tab ; le composant ne contient aucune logique de restauration du focus.

**À VALIDER**

Déterminer si la recherche mobile doit rester une simple disclosure non modale ou devenir une surface de recherche dédiée avec gestion de focus plus stricte.

**PROPOSITION**

Le meilleur compromis actuel est probablement une disclosure dédiée : mémoriser le bouton d'ouverture, restaurer le focus à la fermeture, accepter Escape et éviter une fausse sémantique de dialogue si la surface reste non modale. Si elle devient réellement modale, adopter alors le comportement complet de dialogue.

### A10-06 — Erreur de profil annoncée comme status

**MEDIUM / OBSERVÉ**

Dans `src/app/[locale]/compte/page.tsx`, `statusMessage` couvre à la fois :

- `profile-updated` ;
- `password-changed` ;
- `email-updated` ;
- `error === "profile"`.

Le rendu utilise toujours `role="status"`, y compris pour `profileError`.

**IMPACT**

Une erreur n'est pas traitée comme une erreur dans l'arbre d'accessibilité. Un lecteur d'écran peut recevoir une annonce de statut polie alors que l'information exige une attention plus explicite.

**PROPOSITION**

Séparer le succès et l'erreur dans leur sémantique d'annonce : `status` pour succès et `alert` pour erreur, ou utiliser un mécanisme de formulaire plus précis.

### A10-07 — `aria-invalid` est parfois déclaré sans relation directe avec un message d'erreur

**MEDIUM / OBSERVÉ**

Plusieurs outils déclarent `aria-invalid` sur un champ, mais l'association `aria-describedby` n'est pas systématique.

Exemple vérifié : `ColorConverter.tsx` utilise `aria-invalid={!result}` mais le texte d'erreur rendu plus bas n'est pas référencé par `aria-describedby`.

À l'inverse, `QrCodeGenerator.tsx` fait mieux : `aria-describedby="qr-code-error"` est utilisé lorsque l'erreur existe.

**DEDUIT**

Le projet possède déjà le bon pattern mais ne l'applique pas systématiquement.

**IMPACT**

Le champ peut être annoncé comme invalide sans fournir immédiatement au lecteur d'écran la cause précise de l'invalidité.

**PROPOSITION**

Standardiser un primitive/pattern de champ invalide :

`aria-invalid="true"` + `aria-describedby` vers le message d'erreur, avec conservation du texte d'aide séparé lorsque nécessaire.

### A10-08 — Résultats dynamiques : bonne intention, couverture hétérogène

**OBSERVÉ**

`ResultPanel`, plusieurs convertisseurs et certains outils utilisent `aria-live="polite"`. Les boutons de copie annoncent également leur état via `aria-live`.

**À PRÉSERVER**

Le pattern de résultat dynamique est déjà présent.

**WEAKNESS**

Il n'existe pas de contrat centralisé imposant quand un résultat, une erreur, une progression ou une réussite doit être annoncé.

**DEDUIT**

La couverture dépend aujourd'hui des composants/outils individuels.

**PROPOSITION**

Définir une petite primitive de status/result announcement et l'utiliser systématiquement pour les transitions utilisateur importantes, sans rendre chaque changement de saisie bavard.

### A10-09 — Recherche outil : pattern ARIA relativement mature mais non vérifié par un scanner spécialisé

**OBSERVÉ**

`ToolSearch.tsx` utilise :

- `role="combobox"` ;
- `aria-expanded` ;
- `aria-controls` ;
- `aria-activedescendant` ;
- `role="listbox"` ;
- `role="option"` ;
- navigation ArrowUp/ArrowDown/Enter/Escape.

Les tests E2E vérifient également le déplacement par ArrowDown et Enter.

**À PRÉSERVER**

Le composant constitue une base raisonnable pour une recherche clavier.

**À VALIDER / PROPOSÉ**

Avant d'introduire une bibliothèque de combobox plus lourde, valider ce pattern avec un audit axe + lecteur d'écran et quelques scénarios clavier réels. Le remplacement n'est pas justifié par le seul constat statique.

### A10-10 — Table d'édition : bonne structure principale, preview perfectible

**LOW / OBSERVÉ**

`MarkdownTableGenerator.tsx` fournit une vraie table éditable avec `thead`, `tbody`, `th scope="col"` et labels explicites pour les champs.

La table de preview rend également `thead`/`th`, mais les `th` de cette seconde table ne portent pas explicitement `scope="col"`.

**IMPACT**

Faible dans une table simple, mais une sémantique explicite est préférable pour les lecteurs d'écran et cohérente avec la table éditable.

**PROPOSITION**

Ajouter `scope="col"` aux headers de preview si aucune autre sémantique n'est nécessaire.

### A10-11 — Absence de vraie modal dans l'implémentation actuelle

**OBSERVÉ**

La recherche de code ne trouve aucun `role="dialog"`. Les disclosures actuelles utilisent principalement `details/summary`.

**DEDUIT**

C'est actuellement plus simple qu'une collection de modales custom, et évite une catégorie de bugs de focus-trap.

**CHALLENGE**

Ne pas ajouter une abstraction Dialog simplement pour atteindre une apparence plus moderne. Si une vraie modale devient nécessaire, utiliser un composant accessible qui gère focus initial, restauration, Escape et inertie du fond.

### A10-12 — Images et sorties graphiques : couverture partielle mais bons exemples

**OBSERVÉ**

Le QR code SVG est exposé avec `role="img"` et `aria-label`. Les images HTML inspectées utilisent un `alt`.

**LIMITE**

Un label générique de type « preview » ne décrit pas nécessairement la donnée encodée. Pour un QR code, une alternative textuelle décodable n'est pas toujours possible sans révéler le contenu ; la bonne stratégie dépend donc du contexte de confidentialité.

**À VALIDER**

Pour les sorties graphiques futures, définir quand fournir une description textuelle, une table de données ou uniquement un label de type de sortie.

## 7. Faiblesses et choix sous-optimaux

### 7.1 Accessibilité principalement conventionnelle, pas contractuelle

**OBSERVÉ**

L'accessibilité repose sur de nombreux bons patterns dans le code mais aucun scanner WCAG automatisé dédié n'est exécuté dans CI.

**DEDUIT**

La qualité actuelle dépend fortement de la discipline des développeurs et des tests fonctionnels existants.

**CHALLENGE**

Pour un catalogue d'outils qui va croître, cette stratégie ne scale pas suffisamment.

### 7.2 Les tests E2E prouvent surtout le comportement fonctionnel

**OBSERVÉ**

Les tests utilisent correctement les rôles/labels et couvrent FR/EN, erreurs, résultats, recherche et certains parcours responsive.

Mais ils ne vérifient pas systématiquement :

- absence de violations axe ;
- ordre de focus ;
- restauration du focus ;
- noms accessibles de tous les contrôles ;
- contraste de chaque écran ;
- navigation complète au clavier ;
- zoom/reflow à 200 % ;
- préférences reduced-motion en situation réelle ;
- lecture par un lecteur d'écran.

**DEDUIT**

Un test fonctionnel qui réussit peut coexister avec une régression WCAG.

## 8. Challenges du design actuel

### Challenge 1 — « Les focus rings suffisent-ils ? »

**REJETÉ comme hypothèse suffisante.**

Les focus rings sont bons, mais l'accessibilité est une propriété de parcours complet : ordre, restauration, nom, état, erreur et résultat comptent autant que le style.

### Challenge 2 — « Une bibliothèque ARIA doit-elle remplacer les composants actuels ? »

**REJETÉ / À NE PAS FAIRE PAR DÉFAUT.**

Les primitives natives et les composants actuels sont simples. Le remplacement généralisé ajouterait de la complexité sans preuve de besoin.

### Challenge 3 — « Faut-il ajouter un scanner lourd à chaque PR ? »

**PROPOSÉ : non, pas nécessairement.**

Un axe/équivalent ciblé sur un petit corpus de routes représentatives peut fournir un meilleur rapport signal/coût qu'un scan aveugle de toutes les pages à chaque changement. Le catalogue peut ensuite être étendu progressivement.

### Challenge 4 — « L'accessibilité doit-elle être testée seulement sur les outils ? »

**REJETÉ.**

Le header, la recherche, le compte, les préférences de thème/langue et les surfaces administratives sont des interfaces utilisateur à part entière.

### From scratch

**PROPOSÉ**

Si Loculary était construit aujourd'hui, je conserverais :

- HTML natif en priorité ;
- primitives simples ;
- focus-visible systématique ;
- tokens de couleur centralisés ;
- reduced-motion global ;
- tests Playwright basés sur rôles/labels.

Je changerais principalement la **stratégie de validation** plutôt que l'architecture UI :

1. ajouter un contrôle automatisé WCAG/axe ciblé ;
2. ajouter un petit corpus de parcours clavier déterministes ;
3. formaliser les patterns d'erreur et d'annonce dynamique ;
4. tester le zoom/reflow et les préférences reduced-motion sur quelques routes représentatives ;
5. n'introduire une abstraction Dialog/Combobox que lorsqu'un besoin réel est démontré.

## 15. Conclusion

**Évaluation globale : BASE SOLIDE, GARDE-FOUS INSUFFISANTS**

Loculary possède déjà plusieurs fondations accessibles de bonne qualité : HTML natif, labels, focus-visible, tokens de contraste mesurés conformes sur les combinaisons principales, reduced-motion global, cibles suffisamment grandes et tests Playwright orientés rôles/labels.

Le principal risque n'est pas une architecture UI fondamentalement inaccessible. C'est l'absence d'un **contrat de régression accessibilité automatisé** et quelques incohérences de gestion du focus et des erreurs.

Le challenge from-scratch conduit donc à **préserver l'approche simple actuelle**, mais à renforcer fortement sa validation. Une refonte ou une bibliothèque d'accessibilité généralisée ne serait pas justifiée par les preuves disponibles.

Aucune correction produit n'a été implémentée pendant cet audit.
