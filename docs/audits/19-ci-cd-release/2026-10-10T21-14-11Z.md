## Résultats observés et mesurés

### 1. CI PR et checks requis

**OBSERVÉ — BON CHOIX À PRÉSERVER.** La CI principale déclenche sur les PR vers main. Elle conserve un check stable nommé Node.js 24.21.0 et n’utilise pas de filtre de chemins au niveau du workflow : le check existe même pour les changements documentaires, puis les étapes coûteuses sont conditionnées par la détection. C’est préférable à un filtre global susceptible de laisser un check requis absent ou en attente.

Le job de détection classe les PR purement documentaires et détecte séparément les modifications de package.json ou package-lock.json. Pour les PR documentaires, Setup Node, npm ci, validation des contrats, lint, typecheck, tests et build sont ignorés. Dependency Review ne s’exécute que lorsque les manifests/lockfile changent.

**OBSERVÉ — FRAÎCHEUR DE BASE.** Le workflow compare la base de l’événement PR au main courant et échoue si main a avancé. L’Issue #468 confirme que le ruleset Protect main exige désormais des branches à jour (strict_required_status_checks_policy: true). Le préflight et la règle stricte sont complémentaires ; aucun ne doit être supprimé sans réévaluation du risque de course avant fusion.

**MESURÉ — ÉCHANTILLON LIMITÉ.** Le run [#38085647890](https://github.com/Nabouna32/lab/actions/runs/38085647890), associé à la PR #543, a réussi. L’Issue #468 consigne une durée d’environ 59 secondes pour le job Node. L’outil d’exécution accessible ici ne fournit pas les horodatages précis des jobs ; un seul échantillon ne constitue pas une baseline statistique.

### 2. Double checkout dans la CI principale

**OBSERVÉ — OPPORTUNITÉ D’OPTIMISATION, IMPACT À MESURER.** Le workflow exécute deux jobs successifs. Detect CI scope fait un checkout avec fetch-depth: 0 pour comparer les SHA explicites de base et de tête. Node.js 24.21.0 démarre un second runner et effectue un nouveau checkout avant le contrôle de fraîcheur et les validations. Les runners ne partagent pas leur espace de travail ; cela entraîne un second démarrage de job et un second checkout pour une détection qui ne fait que classifier les chemins.

**CHALLENGE / PROPOSÉ — PRIORITÉ HAUTE, RISQUE ATTENDU FAIBLE.** Déplacer la détection dans le job Node.js 24.21.0, immédiatement après son checkout, puis utiliser les sorties de cette étape pour conditionner les validations. Le check requis conserverait son nom, le cas docs-only continuerait à sauter le travail coûteux et Dependency Review resterait conditionnelle. Il faut récupérer les SHA nécessaires de façon déterministe sans cloner tout l’historique : récupérer explicitement les commits base/tête peut être moins coûteux que fetch-depth: 0.

**À MESURER.** Aucun gain en secondes n’est affirmé sans comparaison avant/après. La suppression d’un runner et d’un checkout constitue le mécanisme de gain attendu, pas une mesure.

### 3. Deux planifications hebdomadaires au même horaire

**OBSERVÉ — REDONDANCE POTENTIELLE, PAS ENCORE UNE DÉCISION.** ci.yml et dependency-security-monitoring.yml utilisent tous deux le cron 30 3 * * 1 (chaque lundi à 03:30 UTC). Le workflow de sécurité lance npm audit --audit-level=high. Le workflow CI principal, lorsqu’il est lancé par schedule, n’est pas une PR documentaire : il exécute donc aussi npm ci, les contrats, lint, typecheck, tests et build.

**CHALLENGE / PROPOSÉ — GAIN POTENTIEL SIGNIFICATIF, DÉCISION À VALIDER.** Si le schedule du CI principal n’a pas d’objectif explicite de détection de dérive environnementale, supprimer ce déclencheur éviterait une validation complète qui ne correspond à aucun changement de code. Si l’objectif est de détecter une dérive due à l’environnement, aux services externes ou à la toolchain, une exécution périodique peut être justifiée, mais il faut le documenter et décider si un sous-ensemble de checks suffit.

**RECOMMANDATION.** Confirmer sa finalité et examiner l’historique des exécutions planifiées avant de supprimer le schedule. Le monitoring de sécurité hebdomadaire doit rester indépendant. Cette recommandation ne modifie pas le workflow.

### 4. Ciblage des workflows Supabase

**OBSERVÉ — BON CHOIX À PRÉSERVER.** Edge Functions CI est filtrée sur supabase/functions/** et le fichier du workflow. La validation de base de données et l’application des migrations en production sont manuelles afin de ne pas démarrer Docker/Supabase sur les PR applicatives ordinaires. Dans le workflow base de données, le mode release exige main et dépend du succès de la validation locale ; la release passe ensuite par l’environnement supabase-production.

Cette séparation est cohérente avec l’objectif de réduire le coût des PR tout en conservant une voie explicite pour les migrations. Elle dépend toutefois d’une discipline opérationnelle : la documentation indique qu’une PR touchant la base doit exécuter manuellement la validation avant fusion. Un CI applicatif vert ne prouve pas la validité des migrations SQL.

### 5. Workflows navigateur

**OBSERVÉ — CONFORME À LA POLITIQUE VALIDÉE.** E2E, validation navigateur de production et captures sont tous déclenchés manuellement. E2E installe les dépendances, construit l’application, installe Chromium puis exécute une liste explicite de specs. La validation de production vérifie d’abord que l’alias sert le SHA attendu et exécute ensuite les assertions runtime/hydratation ; les captures sont séparées.

L’Issue #456 reste ouverte pour l’erreur d’hydratation React #418. L’Issue #533 reste ouverte pour l’échec intermittent de résolution de police Google/Turbopack. Ces incidents ne doivent pas être « optimisés » en supprimant les assertions ou en ajoutant des retries sans preuve.

**OBSERVÉ — NETTOYAGE MINEUR.** e2e.yml conditionne l’upload d’artefacts sur failure() et steps.changes.outputs.docs_only != 'true', mais ce workflow ne définit aucune étape id: changes. La sortie est vide, donc la condition ne filtre actuellement rien : l’upload se produit en cas d’échec comme vraisemblablement prévu.

**PROPOSÉ — PRIORITÉ BASSE.** Remplacer la condition par if: failure() rendrait le comportement explicite et supprimerait une référence morte. Nettoyage autonome et faible risque, à réaliser dans une étape d’implémentation validée. Ce n’est pas un motif pour réactiver E2E sur les PR.

### 6. Permissions, concurrence et sécurité

**OBSERVÉ — À PRÉSERVER.** Les workflows lus définissent des permissions minimales, généralement contents: read. Les workflows concernés annulent les exécutions obsolètes par workflow/ref lorsque cela est approprié. Dependency Review est exécutée dans le check requis uniquement lors de modifications des manifests/lockfile ; son comportement positif/négatif a été vérifié dans l’Issue #544 sans fusionner de dépendance de test.

Aucune preuve recueillie pendant cet audit ne justifie de diminuer les contrôles requis, d’élargir les permissions ou de contourner les protections de main.

## Éléments à préserver

- Check stable requis sur PR ; ne pas masquer le check via un filtre global de chemins.
- Skip ciblé des étapes coûteuses pour les PR purement documentaires.
- Dependency Review conditionnelle aux changements de dépendances, seuil High, scopes runtime/development.
- Monitoring npm périodique séparé.
- Règle de fraîcheur de main et protections du ruleset.
- CI Edge Functions filtrée par chemins.
- Validation DB/release manuelle, release dépendante d’une validation réussie.
- Workflows E2E et navigateur de production manuels pendant la refonte ; captures séparées.
- Permissions minimales et absence de retries spéculatifs.

## Challenge from-scratch

**Si Loculary était construit aujourd’hui, qu’est-ce que nous changerions ?**

Nous garderions un seul check de validation PR stable, mais ferions la détection de périmètre dans le même runner afin de ne pas payer un runner et un checkout supplémentaires. Les contrôles de sécurité resteraient ciblés sur les fichiers pertinents et complétés par un monitoring périodique dédié. Les validations coûteuses — base de données, E2E, navigateur de production et captures — resteraient hors du chemin PR ordinaire lorsqu’elles ne sont pas requises, mais seraient déclenchées explicitement par le type de changement ou une décision opérationnelle. Toute planification périodique devrait avoir un objectif observable et documenté : un cron qui ne détecte rien de différent des autres contrôles est un coût.
