## 6. Findings et anomalies

### F01 — Le statut de traduction anglais contredit la décision durable et n'est pas consommé par le produit

**MEDIUM — OBSERVÉ / TOUJOURS PRÉSENT**

Preuves :
- `src/lib/i18n/config.ts` déclare `languages.en.translationStatus = "complete"` ;
- `src/lib/tools/i18n.test.mjs` affirme également `languages.en.translationStatus === "complete"` ;
- DEC-031 dit explicitement que le statut anglais actuel reste `partial` ;
- une recherche du dépôt montre que `translationStatus` est essentiellement déclaré/testé/documenté, pas utilisé pour gouverner le routing, le selector ou l'affichage utilisateur.

Impact :
- le code contredit une décision durable ;
- une locale déclarée partielle peut être présentée comme une locale normale sans indication de readiness ;
- le signal de qualité existe mais n'a actuellement pas d'effet fonctionnel.

DÉDUIT :
Le problème n'est pas nécessairement que l'anglais est effectivement incomplet sur chaque écran ; DEC-031 dit précisément que le statut ne doit pas être déduit automatiquement de la structure. Le problème vérifié est la divergence entre le statut décidé et le statut codé, ainsi que l'absence de consommation du signal.

PROPOSÉ :
- rétablir la valeur décidée dans le code ;
- décider ensuite si `partial` doit rester purement interne ou produire un comportement utilisateur explicite avant publication ;
- conserver la promotion vers `complete` comme une décision de readiness séparée d'un simple test structurel.

À VALIDER :
- le statut réel de readiness de l'anglais et, si `partial` reste autorisé en production, son éventuelle présentation à l'utilisateur.

### F02 — `enabled` existe dans la registry mais n'est pas la source de vérité du routage

**MEDIUM — OBSERVÉ**

Preuves :
- `src/lib/i18n/config.ts` contient `languages[locale].enabled` ;
- `src/proxy.ts`, `src/app/sitemap.ts`, les pages localisées et `LanguageSelector` utilisent directement `locales` ;
- les chemins statiques sont donc dérivés de la liste des locales, pas d'une liste filtrée par `enabled`.

Impact :
- aujourd'hui les deux locales sont enabled, donc aucun défaut utilisateur immédiat n'est observé ;
- si une locale est passée à `enabled: false`, elle resterait potentiellement routable, sélectionnable et indexable ;
- le champ `enabled` devient alors un faux mécanisme de désactivation.

PROPOSÉ :
- distinguer explicitement `allLocales`/registry de `enabledLocales` ;
- utiliser la seconde pour routing public, selector, génération statique et sitemap ;
- conserver la registry complète pour les métadonnées et les migrations futures.

À VALIDER :
- la sémantique exacte d'une locale disabled : retirée du public, conservée pour compatibilité, ou les deux selon le contexte.

### F03 — La négociation de langue est codée en dur pour FR/EN et ne suit pas la registry

**MEDIUM — OBSERVÉ / CHALLENGE TROISIÈME LANGUE**

Preuve principale :
`src/lib/i18n/request-locale.ts::getPreferredLocale()` teste explicitement :
- `fr` / `fr-*`
- `en` / `en-*`

Toute autre langue tombe directement sur `defaultLocale`.

Impact :
- avec une troisième langue réellement enabled, son Accept-Language ne pourra pas la sélectionner automatiquement ;
- l'ajout d'une locale nécessite une modification du code de négociation au lieu d'une simple extension des données de registry ;
- le mécanisme actuel est donc bilingue par construction.

PROPOSÉ :
- parcourir les locales enabled de la registry et faire correspondre les tags BCP-47 aux codes supportés ;
- conserver `defaultLocale` comme fallback final ;
- tester les langues régionales et les priorités q sans branche spécifique par langue.

À VALIDER :
- politique exacte pour les tags régionaux et les fallbacks entre variantes (ex. pt-BR -> pt si pt existe).

### F04 — Des fallbacks internes restent français alors que l'anglais est la locale par défaut

**LOW/MEDIUM — OBSERVÉ**

Exemples :
- `src/lib/tools/search.ts` : `searchTools(..., locale = "fr")` ;
- `src/components/tools/ToolPage/ToolProcessingStatus.tsx` : prop par défaut `locale = "fr"` ;
- `src/lib/admin/authorization.ts` redirige vers `/fr` en cas de locale invalide ;
- `src/app/[locale]/auth/callback/route.ts` utilise `fr` comme fallback ;
- `src/app/[locale]/admin/utilisateurs/actions.ts` utilise `fr` pour une locale de formulaire invalide.

Impact :
- les chemins normaux transmettent généralement la locale et ne montrent donc pas tous immédiatement un défaut ;
- les chemins d'erreur, d'appel direct ou de composant sans prop peuvent diverger de DEC-036 ;
- ces fallbacks fragilisent encore l'ajout d'une troisième langue et rendent les tests plus difficiles à raisonner.

PROPOSÉ :
- utiliser `defaultLocale` ou la registry plutôt qu'un code de langue littéral ;
- conserver un fallback FR uniquement lorsqu'il est explicitement requis par une contrainte historique et documentée.

### F05 — Trois outils de dates/fuseaux contournent la registry Intl

**MEDIUM — OBSERVÉ**

Preuves :
- `src/components/tools/date-calculator/DateCalculator.tsx` choisit `"fr-FR" : "en-US"` ;
- `src/components/tools/timezone-converter/TimezoneConverter.tsx` fait le même choix ;
- `src/components/tools/unix-timestamp/UnixTimestampConverter.tsx` fait le même choix ;
- `src/lib/i18n/config.ts` possède déjà `getIntlLocale(locale)`.

Impact :
- ces composants ne sont pas réellement extensibles à une troisième locale ;
- une locale ajoutée à la registry ne peut pas obtenir son propre format Intl via ces chemins ;
- le code dupliqué crée plusieurs sources d'autorité pour la relation Locale -> Intl locale.

PROPOSÉ :
- utiliser systématiquement `getIntlLocale(locale)` pour les formats destinés à l'utilisateur ;
- conserver les `Intl` internes fixes uniquement lorsqu'ils sont des formats techniques d'algorithme et non des présentations utilisateur.

### F06 — Quatre composants éditoriaux utilisent un branchement FR/else au lieu du système de contenu localisé

**MEDIUM — OBSERVÉ / CHALLENGE**

Preuves :
- `src/components/tools/json-formatter/ToolEditorial.tsx`
- `src/components/tools/html-previewer/ToolEditorial.tsx`
- `src/components/tools/xml-formatter-validator/ToolEditorial.tsx`
- `src/components/tools/yaml-formatter-validator/ToolEditorial.tsx`

Ces composants utilisent explicitement `const fr = locale === "fr"` puis des ternaires FR/EN dans le JSX.

Contraste :
- la majorité du catalogue utilise des structures localisées séparées et `getToolMessages(locale)` ;
- `src/lib/tools/i18n.test.mjs` vérifie un ensemble de fichiers éditoriaux, mais ces quatre composants ne font pas partie de la liste contrôlée par cette vérification statique.

Impact :
- une troisième langue transforme un composant en série de branches `fr ? ... : ...` ;
- la logique de contenu devient mélangée à la présentation ;
- une nouvelle locale peut passer à travers les tests structurels sans que tous les textes éditoriaux de ces composants soient couverts.

PROPOSÉ :
- sortir ces chaînes dans une structure de contenu localisée ou dans le catalogue de messages ;
- étendre le test de couverture aux composants éditoriaux réellement concernés ;
- privilégier une sélection par locale plutôt qu'un booléen FR/else.

### F07 — La préparation RTL est déclarative mais pas encore suffisamment réelle

**MEDIUM — CHALLENGE / OBSERVÉ**

OBSERVÉ :
- la registry contient `direction` ;
- `[locale]/layout.tsx` transmet la direction à l'élément HTML ;
- les locales actuelles sont LTR.

OBSERVÉ dans l'UI :
- plusieurs composants utilisent des propriétés physiques comme `right-0`, `left-0`, `pl-*`, `border-l-*` et `text-left` ;
- des occurrences sont présentes notamment dans Header, LanguageSelector, ToolSearch, formulaires de compte et certains outils.

DÉDUIT :
Définir `dir="rtl"` ne suffit pas à garantir une interface RTL correcte. Les positions et espacements physiques peuvent rester visuellement inversés ou asymétriques.

PROPOSÉ :
- avant l'ajout d'une langue RTL, auditer les primitives communes et migrer les règles directionnelles vers des propriétés/logiques RTL-aware ;
- privilégier les primitives partagées plutôt que de corriger outil par outil.

À VALIDER :
- si la prochaine langue cible est susceptible d'être RTL ; le niveau d'investissement doit être proportionné à une vraie feuille de route linguistique.

### F08 — Le moteur de relations reste basé sur le français même en anglais

**MEDIUM — OBSERVÉ / TOUJOURS PRÉSENT DEPUIS AUDIT 02**

Revalidation :
- `src/lib/tools/relations.ts::getTerms()` utilise `getToolContent(tool, "fr")` explicitement ;
- les relations sont ensuite affichées dans la locale active.

Impact :
- la découverte anglaise dépend toujours principalement de la sémantique française ;
- ce n'est pas une relation réellement multilingue.

Ce constat confirme F04 de l'Audit 02 ; il n'est pas présenté comme une nouvelle anomalie.

PROPOSÉ :
- calculer les termes dans la locale active ;
- ou construire plus tard un index relationnel multilingue si la taille du catalogue le justifie.

À VALIDER :
- stratégie de relation multilingue avant une évolution importante du catalogue.

## 7. Faiblesses et choix sous-optimaux sans défaut immédiat

### 7.1 Registry de locales : bonne direction, mais mélange de données et de politique

OBSERVÉ :
La registry contient à la fois code, labels, direction, locale Intl, enabled et translationStatus.

CHALLENGE :
C'est un bon centre de données, mais le code contourne plusieurs champs avec des branches littérales.

PROPOSÉ :
Traiter la registry comme l'autorité de données et faire dériver les listes opérationnelles (`enabledLocales`, locale negotiation, Intl locale, direction) à partir d'elle.

### 7.2 Les slugs sont correctement data-driven, mais l'ajout d'une langue reste très manuel

OBSERVÉ :
`src/lib/tools/routes.ts` contient une table de slugs par locale et par outil ; les catégories ont également une table par locale.

CHALLENGE :
Ce modèle est simple et lisible à 42 outils. Il est préférable à une génération opaque. En revanche, une troisième langue exige de toucher chaque entrée de route/SEO/contenu.

PROPOSÉ :
Ne pas introduire maintenant une couche de CMS ou de génération complexe. À court terme, conserver les tables explicites et renforcer les validateurs pour qu'une locale enabled ne puisse pas être partiellement enregistrée sans preuve claire.

### 7.3 Les tests i18n sont utiles mais ciblent surtout la structure

OBSERVÉ :
Les tests vérifient des clés, locales, slugs et quelques règles de structure.

CHALLENGE :
Ils ne peuvent pas déterminer la qualité éditoriale, et plusieurs chemins UI hardcodés échappent au test statique.

PROPOSÉ :
Ajouter des tests ciblés sur les invariants comportementaux :
- chaque locale enabled est négociable ;
- une locale disabled n'est ni routée ni indexée ;
- le language switch conserve la ressource ;
- les formats Intl passent par la registry ;
- aucune branche FR/else n'existe dans les composants déclarés localisés.

## 8. Challenge from-scratch

### Si Loculary était construit aujourd'hui

Je conserverais :

1. une locale par segment d'URL ;
2. des slugs publics localisés ;
3. des IDs internes en anglais ;
4. un fallback anglais explicite ;
5. une registry centrale ;
6. des metadata SEO générées à partir de la locale active ;
7. des messages/outils séparés de la logique métier ;
8. `dir` et `Intl` pilotés par la locale.

Je changerais :

1. **la registry deviendrait réellement autoritaire** : enabled, negotiation, direction et Intl seraient consommés partout ;
2. **aucun composant ne connaîtrait "fr" ou "en" pour choisir un contenu utilisateur** ; il recevrait une structure localisée ;
3. **les fallbacks seraient centralisés** via `defaultLocale` ;
4. **les formats Intl seraient exclusivement dérivés de la registry** ;
5. **le statut de traduction serait cohérent avec la décision et explicite dans la gouvernance** ;
6. **RTL serait traité au niveau des primitives UI**, pas comme une propriété ajoutée au seul `html` ;
7. **les tests d'architecture i18n couvriraient les chemins opérationnels**, pas uniquement quelques fichiers représentatifs.

Je ne ferais pas, à ce stade :

- un CMS de traduction ;
- une abstraction de type gettext/i18next lourde ;
- une génération automatique de toutes les tables de slugs ;
- une refonte complète du catalogue.

À 42 outils et deux langues, la solution actuelle reste suffisamment simple. Le problème est surtout qu'elle commence à mélanger une architecture data-driven avec plusieurs exceptions codées en dur.

## 15. Conclusion

STATUT : COMPLETED

Évaluation globale : **base i18n solide pour FR/EN, mais extensibilité réelle incomplète**.

Le cœur du système est bien orienté : URLs entièrement localisées, IDs internes stables, fallback anglais explicite, registry centrale, metadata SEO cohérentes et sitemap bilingue réel. Les pages FR/EN échantillonnées ont été vérifiées en production et ne montrent pas de fuite de langue évidente.

Les principaux risques ne sont pas dans le routing public actuel mais dans la divergence entre la registry et certains chemins codés en dur. Le point le plus net est la readiness anglaise contradictoire avec DEC-031. Pour l'évolutivité, la négociation Accept-Language, les mappings Intl et plusieurs composants éditoriaux restent explicitement conçus autour de deux langues. La préparation RTL est également déclarative plus que réellement démontrée.

Le challenge from-scratch ne justifie pas une refonte ou l'introduction d'un framework i18n lourd à 42 outils. La meilleure direction est de rendre progressivement la registry réellement autoritaire et d'éliminer les exceptions FR/EN, tout en gardant le modèle de données simple.

Aucune correction produit n'a été appliquée pendant cet audit.
