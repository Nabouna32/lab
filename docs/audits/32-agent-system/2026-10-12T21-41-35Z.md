## Findings

### 1. Bootstrap and source of truth

**OBSERVED:** `AGENTS.md`, `agents/START-HERE.md`, `agents/AGENT-CONTRACT.md`, `agents/PRODUCT-ISSUE-CONTRACT.md`, `agents/AUDIT-CONTRACT.md` and procedure 32 describe a remote-only, GitHub-backed workflow. The Issue is the durable operational checkpoint; Git/GitHub remains authoritative for implementation and delivery evidence.

**ASSESSMENT:** retain this foundation. The label system is not required for Issues to carry objectives, decisions, plans, evidence, risks and next actions.

### 2. Decision rights and approval stages

**OBSERVED:** the common contract already separates analysis, direction discussion, operational plan, conversational decision brief, explicit plan approval, and implementation. The Issue protocol repeats the plan/approval distinction. DEC-050 says a fresh implementation conversation is the default after plan approval, unless an explicit same-conversation exception applies.

**OBSERVED:** commit `db7a49ba` (Issue #574 / PR #578) added a decision brief because a previous audit had already identified that the Issue's detailed plan was not enough for the user to understand what they were authorizing.

**FINDING — MEDIUM:** the written flow still does not explicitly prohibit asking for plan approval while material audit or discovery work remains unfinished. It also does not explicitly require the conversational brief to explain the changes in novice-friendly, non-technical language. “User language” and “affected files” do not guarantee a useful explanation of what changes in practice and why.

**RECOMMENDATION:** require the assistant to finish all investigation that could materially change scope, approach, risk or cost before asking for plan approval. The Issue plan remains the agent's detailed operational checklist. The conversational brief is the user's decision interface: what changes, why, what alternatives were considered, why the recommendation is better, material risks, how success will be verified, and exactly what approval is requested. If a material uncertainty remains, explain it and discuss it before requesting approval rather than hiding it inside the plan.

### 3. Plan traceability

**OBSERVED:** the Issue protocol already requires reading the full Issue and relevant comments, reconciling decisions bidirectionally against planned tasks, and mapping acceptance criteria to verification evidence.

**FINDING — MEDIUM:** these checks protect plan completeness, but they are not a substitute for completing the technical audit before presenting the plan. The failure mode described by the user is therefore a sequencing gap in practice and a missing explicit precondition, not a need for a second technical plan for the user to read.

**RECOMMENDATION:** keep one detailed operational plan in the Issue and one concise plain-language explanation in the conversation. Do not create parallel plans. Plan approval authorizes implementation of that plan, subject to the existing handoff rule and escalation for consequential new evidence; agreement with an audit recommendation alone must not be treated as plan approval.

### 4. Autonomy and escalation

**OBSERVED:** the common contract authorizes routine technical sequencing after plan approval and requires escalation for consequential direction or risk changes.

**ASSESSMENT:** retain this distinction. Improve the pre-approval audit gate rather than requiring approval for each technical step or adding a visible checklist to every response.

### 5. Issue continuity

**OBSERVED:** the Issue protocol independently requires resumable checkpoints, evidence, decisions, blockers, dependencies and next action. Issue #596 concerns stale final checkpoints when PRs close Issues automatically; its scope is broader than labels.

**RECOMMENDATION:** preserve the Issue-based tracking system and #596. Removing labels must not remove checkpoint requirements, native open/closed state, historical Issue records, or the final verification process.

### 6. Contract coherence

**OBSERVED:** commit `e0d6714` added a 40-line label taxonomy/lifecycle section to the common contract, 25 lines to the Issue protocol, label-specific bootstrap wording to `START-HERE.md`, a taxonomy validator and tests. The Issue protocol's section 8 now points to the common taxonomy but still contains label-specific creation, transition and closure rules.

**FINDING — MEDIUM:** active documentation contains obligations that become invalid if labels cease to be part of mission tracking. `START-HERE.md` explicitly says the common contract is canonical for Issue-label taxonomy. These references must be removed or rewritten, not left as dead instructions.

**RECOMMENDATION:** remove the label-specific policy from active contracts and entry-point guidance while preserving the non-label Issue lifecycle rules. Do not edit historical audit reports; they are immutable evidence. Publish a new report and move `LATEST.md` only after that report exists.

### 7. Validator quality and actual guarantees

**OBSERVED:** `agents/validate-workflow-contracts.mjs` imports and invokes `validateIssueLabelPolicy`, reads the label workflow/script/tests and asserts their expected content. `agents/validate-workflow-contracts.rules.mjs` hard-codes 21 expected labels. `agents/validate-workflow-contracts.test.mjs` includes a label taxonomy fixture and tests for missing, duplicate and unexpected labels. The separate `agents/issue-label-lifecycle.mjs` and its tests implement live Issue-label validation and correction.

**ASSESSMENT:** if the label policy is removed, these label-only rules, fixtures, reads and assertions must go too. Retain the audit-catalogue validator and unrelated governance checks. Do not weaken the validator wholesale.

### 8. CI and automation cost

**OBSERVED:** `.github/workflows/issue-label-lifecycle.yml` listens to Issue events, a weekly schedule and manual dispatch; it has `issues: write` permission and runs the standalone label validator. The regular CI workflow includes the label lifecycle test in its lightweight governance test command. `.github/dependabot.yml` independently applies `dependencies` + `npm` to npm PRs and `dependencies` + `github-actions` to GitHub Actions PRs.

**RECOMMENDATION:** remove the dedicated Issue-label workflow and its script/tests, remove only its test from the lightweight CI command, and remove label-only validator dependencies. Keep the lightweight governance path, CI classifier tests, contract validator, dependency review and Dependabot configuration. Keep labels attached to Pull Requests, including Dependabot PRs; the requested cleanup concerns Issue associations, not the global catalogue or PR labels.

### 9. Delivery integrity

**OBSERVED:** no open PRs were returned by the current search. The latest observed commit is `343ce85e`. Current status/run queries returned no entries for that commit.

**NON VERIFIED:** a fresh CI result and current ruleset configuration were not established by these queries. They must be checked during any implementation PR; historical audit evidence is not a substitute.

**RECOMMENDATION:** deliver the eventual implementation through a feature branch and PR, retain the existing protected delivery model, run the lightweight governance path for governance-only changes, inspect the complete diff and report actual checks only.

### 10. Communication and evidence

**OBSERVED:** the contract already requires a decision brief and an internal quality review. Static validation can check the presence of wording but cannot prove that an actual response is understandable or that the assistant has completed the promised investigation.

**RECOMMENDATION:** sharpen the behavior requirement rather than add brittle string checks for “novice language” or a mechanical response template. The brief should be concise, avoid repeating the objective multiple times, and preserve material risks and uncertainties. This audit report is technical evidence for the agent; the user-facing discussion should translate it into everyday language.

### 11. Portfolio and Issue disposition

**OBSERVED:** Issue #587 (“define Issue-label lifecycle”) and #592 (“enforce Issue-label lifecycle compliance”) are closed and concern the label system. Issue #595 concerns closed-Issue/label-event behavior only. Issue #608 concerns preventing agents from inventing lifecycle labels only. Their bodies contain no separate non-label deliverable. Issues #595 and #608 are open and have no comments returned by the connector.

**OBSERVED:** Issue #594 is a completed, broader audit of the agent system; its historical report covers 12 themes and must not be treated as merely a label issue. Issue #596 concerns final Issue checkpoints and must remain tracked. Issue #601 is a product feature Issue, not a label-system Issue.

**RECOMMENDATION:** after implementation, close #595 and #608 with a clear explanation that their label-specific work is intentionally abandoned because the label system is being removed. Do not close #596 or reclassify #594 as label-only. Leave #587 and #592 closed. Remove labels from all currently labeled Issue records (open and closed) as requested, but preserve labels attached to PRs. Before any closure, reread the complete Issue and comments and recheck that no broader requirement has appeared.

### 12. Rebuild challenge

If rebuilding from zero, I would retain:
- GitHub Issues as the durable mission/checkpoint mechanism;
- explicit direction discussion and separate plan approval;
- a technical operational plan written for the agent;
- a plain-language decision brief written for the user;
- evidence-based verification, issue recovery, immutable audit reports and controlled PR delivery;
- lightweight governance validation unrelated to labels.

I would remove:
- mandatory `state:*`, `type:*` and `area:*` classification for Issues;
- the label lifecycle workflow, classifier, tests and CI wiring;
- the hard-coded label taxonomy validator and label-only contract requirements;
- any active instruction that says mission Issues must carry lifecycle labels.

I would not:
- delete the global label catalogue, which is explicitly outside the chosen scope and cannot be reliably inspected here;
- remove Dependabot labels from PRs;
- delete or rewrite historical Issues or audit reports;
- remove general checkpoint, closure, evidence, priority or delivery rules merely because they currently sit near label-specific rules.

## Recommended direction for discussion

1. Remove the Issue-label lifecycle system comprehensively while keeping the catalogue and PR labels.
2. Preserve all Issue tracking guarantees that do not depend on labels.
3. Close #595 and #608 only after a fresh body/comment review and with an explicit explanation; leave broader Issues alone.
4. Clarify the workflow so the audit and decision-critical verification finish before the user is asked to approve a plan. Present the final plan in the Issue for the agent, then explain it in plain language in the conversation. Do not ask the user to approve a plan whose core investigation is still pending.
5. After the user validates the direction, prepare the detailed implementation plan in #609. Do not implement before that plan is explicitly approved.
