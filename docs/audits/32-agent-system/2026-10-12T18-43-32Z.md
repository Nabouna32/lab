## Executive summary

**Result: the core agent governance is substantially more coherent than in the previous audit, but the live Issue-label workflow has a confirmed lifecycle bug and two additional reliability/coverage gaps deserve follow-up.** Audit 32 is the correct procedure for this mission; it covers the collaboration contracts, validator/CI boundaries, live label automation, issue continuity, communication and the rebuild challenge.

The strongest finding is concrete: after Issue #592 was closed and its lifecycle label removed, targeted workflow run [#38291160712](https://github.com/Nabouna32/lab/actions/runs/38291160712) failed because the validator treated the closed Issue as missing a required `state:*` label. The contract only requires state/type labels on open Issues. The targeted event path fetches the Issue but does not check its current native state before validating it. This is a false failure, not evidence that the closed Issue is incorrectly labelled.

The workflow also emitted five runs within roughly one second when Issue #594 was created with four labels; one succeeded and four were cancelled by per-Issue concurrency. That does not prove persistent label corruption, but it exposes a need to test idempotency and interruption behavior around event bursts. The CI change classifier is another coverage gap: its safety-critical shell logic has no dedicated behavioral tests, while the governance validator checks selected strings in the workflow.

The earlier audit findings on audit numbering/catalogue integrity and plan-approval communication have been addressed in merged changes. The live workflow's closed-Issue failure and a stale closed-Issue checkpoint were not caught by those improvements. Follow-ups are tracked in #595, #596 and #597. No implementation was performed during this read-only audit.

## Results by required coverage

### 1. Bootstrap and source of truth

**OBSERVED:** Current `main` is `f04760d10253742334979da1441c480b3ca010e0`, the merge commit for PR #593 / Issue #592. No open PRs were returned at the audit checkpoint. The required entry-point and contract files were fetched from GitHub during this audit rather than assumed to be present from prior context.

**OBSERVED:** The active `Protect main` repository ruleset was read directly. It targets the default branch, requires a pull request and the `Node.js 24.21.0` status check, requires the PR base to be current, prohibits deletion and force pushes, and has no bypass actors. The API reports that the current user cannot bypass it. The separate branch-protection endpoint returned 403, but the active ruleset exposed the relevant delivery rules.

**ASSESSMENT:** The source-of-truth hierarchy and bootstrap are clear and actionable. Retain them. Remote-only limitations are explicitly documented and this audit did not claim local execution.

### 2. Decision rights

**OBSERVED:** The common contract distinguishes recommendations, consequential decisions, plan approval and routine implementation. It gives the user final authority over consequential direction, requires explicit validation before changing direction, and tells the assistant to diagnose ordinary technical failures autonomously.

**ASSESSMENT:** No material contradiction was found in the current decision-rights model. Retain it; avoid turning routine technical choices into repeated approval requests.

### 3. Plan traceability and approval

**OBSERVED:** The common contract requires a bidirectional coverage review between the Issue and plan, maps important acceptance criteria to evidence, and requires a concise decision brief in the user's language before plan approval. The Issue protocol reinforces the separation between direction approval and implementation-plan approval.

**OBSERVED:** The previous audit's finding about missing conversational decision briefs is reflected in current contracts and was delivered by PR #578. The related limitation remains accurate: written rules and static tests cannot prove every future response will follow them.

**OBSERVED — LOW:** Issue #577 was closed automatically by merged PR #581, but its Issue body still contains unchecked implementation tasks and a next action to begin implementation. The PR body and CI contain the actual result, so delivery evidence exists, but the Issue alone presents stale status. This weakens resumability and is tracked in [#596](https://github.com/Nabouna32/lab/issues/596).

**ASSESSMENT:** The plan model is strong. Closure needs to preserve the Issue checkpoint as well as the PR's delivery evidence; automatic closure by a PR does not guarantee the Issue body is current.

### 4. Autonomy and escalation

**OBSERVED:** The common contract instructs the assistant to wait for accessible required checks, inspect results and relevant logs, distinguish regressions from environment incidents, fix legitimate issues and rerun checks. It reserves escalation for material changes in direction or risk.

**ASSESSMENT:** This is a sound balance. Do not add approvals for routine fixes. The current static validator cannot prove that the assistant follows this behavior in every conversation; the contract appropriately avoids claiming that it can.

### 5. Issue continuity and recovery

**OBSERVED:** Mission Issues normally contain plans, checkpoints, decisions, verification evidence and next actions. Issue #577 is a concrete counterexample: it was closed by PR #581 while its body retained stale unchecked work, despite the PR having the final verification evidence.

**OBSERVED:** The #592 mission was closed with a final checkpoint and effective labels were checked. The subsequent live workflow failure on that closed Issue shows that Issue closure semantics and workflow event semantics were not tested together.

**ASSESSMENT:** The operational checklist is valuable, but its application remains behavioral rather than mechanically guaranteed. The stale checkpoint is tracked in #596; the closed-Issue workflow defect is tracked in #595.

### 6. Contract coherence

**OBSERVED:** The common contract defines the canonical label taxonomy and says its operational checklist applies to open Issues. The Issue protocol refers to that canonical source and adds mission-specific application guidance. These documents agree on the intended lifecycle: closed Issues do not require a `state:completed` label or an open-state label.

**OBSERVED — MEDIUM:** The live validator does not implement that distinction on its targeted path. `agents/issue-label-lifecycle.mjs` uses the open-only list for full audits, but for an Issue event it fetches the Issue by number and immediately calls `validateIssueLabels`, without checking the fetched Issue's `state`. The workflow subscribes to `unlabeled`, so removing a lifecycle label from a closed Issue can cause the false failure recorded in run #38291160712.

**ASSESSMENT:** This is a real contract-to-runtime mismatch. The correct direction is to make targeted validation respect the current native Issue state and to add event-path tests, not to require labels on closed Issues or weaken the contract.

### 7. Validator quality

**MEASURED:** CI run [#38261552452](https://github.com/Nabouna32/lab/actions/runs/38261552452) passed 21 governance tests with zero failures and ran the workflow-contract validator, which checked 33 audit procedures, contiguous specialist IDs 01–32, reserved audit 99, metadata and catalogue consistency. The run also passed the PR-base freshness check on the reviewed PR head. It is PR-event evidence; no separate post-merge full CI run is claimed.

**OBSERVED:** The audit catalogue validator now parses exact metadata lines and checks catalogue-to-file and file-to-catalogue relationships. Negative fixtures cover missing/duplicate metadata, mismatched paths, malformed/stale catalogue links and duplicates. This resolves the previous audit's #573 validator findings; PR #576 merged.

**OBSERVED — MEDIUM:** Live-label unit tests cover canonical/missing/ambiguous labels and suspended-state fields, but do not test the orchestration behavior for a closed Issue or a targeted event that occurs after closure. The contract validator checks that expected event names and selected workflow strings exist; it does not prove the event handler respects the native Issue state. This gap allowed the confirmed false failure to pass CI.

**OBSERVED — LOW/MEDIUM:** The CI change classifier in `.github/workflows/ci.yml` contains important fail-closed checks for paginated changed-file retrieval, count mismatch, empty path lists and the API's 3,000-file limit. However, there are no dedicated behavioral tests for the classifier itself; current checks mostly assert the presence of selected strings. Tracked in [#597](https://github.com/Nabouna32/lab/issues/597). No actual classifier regression was demonstrated.

### 8. CI efficiency and coverage

**OBSERVED:** Governance-only PRs run the dependency-free Node tests and contract validator in the lightweight change-detection step, while ordinary code/dependency changes run the full configured suite. The required check name remains `Node.js 24.21.0`; PR base freshness is checked. The lightweight path intentionally skips dependency installation, lint, typecheck, the full application test suite and build when only governance paths change.

**MEASURED:** The manual full audit [#38290975852](https://github.com/Nabouna32/lab/actions/runs/38290975852) succeeded on `main` and inspected 20 open Issues: 20 compliant without mutation, zero corrections and zero requiring explicit resolution. This result is valid for those 20 Issues at that time; it does not cover closed Issues or the later event-path failure.

**OBSERVED:** The closure-triggered run [#38291160712](https://github.com/Nabouna32/lab/actions/runs/38291160712) failed on the closed #592, while the targeted run for #594 [#38292086391](https://github.com/Nabouna32/lab/actions/runs/38292086391) succeeded. When #594 was created with four labels, five workflow runs appeared within about one second: one succeeded and four were cancelled under per-Issue `cancel-in-progress` concurrency.

**DEDUCED:** Event cancellation is intended to coalesce rapid changes, but the current tests do not establish whether a cancellation during multiple sequential label deletions can leave a partially applied correction. No such persistent corruption was observed. Test idempotency and interruption safety before redesigning concurrency.

**ASSESSMENT:** The lightweight/full-suite split is proportionate and should be retained. Add focused tests for the classifier and event lifecycle; do not add full application builds to governance-only PRs merely to increase check volume.

### 9. Delivery integrity

**OBSERVED:** The active ruleset requires a PR and the named CI check, keeps the base current, disallows force pushes/deletion and has no bypass actors. No open PR was found at the audit checkpoint. PR #593 was merged normally after its PR CI succeeded on the reviewed head.

**LIMITATION:** The available evidence establishes the active ruleset configuration and PR-event CI results. It does not establish a post-merge full application build for the current main commit, and none is claimed.

**ASSESSMENT:** The delivery model is sound. Retain controlled manual merge and explicit evidence checks.

### 10. Communication and evidence

**OBSERVED:** The common contract now requires a user-language decision brief before plan approval and a discreet, proportionate response-quality review. The emoji convention is canonical in the common contract; the entry point points to it without a fixed quota or duplicated detailed rule.

**ASSESSMENT:** Do not try to enforce subjective communication behavior with brittle static tests or mandatory visible receipts. Keep structural checks limited to properties they can actually prove, then assess runtime behavior through real mission examples.

### 11. Portfolio and interruption judgment

**OBSERVED:** Issue #461 remains open with `state:waiting`; its body says the HIGH-severity `braces@3.0.3` advisory is unresolved and that a remediation/risk-treatment decision is still required. The latest inspected dependency-monitoring run [#38241098791](https://github.com/Nabouna32/lab/actions/runs/38241098791) failed with npm reporting five HIGH package entries, including the `braces` advisory GHSA-vfj7-8cjw-p6xm in the development dependency chain. The run is real evidence that the gate remains active; it is not proof of a production exploit or a new check of upstream patch availability.

**ASSESSMENT:** This is a separate, higher-risk portfolio item than the low/medium governance improvements in this audit. Do not silently change its priority or weaken the gate. The next portfolio discussion should resolve the existing #461 treatment decision before spending time on lower-priority polish, unless new evidence changes urgency.

### 12. Rebuild challenge

If designing the system today from zero, I would retain:
- one shared contract for decision rights, evidence, continuity and delivery;
- short entry-point guidance and genuinely domain-specific specialist procedures;
- the Issue as the durable operational checkpoint;
- the dependency-free validator and targeted live-label workflow;
- the lightweight governance CI path, protected PR merge and immutable historical audit reports.

I would improve:
- explicit state handling in the live-label event path;
- behavioral tests for event orchestration and the CI classifier, rather than relying on string-presence checks for those guarantees;
- the final checkpoint discipline when a PR closes an Issue automatically.

I would **not** add a broad agent framework, duplicate every shared rule into each specialist document, require a state label on closed Issues, weaken the dependency gate, or pretend static validation can prove conversational behavior. The right next step is a small, evidence-led reliability correction, followed by focused tests and observed workflow behavior.

The next correction should focus on the confirmed closed-Issue false failure and event-path coverage (#595), then the CI classifier tests (#597). The open HIGH-severity dependency advisory tracked in #461 remains the more important portfolio risk and requires its already-documented explicit treatment decision. This audit does not authorize implementation of any follow-up. The historical report is evidence only; each follow-up must use its own validated implementation plan.
