## 6. Observed results

### 6.1 Token foundation

**OBSERVED — INFO**

`src/app/globals.css` contains a compact semantic token layer covering:

- background/foreground/surface roles;
- muted and border roles;
- accent roles;
- info/success/warning/danger base roles;
- radii from small through 2xl plus pill;
- three shadow levels;
- focus ring;
- three motion durations;
- three content-width values.

Light and dark themes override the same semantic variables through `.dark`.

This is a good foundation: consumers generally reference semantic variables rather than embedding the palette repeatedly.

### 6.2 Theme architecture

**OBSERVED — INFO**

The theme model is intentionally simple: light/dark semantic variables with a system option supplied by the theme provider. The global stylesheet also respects `prefers-reduced-motion`.

**PRESERVE**

The current semantic-variable approach is preferable to duplicating separate light/dark component styles. It is lightweight, understandable and compatible with future tool-specific compositions.

### 6.3 Shared primitive adoption

Targeted repository searches show meaningful reuse of the shared primitives:

**OBSERVED — INFO**

### 6.4 Semantic status-color defect

**OBSERVED — HIGH**

`globals.css` defines:

- `--success` and `--success-soft`;
- `--warning` and `--warning-soft`;
- `--danger` and `--danger-soft`;
- `--info` and `--info-soft`.

It does **not** define `--success-foreground` or `--danger-foreground`.

Those variables are nevertheless consumed in multiple production components, including:

- `src/app/[locale]/compte/connexion/page.tsx`;
- `src/app/[locale]/compte/email/page.tsx`;
- `src/app/[locale]/compte/inscription/page.tsx`;
- `src/app/[locale]/compte/suppression/page.tsx`;
- `src/app/[locale]/compte/mot-de-passe/page.tsx`;
- `src/app/[locale]/compte/mot-de-passe-oublie/page.tsx`;
- `src/app/[locale]/compte/mot-de-passe/reinitialiser/page.tsx`;
- `src/components/account/AccountActionLink.tsx`;
- `src/components/account/SubmitButton.tsx`.

The most consequential case is `SubmitButton`: its danger variant attempts to use `var(--danger-foreground)` as its border/background color. Because that custom property is absent, those declarations are invalid CSS rather than a valid semantic danger surface.

**DEDUCED — HIGH**

The current design-system contract is internally inconsistent: consumers can request semantic foreground roles that the token layer does not provide. This makes status/danger styling depend on CSS fallback/inheritance instead of a defined design token.

This is not merely cosmetic. It can weaken visual error/warning differentiation and make destructive actions fail to render with the intended semantic styling.

**PROPOSED**

Define a complete semantic status-token model, preferably with explicit foreground roles for every status that needs text or controls, then validate references so undefined semantic tokens cannot reach production.

**À VALIDER**

Whether the desired status-token model should be:

- a full `*-foreground` pair for info/success/warning/danger;
- or a smaller model where foreground always uses the global foreground and only status backgrounds are specialized.

The audit recommends the first because it makes contrast and component intent explicit, but this remains a design-system decision.

### 6.5 Radius vocabulary is only partially governed

**MEASURED — MEDIUM**

The repository already defines semantic radii:

- `--radius-sm`;
- `--radius-md`;
- `--radius-lg`;
- `--radius-xl`;
- `--radius-2xl`;
- `--radius-pill`.

However, targeted searches found direct radius choices outside that vocabulary, including:

- `rounded-2xl` in 16 files;
- `rounded-3xl` in 2 files;
- `rounded-full` in 4 files;
- `rounded-lg` in 2 files;
- `rounded-[1.35rem]` in `ToolSearch.tsx`.

The same visual concept can therefore be expressed either through the design token layer or directly through Tailwind's scale/arbitrary values.

**DEDUCED — MEDIUM**

This is acceptable while the codebase is small, but it weakens the claim that radii are governed tokens. At hundreds of tools, local choices will gradually create visual drift even if every individual choice looks reasonable.

**PROPOSED**

Keep Tailwind as the implementation mechanism, but establish an explicit rule:

- shared/platform components use semantic design tokens;
- tool-local components may use Tailwind values only when the variation is intentional;
- arbitrary radius values require an explicit reason.

A small static check could enforce this boundary without creating a heavy design-system runtime.

### 6.6 Token taxonomy is incomplete

**OBSERVED — MEDIUM**

The token layer governs colors, radii, shadows, motion durations and content widths, but there is no comparable semantic vocabulary for:

- spacing scale;
- typography roles/type scale;
- line-height roles;
- font weights;
- breakpoint names;
- motion easing;
- motion distance/transform intensity.

Those dimensions are largely expressed through Tailwind defaults and local utility classes.

**DEDUCED — MEDIUM**

The current approach is simple, but it means the design system is only partially a token system. A future contributor can remain visually consistent with existing components without ever consulting a documented design-token contract because much of the system lives implicitly in Tailwind's default scale.

This is the main scalability weakness: the code has a visual system, but not yet a fully explicit **governance system** for that visual system.

**PROPOSED**

Do not introduce tokens for every Tailwind utility. Instead formalize only the decisions that are intended to be brand/product-level invariants:

- semantic colors;
- surface/border roles;
- radius tiers;
- elevation tiers;
- spacing rhythm;
- typography roles;
- motion duration/easing;
- responsive layout tiers.

Tailwind should remain the low-level composition layer.

### 6.7 Primitive APIs versus tool diversity

**OBSERVED — MEDIUM**

The shared primitives are deliberately small:

- `Card` mainly provides surface/border treatment and optional link behavior;
- `Panel` provides a surface with `div|section`;
- `ResultPanel` has a narrow `accent|neutral` tone API;
- `Button` has `primary|secondary|ghost`;
- `TextField`, `TextArea` and `Select` standardize common form controls.

At the same time, representative tool implementations still contain many local surface recipes and editorial primitives.

**CHALLENGE**

It would be tempting to solve this by creating a universal `ToolCard`, `ToolPanel`, `ToolLayout`, `ToolResult`, etc. with many variants.

That would be the wrong direction.

The product explicitly wants small utilities, advanced tools and mini-applications to retain different compositions. A large variant-heavy component library would likely turn into a lowest-common-denominator renderer and make unusual tools harder to build.

**PROPOSED**

Keep primitives intentionally small and composable. Add **recipes/patterns** only when the same interaction structure is demonstrably repeated, rather than creating one component for every visual shape.

The missing layer is therefore more about documented recipes and token governance than about adding dozens of components.

### 6.8 Motion

**MEASURED — LOW**

Motion durations are mostly tokenized through `--motion-fast`, `--motion-standard` and `--motion-slow`.

Targeted searches nevertheless found direct `duration-200` usage in 3 files and `duration-150` in 1 file.

**OBSERVED — INFO**

The global `prefers-reduced-motion: reduce` rule disables/reduces animation and transition duration and removes smooth scrolling.

**DEDUCED — LOW**

The accessibility baseline is strong, but the motion design language is incomplete. Duration is governed; easing and movement intensity are not.

**PROPOSED**

Keep motion deliberately small. If a motion system is expanded, add a few semantic easing/intensity recipes rather than a large animation taxonomy.

### 6.9 Typography

**OBSERVED — MEDIUM**

Geist and Geist Mono are consistently established at the layout level. However, typography is primarily expressed directly through Tailwind utility combinations rather than semantic roles.

Examples include repeated combinations of:

- `text-sm`;
- `text-base`;
- `text-3xl`;
- `text-4xl`;
- `text-5xl`;
- `font-bold`;
- `font-black`;
- custom tracking values.

**DEDUCED — MEDIUM**

The typography is coherent enough today, but there is no explicit contract distinguishing, for example, page title, tool title, result value, supporting label, metadata, and editorial body roles.

That makes future large-scale tool contribution more dependent on copying existing code.

**PROPOSED**

Define a small semantic type-role vocabulary for platform surfaces while allowing tool-specific typography when justified. This should remain a role layer over Tailwind, not a replacement for Tailwind.

### 6.10 Breakpoints and responsive governance

**OBSERVED — MEDIUM**

The code consistently uses Tailwind responsive tiers such as `sm` and `lg`, and platform containers use semantic content-width variables.

No project-specific breakpoint token/contract was found.

**DEDUCED — LOW/MEDIUM**

Using Tailwind defaults is not inherently a problem. The risk is governance: the project has an explicit product requirement for desktop, tablet and mobile first-class behavior, but breakpoint intent is not encoded as a design-system rule.

**PROPOSED**

Document breakpoint intent rather than necessarily introducing new CSS variables. For example, define which layout transitions are considered mobile, compact/tablet and wide-desktop decisions.

### 6.11 i18n compatibility

**OBSERVED — INFO**

Shared interactive primitives generally accept labels as props, while action primitives such as `CopyButton` and `ClearButton` obtain localized labels through the current locale/message system.

This is compatible with the product's requirement that translations remain product content rather than hard-coded UI strings.

**PRESERVE**

Do not bake locale-specific strings into generic visual primitives. The current prop/message approach is the correct boundary.

### 6.12 Accessibility and contrast

**MEASURED — INFO**

Calculated contrast ratios from the audited light/dark token values include:

| Combination | Contrast |
|---|---:|
| light muted `#68686f` on `#f7f7f8` | 5.16:1 |
| dark muted `#a4a4ad` on `#101012` | 7.69:1 |
| light accent `#5b4de3` on white | 5.81:1 |
| dark accent `#9b90ff` on `#121117` | 7.00:1 |
| light success `#167a55` on white | 5.32:1 |
| light warning `#9a6500` on white | 4.96:1 |
| light danger `#bf3f46` on white | 5.23:1 |

These values indicate that the defined primary semantic palette is broadly capable of meeting normal-text AA contrast.

**OBSERVED — HIGH**

A separate concrete problem exists in the header/account styling: several components explicitly use `text-white` on `var(--accent)`. In dark mode the accent is `#9b90ff`, for which white text has only about **2.68:1** contrast.

The most obvious example is the Loculary header mark in `src/components/layout/Header.tsx`, and account submit buttons also explicitly use white text.

**DEDUCED — HIGH**

The dark theme's semantic accent token already defines `--accent-foreground: #121117` specifically for this purpose, but several consumers bypass it with `text-white`. This creates a real theme-specific accessibility regression.

**PROPOSED**

Replace hard-coded white-on-accent patterns in platform components with the semantic `--accent-foreground` token. Keep literal white/black only for genuinely content-specific use cases such as image/palette previews where the color is part of the content.

- **Evidence:** dark `--accent` is `#9b90ff`; header mark and several account controls use `text-white`; calculated white-on-accent contrast is ~2.68:1.
- **Impact:** fails WCAG AA normal-text contrast when the text is meaningful.
- **Reproduction:** enable dark theme and inspect `Header.tsx` / account submit controls.

### F-09-03 — Tokenization is incomplete and weakly governed

- **Severity:** MEDIUM
- **Status:** OBSERVED + MEASURED + DEDUCED
- **Evidence:** semantic tokens exist for colors/radii/shadows/motion/content widths, but spacing/typography/breakpoints/easing are mostly implicit; direct radius variants remain across the codebase.
- **Impact:** increasing visual drift and contributor dependence on copying existing implementation details.
- **Reproduction:** inspect `globals.css` and targeted radius/motion searches.

### F-09-04 — Shared primitives do not yet provide a governance layer for repeated recipes

- **Severity:** MEDIUM

- **Evidence:** high reuse for form/action primitives, but many platform/account/editorial/tool surfaces still encode local recipes.
- **Impact:** consistency depends on discipline rather than enforceable or discoverable patterns.

### F-09-05 — Motion system is only partially semantic

- **Severity:** LOW

- **Evidence:** duration tokens exist, but direct duration utilities remain and no semantic easing/intensity vocabulary exists.
- **Impact:** small long-term drift; limited immediate product risk.

## 8. Weaknesses and suboptimal choices

1. **The token layer is useful but not complete.** It solves palette/theme concerns better than spacing/type/responsive governance.
2. **Undefined semantic tokens are allowed into production.** This is the clearest design-system correctness gap.
3. **Semantic tokens are not consistently preferred by platform components.** `text-white` is the concrete example that breaks dark-theme contrast.
4. **The design system is more of a set of conventions than a governed contract.** Contributors can use the right system, but the repository does not strongly prevent semantic drift.
5. **The primitive layer is intentionally small, but its patterns are not sufficiently codified.** The solution should be recipes and validation, not a huge component abstraction.

## 9. Challenges to the current design

### Challenge A — Should Loculary build a heavier component/design-token framework?

**Answer: reject/defer.**

A heavyweight design-system runtime, CSS-in-JS token engine or large UI-kit abstraction would add complexity without solving the central problem. Loculary already has Tailwind 4, semantic CSS variables and small React primitives.

A lighter governance layer is a better fit.

### Challenge B — Should every tool use the same surface components?

**Answer: reject.**

That conflicts with the explicit product direction allowing small tools, advanced tools and mini-applications to have different compositions and visual identities.

### Challenge C — Should all visual values become tokens?

**Answer: reject.**

Tokenizing every `gap`, `padding`, font size and border radius would create ceremony and make legitimate local composition harder.

Only product-level invariants should become semantic tokens.

### Challenge D — Should the current CSS-variable + Tailwind foundation be preserved?

**Answer: preserve, with governance improvements.**

It is the simplest credible foundation for the current scale and future catalog growth. The audit does not find evidence that replacing the underlying styling stack would improve the product.

## 10. Elements to preserve

- semantic light/dark CSS variables;
- `--accent-foreground` rather than hard-coded foreground assumptions;
- reduced-motion handling;
- small reusable interaction primitives;
- tool-specific composition freedom;
- localized component labels and message-driven UI;
- shared tool-page shell;
- semantic content-width tokens;
- the distinction between platform contracts and tool-owned visual composition;
- Tailwind as the low-level composition layer.

## 11. Proposals

### P-09-01 — Complete semantic status tokens

Add a deliberate status-token contract for foreground/background roles and ensure every referenced semantic token is defined.

### P-09-02 — Add design-token reference/guidance

Document only the semantic design decisions that contributors must preserve: colors, status roles, radii, elevation, typography roles, spacing rhythm, motion and responsive intent.

### P-09-03 — Add static token-reference validation

Introduce a machine-checkable test/lint rule that detects references to undefined project semantic variables in `src/`.

This should be scoped carefully so arbitrary browser/CSS variables and third-party content are not falsely flagged.

### P-09-04 — Establish platform-versus-tool styling boundaries

Define a small rule set:

- platform/shared components: semantic tokens first;
- tool-local visual experiments: local utilities allowed;
- arbitrary values: acceptable when the variation is intentional and local;
- repeated pattern: promote to a primitive or recipe only after evidence of reuse.

### P-09-05 — Prefer semantic foreground tokens in theme-sensitive controls

Platform controls that sit on semantic surfaces should use `--accent-foreground` / future status foreground tokens rather than literal `text-white` or `text-black`.

## 12. Decisions requiring explicit validation

1. **À VALIDER:** exact semantic status-token taxonomy, especially whether info/success/warning/danger should each have explicit foreground roles.
2. **À VALIDER:** whether token-reference validation should be a required CI check.
3. **À VALIDER:** whether the design system should formalize a small typography/spacing/responsive role vocabulary now, or defer until the catalog becomes materially larger.
4. **À VALIDER:** whether arbitrary visual values in tool-local components should require an explicit code-level convention/documentation rule.

These are recommendations, not decisions.

## 13. Implementation scope and plan

If the proposals are validated, the smallest coherent implementation sequence would be:

1. define the semantic status foreground model;
2. replace theme-sensitive hard-coded foreground colors in shared/platform components;
3. add a focused automated validation for undefined semantic design variables;
4. document the semantic design-system contract;
5. audit and normalize the highest-value shared/platform outliers;
6. leave intentionally distinctive tool-local composition untouched;
7. add focused tests for theme/contrast/token integrity.

No full component-library rewrite is recommended.

## 16. Conclusion

**Évaluation globale : design system sain comme fondation, mais insuffisamment gouverné pour son ambition de très grand catalogue.**

La base actuelle est bonne : semantic CSS variables, thèmes, petits primitives, Tailwind, reduced-motion et liberté de composition sont des choix pragmatiques et cohérents avec Loculary.

Le problème principal n'est pas l'absence d'un framework de design system. C'est l'écart entre une **fondation visuelle déjà présente** et un **contrat de design system encore partiellement implicite**.

Les deux corrections prioritaires sont concrètes :

1. **HIGH — réparer les tokens foreground de statut manquants ;**
2. **HIGH — éliminer les usages hard-codés de blanc sur l'accent sombre et utiliser les foreground tokens sémantiques.**

Ensuite, le meilleur investissement est une gouvernance légère : quelques invariants explicites + validation automatisée, plutôt qu'une refonte lourde.

### Réponse from-scratch

**Si Loculary était construit aujourd'hui, nous ne choisirions pas une autre stack UI.** Nous conserverions CSS variables + Tailwind + primitives React.

En revanche, nous concevrions dès le départ trois couches explicitement séparées :

1. **Tokens sémantiques** — décisions de marque/accessibilité/thème.
2. **Recipes/primitives** — comportements et patterns réutilisables.
3. **Tool composition** — liberté visuelle locale sous contraintes de plateforme.

Cette séparation préserverait la diversité voulue par Loculary tout en empêchant le catalogue de dériver visuellement à mesure qu'il grandit.
