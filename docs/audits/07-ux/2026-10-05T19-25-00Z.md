## 6. Résultats observés

### 6.1 Homepage — bonne direction structurelle

**OBSERVÉ — À PRÉSERVER**

La homepage suit réellement la direction validée « action/search first » :

1. message « Que voulez-vous faire ? » ;
2. description courte ;
3. recherche principale ;
4. suggestions rapides ;
5. quelques outils ;
6. exploration par domaine.

Le HTML de production actuel confirme cette hiérarchie. Le contenu n'est pas construit comme une landing page marketing avec un long préambule avant l'outil.

**CHALLENGE**

La structure est saine pour le catalogue actuel. Je ne recommande pas de remplacer cette homepage par une grille de catégories ou un hero marketing.

**PROPOSÉ**

Conserver cette base et investir prioritairement dans la qualité de la recherche et de la découverte plutôt que dans l'ajout de sections décoratives.

---

### 6.2 Header et navigation — simple, mais déjà chargé en contrôles

**OBSERVÉ — INFO / À PRÉSERVER AVEC VIGILANCE**

Le header expose selon le contexte :

- recherche ;
- accès à tous les outils ;
- compte ;
- langue ;
- thème ;
- menu mobile.

Sur desktop, la recherche est directement visible. Sur mobile/tablette, elle devient une action ouvrant un champ dédié. Les tests Playwright vérifient explicitement ce comportement à 390 px, 820 px et 1024 px sur le parent produit identique.

**CHALLENGE**

Le header reste acceptable, mais il cumule déjà plusieurs affordances secondaires. À mesure que Loculary ajoutera favoris, historique, collections, etc., il faudra éviter d'utiliser le header comme conteneur universel de toutes les fonctions.

**PROPOSÉ**

Préserver la recherche comme action principale et maintenir les fonctions secondaires derrière des surfaces dédiées plutôt que d'allonger progressivement le header.

---

### 6.3 Recherche — fondation solide mais feedback asynchrone insuffisant

**MEDIUM — OBSERVÉ / DÉDUIT**

`ToolSearch.tsx` charge `search-client` dynamiquement puis met à jour `results` et `resultsQuery`.

Pendant l'intervalle entre une modification de `query` et la résolution du chargement/recalcul, `visibleResults` vaut vide lorsque `normalizeSearchText(query) !== resultsQuery`.

Or l'interface affiche immédiatement le bloc « aucun résultat » lorsque `showResults` est vrai et que `visibleResults.length === 0`.

Conséquence : l'état « recherche en cours » n'est pas distingué de l'état « aucune correspondance ».

**DEDUIT**

Sur un chargement initial ou une frappe suffisamment lente pour laisser apparaître l'état intermédiaire, l'utilisateur peut voir une absence de résultat alors que la recherche n'a pas encore fini de produire ses résultats.

Le problème est structurel dans le composant ; il ne dépend pas d'un cas exotique du catalogue.

**CHALLENGE**

Pour une fonctionnalité stratégique comme la recherche, un état implicite ne doit pas être interprété comme un état métier. Le système devrait avoir au minimum :

- idle ;
- searching ;
- results ;
- no-results ;
- éventuellement error.

**PROPOSÉ**

Ajouter un état de recherche explicite, idéalement piloté par la requête courante et la fin du calcul. Le no-result ne devrait apparaître qu'après résolution effective de la requête.

**À VALIDER**

Le niveau de feedback souhaité : indicateur visuel discret pendant la recherche ou simple maintien de l'état précédent jusqu'à résolution.

---

### 6.4 Recherche — bon support des requêtes naturelles simples

**OBSERVÉ / MESURÉ**

Le smoke test vérifie réellement :

> « calculer 17 % de 283 »

et obtient « Calculateur de pourcentage », avec catégorie et description.

Le moteur prend en compte :

- nom ;
- description ;
- tags ;
- aliases ;
- catégories ;
- tolérance typographique ;
- mots ignorés ;
- scoring multi-termes.

**ÉLÉMENT À PRÉSERVER**

C'est une bonne base pour la promesse « trouver un outil sans connaître exactement son nom ».

**CHALLENGE**

Le moteur reste un moteur de recherche de catalogue enrichi, pas encore un moteur d'intention. C'est cohérent avec le niveau actuel du produit et il serait prématuré de brancher de l'IA simplement pour masquer cette limite.

**PROPOSÉ**

Continuer à enrichir le modèle déterministe avant toute couche IA : synonymes, intentions structurées, reformulations et signaux comportementaux mesurables.

---

### 6.5 No-result — utile, mais encore trop statique

**MEDIUM — OBSERVÉ**

Le no-result propose des suggestions fixes définies dans les messages de locale.

C'est préférable à un écran vide, mais les suggestions ne sont pas déduites de la requête ni du contexte de navigation.

**CHALLENGE**

Pour un utilisateur qui cherche une capacité absente, une liste fixe ne répond pas toujours à l'intention réelle.

**PROPOSÉ**

À terme, proposer un second niveau de récupération :

1. reformulations liées à la requête ;
2. outils proches ;
3. catégorie probable ;
4. éventuellement « proposer un outil ».

La dernière possibilité reste une proposition produit et n'est pas une décision actuelle.

---

### 6.6 Page « Tous les outils » — bonne architecture de découverte, intention encore incomplète

**MEDIUM — OBSERVÉ / DÉDUIT**

La page catalogue expose :

1. titre/description ;
2. recherche ;
3. intentions ;
4. catégories ;
5. catalogue complet.

Cela correspond bien à l'idée d'un Explorer séparé de la homepage.

Cependant `intentCategoryMap` transforme actuellement une intention en **une seule catégorie** :

- calculate → calculations ;
- convert → computing ;
- generate → development ;
- analyze → files/video, avec le premier domaine disponible ;
- measure → dates/calculations, avec le premier domaine disponible.

L'utilisateur qui choisit « Convertir » n'obtient donc pas une vue « tous les outils de conversion ». Il est redirigé vers un domaine choisi par le mapping.

**CHALLENGE**

C'est une approximation utile pour le MVP, mais pas une véritable architecture d'intention. Elle risque de devenir trompeuse lorsque le catalogue se diversifiera.

**PROPOSÉ**

À terme, une intention devrait produire un ensemble de résultats filtrés ou une page d'intention, sans perdre les catégories sous-jacentes.

Alternative plus simple à court terme : assumer explicitement que ces chips sont des raccourcis vers des domaines, et ne pas les présenter comme des intentions générales.

**À VALIDER**

Choisir entre :
- intention réelle ;
- raccourci de catégorie assumé ;
- page intermédiaire d'intention.

---

### 6.7 Catalogue complet — acceptable à 42 outils, pas encore un modèle à très grande échelle

**OBSERVÉ**

Le catalogue actuel contient 42 outils publiés. La page « Tous les outils » rend l'ensemble sous forme de grille de cartes.

À ce volume, la structure reste raisonnable et la recherche placée au-dessus réduit la dépendance au défilement.

**CHALLENGE**

La décision serait différente à plusieurs centaines d'outils. Une grille exhaustive deviendrait une surface de découverte médiocre, même si elle reste techniquement fonctionnelle.

**PROPOSÉ**

Conserver le catalogue complet pour le volume actuel, mais prévoir une bascule progressive vers :

- recherche ;
- filtres ;
- catégories ;
- intentions ;
- pagination/virtualisation si nécessaire ;
- tri pertinent.

Aucune migration n'est recommandée maintenant sur la seule base du volume actuel.

---

### 6.8 Page d'outil — hiérarchie générale bonne, ordre des « next actions » discutable

**MEDIUM — OBSERVÉ**

La page d'outil suit :

- breadcrumb ;
- identité concise ;
- statut de processing ;
- runtime de l'outil ;
- « Pour continuer » / related tools ;
- documentation éditoriale.

Le HTML production du calculateur de pourcentage confirme cet ordre : « Pour continuer » apparaît avant les sections « Calculer un pourcentage », « Mesurer une évolution... », etc.

Or `docs/UX.md` définit explicitement la hiérarchie recommandée :

> inputs → primary result → actions → explanation → documentation → related/discovery content.

Le code de `src/app/[locale]/[section]/[category]/[slug]/page.tsx` rend `RelatedTools` avant `ToolEditorial`.

**IMPACT**

L'utilisateur peut être invité à quitter ou poursuivre vers un autre outil avant d'avoir obtenu l'explication qui consolide sa compréhension du résultat.

**CHALLENGE**

Le choix « next tool immédiatement après le runtime » est défendable si la continuation est réellement contextuelle. Mais il n'est pas cohérent avec la hiérarchie UX durable actuellement documentée.

**PROPOSÉ**

Tester en priorité l'ordre :

> outil → résultat/actions → explication/documentation → « Pour continuer ».

Une variante possible est de conserver une micro-suggestion de continuation juste après le résultat et de réserver la section développée « Pour continuer » à la fin. Cela mérite une validation UX avant modification.

**À VALIDER**

L'ordre exact des related tools sur les pages d'outils.

---

### 6.9 Related tools — principal défaut UX actuellement observé

**MEDIUM — OBSERVÉ / MESURÉ**

Le moteur `src/lib/tools/relations.ts` calcule les relations à partir :

- de termes du nom français ;
- tags ;
- aliases ;
- bonus de catégorie.

Il ne consomme pas `relatedToolIds` pourtant présent dans le contrat `Tool`.

Sur la page production du **Calculateur de pourcentage**, les trois continuations actuellement affichées sont :

1. Calculateur de sous-réseau IPv4 ;
2. Calculateur de date ;
3. Calculateur de réduction.

Seul le troisième est naturellement proche du besoin « pourcentage ».

**IMPACT**

La section « Pour continuer » peut casser la promesse « next action utile » en affichant des outils techniquement valides mais sémantiquement faibles.

**CHALLENGE**

Le moteur automatique est plus simple à maintenir que des listes manuelles, mais la pertinence utilisateur est plus importante que l'absence de maintenance éditoriale.

Le champ `relatedToolIds` est actuellement une seconde source d'intention non consommée. L'audit 02 avait déjà identifié cette incohérence ; elle reste **TOUJOURS PRÉSENTE** après revalidation sur le commit actuel.

**PROPOSÉ**

À court terme, conserver un moteur automatique mais renforcer son score avec des signaux réellement sémantiques et éventuellement des relations éditoriales contrôlées.

À moyen terme, un modèle hybride est probablement le meilleur compromis :

- relations éditoriales explicites pour les associations importantes ;
- fallback algorithmique pour les cas non définis ;
- validation empêchant les relations incohérentes.

**À VALIDER**

Le modèle d'autorité des relations : algorithmique, éditorial ou hybride.

### 6.10 Processing/privacy — très bon pattern de confiance

**OBSERVÉ — À PRÉSERVER**

Chaque page d'outil inspectée expose un statut de traitement.

Pour le calculateur de pourcentage, la production affiche « Traitement local » avec une explication indiquant que le calcul reste dans le navigateur et qu'aucune donnée n'est envoyée à un serveur ni stockée par Loculary.

Le composant `ToolProcessingStatus` fournit également, pour les modes non locaux :

- stockage ;
- rétention ;
- fournisseurs externes ;
- catégories de données.

**CHALLENGE**

Le pattern est meilleur qu'un simple badge « privacy » car il rend la frontière de traitement inspectable sans monopoliser la page.

**ÉLÉMENT À PRÉSERVER**

Ne pas supprimer ou réduire cette transparence au profit d'un design plus minimaliste.

### 6.11 Résultats et feedback — primitives correctes

**OBSERVÉ — À PRÉSERVER**

`ResultPanel` utilise `aria-live="polite"` pour les résultats et distingue clairement état vide et valeur produite.

Les primitives `Button`, `TextField` et `ValidationMessage` fournissent :

- focus visible ;
- labels ;
- états invalides ;
- `role="alert"` pour les erreurs ;
- contrôles de taille raisonnable.

Les tests existants couvrent notamment :

- états vides ;
- erreurs ;
- copy ;
- reset ;
- calculs ;
- recherche clavier.

**CHALLENGE**

Il n'est pas nécessaire de créer un framework UX plus abstrait tant que les primitives actuelles couvrent correctement les patterns communs.

### 6.13 Footer et confiance — surface publique minimale

**LOW — OBSERVÉ**

Le footer public expose principalement :

- outils ;
- accueil ;
- compte ;
- tagline ;
- copyright.

Il ne fournit pas de chemin visible vers une information de confidentialité, d'aide, de contact ou de transparence générale depuis la surface publique principale.

**CHALLENGE**

Pour un produit qui place la confiance et la transparence au cœur de sa proposition, cette surface pourrait devenir insuffisante à mesure que le produit ajoute analytics, publicité, comptes et fonctionnalités externes.

**PROPOSÉ**

Prévoir à terme une surface publique claire pour :

- confidentialité/traitement ;
- aide/contact ;
- éventuellement conditions ou informations légales.

Ce constat ne constitue pas une conclusion juridique et ne prescrit pas le contenu légal à publier.

## 8. Faiblesses et choix sous-optimaux

### 8.1 Relations automatiques sans signal éditorial effectif

**OBSERVÉ**

Le contrat possède `relatedToolIds`, mais le moteur de rendu n'en tient pas compte.

**CHALLENGE**

Une propriété non consommée donne une illusion de contrôle éditorial. Il faut éviter deux autorités concurrentes.

**PROPOSÉ**

Décider explicitement d'un modèle unique ou hybride avant d'augmenter le catalogue.

### 8.2 Intentions représentées par des catégories

**OBSERVÉ**

Le concept d'intention existe dans l'UI mais son mapping est actuellement un raccourci vers une catégorie.

**CHALLENGE**

Cette simplification est acceptable à 42 outils mais risque de devenir trompeuse avec la croissance.

**PROPOSÉ**

Faire évoluer les intentions vers des filtres/résultats structurés lorsque le besoin est démontré.

### 8.3 Tests UX encore centrés sur le nominal

**OBSERVÉ**

Les tests Playwright sont utiles et nombreux, mais la recherche ne teste pas explicitement un état de chargement lent/intermédiaire, et les relations ne sont pas testées sur leur pertinence sémantique.

**PROPOSÉ**

Ajouter des scénarios ciblés lorsque les choix UX correspondants sont validés :

- recherche lente ;
- transition query A → query B ;
- no-result après résolution ;
- pertinence des related tools ;
- parcours intention → résultats.

## 9. Challenges à la conception actuelle

### Search-first

**DÉCISION D'AUDIT : PRÉSERVER**

La direction search/action-first est bonne. Une refonte vers un catalogue plus visuel ou une landing page marketing serait une régression pour la mission utility.

### Heuristique des relations

**DÉCISION D'AUDIT : MODIFIER / À VALIDER**

L'automatisation est intéressante mais ne doit pas sacrifier la pertinence. Le moteur actuel produit déjà des associations faibles.

### Documentation avant related tools

**DÉCISION D'AUDIT : À VALIDER**

La documentation doit rester secondaire, mais la relation « next action » doit normalement arriver après que l'utilisateur a compris le résultat.

### Intentions

**DÉCISION D'AUDIT : MODIFIER**

Le concept mérite d'être conservé ; son implémentation actuelle est trop proche d'un alias de catégorie.

### Primitives communes

**DÉCISION D'AUDIT : PRÉSERVER**

Les primitives communes et le framework ToolPage donnent une base suffisamment solide sans imposer une UI identique à chaque outil.

## 10. Éléments à préserver

- homepage **action/search first** ;
- recherche déterministe enrichie par descriptions, tags, aliases et tolérance typographique ;
- catalogue et registry centralisés ;
- diversité des interfaces d'outils ;
- processing status visible et inspectable ;
- anonymous-first ;
- feedback des résultats avec `aria-live` ;
- labels, focus visible et erreurs accessibles ;
- adaptation mobile/tablette/desktop déjà couverte par des scénarios Playwright ;
- documentation réelle dans les pages publiques ;
- séparation runtime/editorial ;
- approche local-first.

## 11. Propositions

### Priorité 1 — fiabiliser le feedback de recherche

Ajouter un état explicite « recherche en cours » et empêcher l'état no-result prématuré.

### Priorité 2 — corriger la pertinence des related tools

Décider du modèle de relations, puis implémenter un moteur cohérent. Le modèle hybride paraît le meilleur compromis, mais reste **PROPOSÉ**, pas décidé.

### Priorité 3 — repositionner la découverte secondaire

Tester l'ordre :

> outil → résultat/actions → explication → documentation → pour continuer.

### Priorité 4 — transformer les intentions en vraie découverte

Lorsque le catalogue justifie cette évolution, faire des intentions une vue de résultats plutôt qu'un mapping vers une seule catégorie.

### Priorité 5 — renforcer la surface de confiance publique

Ajouter une surface publique de confidentialité/aide lorsque les fonctions correspondantes deviennent centrales.

## 12. Décisions nécessitant validation

1. **Recherche :** faut-il afficher un indicateur de recherche ou simplement maintenir les résultats précédents jusqu'à résolution ?
2. **Relations :** modèle algorithmique, éditorial ou hybride ?
3. **Ordre de page outil :** related tools avant ou après documentation ?
4. **Intentions :** vraie couche de filtrage/découverte ou raccourcis de catégories assumés ?
5. **Footer/confiance :** quelles surfaces publiques de confidentialité, aide et information doivent être mises en avant ?

Aucune proposition ci-dessus n'est considérée comme une décision produit.

## 16. Conclusion

**STATUT : COMPLETED**

### Verdict

La base UX de Loculary est **bonne et cohérente dans sa direction**, mais elle possède déjà quelques mécanismes qui fonctionnent techniquement sans encore atteindre la qualité UX visée par la nouvelle direction.

Le point important est que **la fondation n'est pas à jeter**.

À préserver :
- search/action-first ;
- outil au centre ;
- processing transparent ;
- primitives accessibles ;
- responsive testé ;
- diversité des outils.

À challenger sérieusement :
1. la recherche doit distinguer « je cherche » de « il n'y a rien » ;
2. les related tools doivent devenir réellement pertinents ;
3. l'ordre des next actions et de la documentation doit être explicitement décidé ;
4. les intentions doivent devenir une vraie dimension de découverte si elles restent présentées comme telles.

### From scratch — si Loculary était construit aujourd'hui

Je repartirais avec exactement la même idée générale de **boîte à outils orientée action**, mais je formaliserais dès le départ trois index de découverte distincts :

- **texte / recherche** — « je sais approximativement ce que je veux » ;
- **intention** — « je sais ce que je veux accomplir mais pas quel outil » ;
- **relation / continuation** — « je viens d'obtenir ce résultat, quelle est la prochaine action utile ? ».

Le dépôt actuel possède déjà les trois embryons, mais ils sont encore partiellement confondus : le moteur de relations est heuristique, l'intention est mappée vers une catégorie et la recherche ne possède pas un cycle d'état explicite.

C'est le principal axe de maturation UX identifié par cet audit.

**Conclusion globale : MEDIUM.**

Le produit nominal fonctionne et la direction UX est saine. Les priorités sont de qualité de découverte et de confiance dans les suggestions, pas une refonte visuelle générale.
