## 6. Findings et anomalies

### F01 — Les quatre calculateurs financiers/proportionnels n'acceptent pas la saisie décimale française comme le reste du catalogue

**HIGH — OBSERVÉ**

Outils concernés :
- src/components/tools/percentage/PercentageCalculator.tsx
- src/components/tools/reduction/ReductionCalculator.tsx
- src/components/tools/tva/TVACalculator.tsx
- src/components/tools/regle-de-trois/RuleOfThreeCalculator.tsx

Preuve :
- ces composants convertissent leurs champs numériques avec `Number(value)` ;
- le projet possède pourtant `src/lib/numbers.ts::parseLocalizedNumber()`, qui normalise explicitement une virgule décimale en point ;
- plusieurs autres outils utilisent déjà `parseLocalizedNumber()` pour le même type d'entrée.

Impact :
- en français, une saisie courante telle que `12,5` est rejetée dans ces quatre outils alors que l'interface et les résultats sont localisés en français ;
- le comportement est incohérent entre outils ayant le même besoin numérique ;
- le problème touche directement la confiance dans des outils fondamentaux du catalogue.

MESURÉ / DÉDUIT :
- `Number("12,5")` n'est pas un nombre JavaScript valide ;
- le chemin partagé `parseLocalizedNumber("12,5")` produit au contraire 12.5.
- aucune correction n'a été appliquée pendant l'audit.

Challenge :
Le choix initial de `Number()` est simple mais n'est plus défendable alors qu'une primitive locale existe déjà et est utilisée ailleurs.

PROPOSÉ :
- centraliser toutes les saisies numériques utilisateur sur `parseLocalizedNumber()` lorsque l'entrée est textuelle ;
- ajouter des tests UI/outil sur les décimales françaises et anglaises ;
- vérifier les champs `type=number` séparément car le navigateur peut déjà normaliser leur valeur.

À VALIDER :
- si la règle doit devenir une convention globale obligatoire pour tous les outils numériques.

### F02 — Le calculateur Cron peut annoncer implicitement « aucune prochaine exécution » pour une expression valide

**HIGH — OBSERVÉ / MESURÉ**

Preuve :
- src/lib/tools/cron-expression.ts::getNextCronRuns()
- la recherche est limitée à `cursor + 366 jours`.

Cas reproductible :
- expression : `0 0 29 2 *` ;
- départ : 2026-03-01 ;
- la fenêtre inspectée se termine le 2027-03-02 ;
- la prochaine occurrence valide est le 2028-02-29.

MESURÉ par calcul indépendant :
- fenêtre actuelle : 366 jours ;
- prochaine occurrence : 730 jours après le départ.

Impact :
- une expression Cron parfaitement valide peut produire zéro résultat alors qu'une prochaine exécution existe ;
- pour un outil présenté comme calculateur de prochaines exécutions, cela crée une réponse factuellement trompeuse.

Challenge :
Une fenêtre fixe d'un an est raisonnable pour une UI légère, mais elle transforme une limite d'optimisation interne en limite fonctionnelle silencieuse.

PROPOSÉ :
- soit augmenter/repenser la stratégie de recherche ;
- soit annoncer explicitement la limite de recherche ;
- préférable : rechercher jusqu'à obtenir le nombre demandé, avec une borne de sécurité bien définie et un message d'absence réellement justifié.

À VALIDER :
- horizon fonctionnel maximal acceptable et comportement lorsque le nombre demandé est irréalisable dans cet horizon.

### F03 — Le modèle de relations contient une propriété éditoriale qui n'est pas la source de vérité du moteur de relations

**MEDIUM — OBSERVÉ / DEDUIT**

Preuves :
- Tool contient `relatedToolIds` ;
- le validator vérifie que les IDs référencés existent et ne sont pas auto-référencés ;
- les 42 outils publiés ont actuellement `relatedToolIds: []` via la construction canonique ;
- src/lib/tools/relations.ts ignore `relatedToolIds` et calcule dynamiquement les relations à partir des noms/tags/aliases/catégorie ;
- src/components/tools/RelatedTools.tsx utilise ce moteur dynamique.

Impact :
- deux modèles existent simultanément : relation éditoriale déclarée et relation algorithmique ;
- la validation d'un champ qui n'est pas utilisé donne une impression de contrôle sans effet runtime ;
- une future modification d'un `relatedToolIds` peut passer les validations tout en n'ayant aucun effet utilisateur.

Challenge :
Le moteur algorithmique actuel est plus scalable que de maintenir manuellement 42 listes de voisins, mais le champ mort ajoute une fausse source d'autorité.

PROPOSÉ :
- choisir explicitement entre relations purement calculées, relations éditoriales, ou modèle hybride ;
- si calcul automatique retenu, supprimer à terme le champ non utilisé ou le renommer comme override/seed ;
- si relations éditoriales nécessaires, faire réellement consommer les IDs.

À VALIDER :
- modèle de gouvernance des relations avant toute modification de schéma.

### F04 — Les relations sont calculées à partir de termes français même quand l'utilisateur navigue en anglais

**MEDIUM — OBSERVÉ**

Preuve :
- src/lib/tools/relations.ts::getTerms() utilise systématiquement `getToolContent(tool, "fr")` ;
- il complète avec tags/aliases, actuellement majoritairement français ;
- RelatedTools affiche ensuite le nom/description dans la locale active.

Impact :
- les relations cross-category dépendent de la sémantique française même sur une page anglaise ;
- le résultat peut rester acceptable grâce au bonus de catégorie, mais il ne s'agit pas d'un moteur de relation réellement localisé.

Challenge :
Le choix réduit le coût de calcul et évite de recalculer par locale, mais il contredit progressivement le principe de découverte bilingue.

PROPOSÉ :
- calculer les termes dans la locale active ;
- ou produire un index relationnel normalisé multilingue si le catalogue grossit fortement.

À VALIDER :
- stratégie relationnelle multilingue et seuil de complexité justifiant un index.

### F05 — Le partage est prévu par le contrat mais aucun outil publié ne l'exerce

**INFO / PROPOSÉ — OBSERVÉ**

Preuves :
- ToolSharingMetadata et ToolSharingMode existent ;
- ResultPanel accepte des actions ;
- les 42 outils publiés sont construits avec `sharing: { supported: false, mode: "none" }`.

Impact :
- aucune incohérence immédiate pour le MVP, car le contrat autorise explicitement l'absence de partage ;
- en revanche, des outils où le partage d'une configuration ou d'un résultat serait naturellement utile n'en bénéficient actuellement pas.

Challenge :
Il serait contre-productif de forcer un partage universel, surtout pour les outils manipulant des données sensibles. En revanche, ne jamais activer le partage signifie que le modèle prévu n'est pas encore éprouvé.

PROPOSÉ :
- sélectionner quelques outils à faible risque pour un partage de configuration déterministe ;
- exclure par défaut les contenus sensibles et les outils dont le résultat contient des données privées.

À VALIDER :
- politique de partage par type d'outil avant toute activation.

## 7. Faiblesses et choix sous-optimaux

### 7.1 Validation des tests par métadonnée

OBSERVÉ :
`quality.tests: "required"` est automatiquement dérivé du lifecycle publié dans `tools.ts`. Le validator vérifie donc que la valeur est `required`, mais ne vérifie pas à lui seul qu'un fichier de test ou un scénario correspondant existe.

CONTEXTE :
L'état actuel compense cette faiblesse : les 42 outils publiés possèdent bien un test unitaire dédié.

CHALLENGE :
La qualité réelle ne devrait pas dépendre d'une métadonnée auto-affirmée.

PROPOSÉ :
- conserver le champ comme déclaration de politique ;
- ajouter une vérification machine indépendante de l'existence/association des tests, idéalement au niveau du Tool Factory/CI.

### 7.2 Le catalogue est extrêmement homogène sur les capacités

OBSERVÉ :
42/42 outils sont local/offline/anonymous sans partage.

CHALLENGE :
C'est excellent pour la confidentialité et la simplicité du MVP, mais cela masque les cas réels qui mettront à l'épreuve les axes external/server/hybrid, account-data, database et sharing du contrat.

PROPOSÉ :
Ne pas introduire artificiellement des outils réseau. Utiliser de vrais besoins futurs comme cas d'intégration des capacités, avec tests de permission et de traitement avant publication.

### 7.3 Les tests unitaires ne remplacent pas les tests de parcours

OBSERVÉ :
Le socle unitaire est très bon, mais plusieurs bugs relevés ici sont dans le wiring UI : parsing localisé et comportement de recherche Cron.

CHALLENGE :
Une suite de fonctions pures ne suffit pas pour garantir que l'entrée réellement acceptée par le navigateur et l'UI correspond au contrat utilisateur.

PROPOSÉ :
Conserver l'unitaire comme première ligne et ajouter des tests navigateur ciblés sur :
- décimales FR/EN ;
- erreurs et bornes ;
- reset ;
- copy ;
- résultats des cas limites temporels.

## 8. Challenges à la conception actuelle

### Registre et modules

**À PRÉSERVER — OBSERVÉ / DEDUIT**

Le registre central + modules indépendants est un bon compromis actuel : il garde le routeur générique, évite un énorme switch UI et permet de charger runtime/éditorial séparément.

Alternative crédible :
un registre généré automatiquement à partir de conventions de fichiers réduirait encore le risque de divergence manuel, mais introduirait une couche de génération et de conventions implicites. À 42 outils, le bénéfice n'est pas encore démontré.

### Calculs purs dans src/lib

**À PRÉSERVER**

Les fonctions de calcul sont isolées et testables. Une refonte vers un moteur générique unique serait probablement une mauvaise simplification : les domaines ont des règles différentes.

### Actions communes

**À AMÉLIORER**

ClearButton, CopyButton et CalculatorActions sont de bonnes primitives. En revanche, le produit n'a pas encore une politique explicite disant quelles actions sont obligatoires par classe d'outil.

**PROPOSÉ :** définir une matrice de capacités UX par classe :
- calcul simple : reset + éventuellement copy ;
- résultat textuel : copy ;
- génération : regenerate/reset + copy/download selon sortie ;
- fichier : clear + download ;
- partage : uniquement si le modèle de données est sûr.

### From scratch

**PROPOSÉ — si Loculary était construit aujourd'hui :**

Je conserverais :
1. calculs métier séparés de l'UI ;
2. tests unitaires dédiés ;
3. registre dynamique runtime/éditorial ;
4. primitives communes de copie/réinitialisation ;
5. processing local par défaut ;
6. capacités explicites.

Je changerais :
1. une règle numérique commune dès le premier outil pour éliminer `Number()` vs `parseLocalizedNumber()` ;
2. un contrat de recherche Cron sans horizon fonctionnel silencieux ;
3. un seul modèle de relations, au lieu de conserver une propriété `relatedToolIds` non consommée ;
4. une matrice de QA par type d'outil pour rendre les actions attendues explicites.
