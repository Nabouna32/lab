## 4. Architecture actuellement observée

### OBSERVÉ

Le système de tools est aujourd’hui essentiellement Git-backed :

- src/lib/tools/tools.ts contient les définitions de catalogue.
- src/lib/tools/catalog.ts fournit une petite frontière d’accès au catalogue.
- src/lib/tools/registry.ts associe chaque ToolId à deux loaders explicites : runtime et editorial.
- src/lib/tools/routes.ts contient les slugs publics localisés.
- src/lib/tools/seo.ts contient les métadonnées SEO.
- src/lib/i18n/tool-messages.ts contient les messages d’interface de tous les tools.
- Les composants d’exécution et d’éditorial sont majoritairement colocalisés par tool sous src/components/tools/<tool>/.

Le routeur public est générique : une seule page dynamique résout locale, catégorie et slug, puis récupère l’entrée du registre.

### ÉLÉMENT À PRÉSERVER

Le registre central explicite n’est pas, en lui-même, un mauvais design.

Les loaders utilisent des imports statiques explicites. C’est compatible avec les contraintes de Next.js sur les imports dynamiques et permet de garder un mapping déterministe entre un ToolId et son code exécutable.

DÉDUIT / CHALLENGE : remplacer ce registre par un import construit à partir d’un nom de module venant du catalogue serait une régression de robustesse. Le catalogue peut décider du metadata produit ; il ne doit pas fabriquer dynamiquement des chemins de modules exécutables.

## F01 — Surface de changement d’un tool trop fragmentée

Sévérité : HIGH

Statut : TOUJOURS PRÉSENT sur le commit audité

### OBSERVÉ

L’identité d’un tool est répartie entre plusieurs sources :

- union ToolId dans types.ts ;
- définition principale dans tools.ts ;
- descriptions de traitement local dans une map séparée du même fichier ;
- SEO dans seo.ts ;
- routes dans routes.ts ;
- runtime/editorial dans registry.ts ;
- messages d’interface dans tool-messages.ts.

Le contrat de données final est ensuite assemblé par tools.ts à partir de plusieurs morceaux.

### MESURÉ

L’ajout de xml-formatter-validator entre les commits 72c894d8 et 99896685 a représenté 7 commits et a modifié 6 fichiers centraux pour le câblage catalogue/routes/SEO/registry/types/messages :

- src/lib/i18n/tool-messages.ts
- src/lib/tools/registry.ts
- src/lib/tools/routes.ts
- src/lib/tools/seo.ts
- src/lib/tools/tools.ts
- src/lib/tools/types.ts

Le composant du tool existe par ailleurs dans son propre dossier.

### IMPACT

Le risque principal n’est pas la taille actuelle de 42 tools ; elle reste gérable.

Le problème est la croissance du coût cognitif et du risque d’oubli : ajouter un tool nécessite de connaître plusieurs fichiers centraux et plusieurs conventions implicites.

Le code contient des protections, mais elles ne suppriment pas la surface de changement.

### CHALLENGE

Si Loculary était construit aujourd’hui, nous ne supprimerions pas le registre exécutable, mais nous réduirions les sources de vérité parallèles.

Une meilleure séparation serait :

1. un descripteur canonique du tool pour son identité et ses metadata produit ;
2. un registre d’exécution explicite séparé, uniquement pour les imports de code ;
3. des messages et contenus suffisamment proches du domaine tool pour limiter les conflits ;
4. des dérivations automatiques pour les données qui peuvent être calculées depuis le descripteur.

Cela conserve le meilleur point de l’architecture actuelle — le runtime reste explicite — tout en réduisant le travail de synchronisation.

### PROPOSÉ

Faire évoluer progressivement le modèle vers un descripteur canonique contenant notamment slug/SEO/processing metadata, puis dériver les index nécessaires.

Ne pas transformer cette proposition en migration immédiate vers Supabase.

### À VALIDER

- Quelles metadata doivent être réellement éditables indépendamment du code ?
- Le catalogue Git reste-t-il la source des metadata publiques tant que l’administration éditoriale n’est pas branchée ?
- Les traductions tool-specific doivent-elles être colocalisées par tool ou rester centralisées ?

## F02 — La convention de routes localisées n’est pas exhaustivement garantie

Sévérité : HIGH

Statut : OBSERVÉ sur le commit audité

### OBSERVÉ

src/lib/tools/routes.ts utilise une Record<string, Record<Locale, string>> et fournit un fallback vers toolId.

Contrairement à seo.ts, la table des slugs n’est pas typée comme exhaustive sur ToolId.

### MESURÉ

Sur les 42 tools publiés, 7 n’ont pas d’entrée explicite dans la table des slugs :

- percentage
- discount
- vat
- age
- duration
- yaml-formatter-validator
- text-diff-checker

Pour ces IDs, le slug français retombe sur l’identifiant interne anglais/neutre au lieu d’avoir un slug français explicite.

### IMPACT

Cela contredit directement la convention documentée dans docs/I18N.md selon laquelle les URLs publiques des tools sont pleinement localisées en français.

Le fallback rend l’omission silencieuse : le build n’échoue pas nécessairement et le test actuel ne vérifie pas l’exhaustivité de toute la table.

### CHALLENGE

Le fallback est utile pour des APIs génériques, mais il est mauvais pour une donnée qui constitue une convention publique.

Pour les données de routage canonique, l’absence d’une valeur doit être détectée comme une erreur de catalogue plutôt que transformée silencieusement en URL valide.

### PROPOSÉ

Rendre les slugs localisés exhaustifs et validés par le contrat du catalogue, ou centraliser ces slugs dans le descripteur canonique du tool.

Ajouter une vérification qui échoue si un tool publié ne possède pas explicitement ses slugs pour chaque locale supportée.

### À VALIDER

Aucune décision produit nouvelle n’est nécessaire pour constater le problème ; le choix précis entre centralisation et validation indépendante reste une décision d’implémentation.

## F03 — tool-messages.ts est devenu un monolithe de domaine

Sévérité : MEDIUM

Statut : OBSERVÉ

### MESURÉ

src/lib/i18n/tool-messages.ts contient 64 273 caractères et 755 lignes.

Il contient les messages spécifiques aux 42 tools publiés, avec une interface TypeScript centrale et deux grands dictionnaires de locale.

### IMPACT

Le système de composants est pourtant organisé par tool, mais les messages UI ne suivent pas ce découpage.

Conséquences :

- forte zone de conflit Git ;
- ownership moins clair ;
- onboarding plus difficile ;
- chaque ajout de tool modifie un fichier central volumineux ;
- difficulté à supprimer proprement un tool sans toucher plusieurs zones globales.

### CHALLENGE

La centralisation reste intéressante pour les messages réellement partagés.

Elle est moins convaincante pour des centaines de chaînes propres à un seul tool.

Next.js traite les Server Components et le code client avec des frontières de bundle distinctes ; les outils sont déjà conçus pour être chargés séparément. Une organisation des messages par domaine permettrait également de mieux aligner ownership et chargement, sous réserve d’une mesure réelle des bundles avant d’en faire un objectif de performance.

### PROPOSÉ

Conserver les messages globaux dans l’i18n partagé, mais envisager des modules de messages par tool ou par groupe cohérent, avec une agrégation typée minimale.

Ne pas introduire une bibliothèque i18n supplémentaire uniquement pour résoudre ce problème.

### À VALIDER

Le choix de colocalisation des messages tool-specific doit être validé avant une migration globale.

## F04 — Plusieurs tests d’architecture vérifient la forme du source plutôt que le comportement

Sévérité : MEDIUM

Statut : OBSERVÉ

### OBSERVÉ

src/lib/tools/registry.test.mjs lit registry.ts et tools.ts comme du texte et extrait les IDs avec des expressions régulières et une analyse ligne par ligne.

src/lib/tools/page-metadata.test.mjs vérifie également plusieurs garanties par regex sur le contenu des fichiers.

### IMPACT

Ces tests sont sensibles à la forme du code.

Un refactor purement structurel peut provoquer des faux positifs/faux négatifs :

- changement de formatage ;
- déplacement d’une expression ;
- changement d’un helper ;
- renommage interne sans changement de comportement.

Inversement, la présence d’un chemin d’import sous forme de texte ne prouve pas que le module correspondant existe réellement ou se charge correctement.

### CHALLENGE

Ces tests ont une utilité comme garde-fous structurels, surtout lorsqu’un module ne peut pas être importé facilement hors du runtime Next.js.

Mais ils ne devraient pas être la seule preuve d’un contrat architectural.

### PROPOSÉ

Compléter ces tests par une validation exécutable indépendante :

- vérification réelle de l’existence des modules référencés ;
- validation exhaustive des IDs depuis le contrat canonique ;
- vérification de génération des routes ;
- idéalement une étape CI/build qui exerce le chemin réel de compilation.

Conserver les tests source-text uniquement lorsqu’ils vérifient volontairement une convention statique impossible à tester autrement.

## F05 — Le contrat de capabilities est plus avancé que son enforcement runtime

Sévérité : MEDIUM

Statut : OBSERVÉ / RISQUE D’ÉVOLUTION

### OBSERVÉ

Tool déclare des capabilities :

- local-processing ;
- file-input ;
- clipboard ;
- camera ;
- microphone ;
- geolocation ;
- network ;
- account-data ;
- database.

ToolRuntimeProvider fournit actuellement un enforcement concret pour clipboard.

Le tool image-compressor, par exemple, déclare file-input, mais son composant utilise directement l’API HTML input type=file ; la capability est déclarative plutôt qu’imposée par un adapter runtime.

Aucune utilisation actuelle de geolocation, microphone ou camera n’a été observée.

### CHALLENGE

Ce n’est pas une faille de sécurité actuelle : les tools publiés sont tous locaux, anonymes et le runtime ne donne pas aujourd’hui accès à des capabilities distantes sensibles.

En revanche, le contrat peut donner une impression d’enforcement plus complète qu’elle ne l’est réellement.

Le risque augmente lorsque des tools externes, account-backed ou device-backed apparaîtront.

### PROPOSÉ

Faire évoluer les capabilities par adapters explicites au moment où chaque famille devient nécessaire :

- clipboard ;
- file input ;
- network ;
- account data ;
- device APIs ;
- database.

Un tool ne devrait pas seulement déclarer une capability ; les accès sensibles devraient progressivement passer par le runtime correspondant.

Ne pas construire aujourd’hui des adapters pour des capabilities qui n’ont aucun consommateur.

### À VALIDER

Le niveau d’enforcement requis avant l’introduction de chaque nouvelle famille de capability.

## F06 — Deux catalogues existent conceptuellement, mais un seul est réellement utilisé

Sévérité : MEDIUM

Statut : OBSERVÉ / À VALIDER

### OBSERVÉ

Supabase possède une fondation tool_catalog et une migration de seed.

Le seed contient 12 tools.

La recherche structurée du dépôt ne trouve aucune référence tool_catalog sous src/.

Le runtime public passe par src/lib/tools/catalog.ts, qui retourne explicitement le catalogue Git-backed.

catalog.ts indique lui-même que cette frontière permet un futur remplacement par une base.

### DOCUMENTATION

docs/DATABASE.md décrit néanmoins une frontière de catalogue où la base porte les metadata éditables et expose les lectures publiques, tout en précisant que le comportement exécutable reste dans Git.

### IMPACT

Il existe donc aujourd’hui :

- un catalogue Git réel de 42 tools ;
- une fondation Supabase de 12 tools ;
- une documentation décrivant la cible de séparation.

Ce n’est pas nécessairement mauvais pendant une phase de transition, mais cela crée un risque de dérive si la frontière reste implicite.

### CHALLENGE

Le mauvais choix serait de brancher immédiatement le runtime sur Supabase simplement parce que la table existe.

Le bon découpage reste :

- Git pour le code exécutable ;
- une source de metadata unique lorsque l’édition de ces metadata devient réellement un besoin ;
- un bridge stable ToolId vers module exécutable.

### PROPOSÉ

Clarifier explicitement le statut actuel :

1. Git-backed catalog = source runtime actuelle ;
2. Supabase catalog = fondation non branchée ;
3. aucune synchronisation bidirectionnelle tant que le modèle de responsabilité n’est pas validé.

Puis, lorsque l’administration éditoriale le justifiera, décider précisément quelles colonnes quittent Git et quelles données restent versionnées avec le code.

### À VALIDER

La date/condition à partir de laquelle tool_catalog devient une source runtime effective.

## 6. Éléments à préserver

### OBSERVÉ / CHALLENGÉ

1. Catalogue derrière catalog.ts : bonne frontière d’accès ; elle évite de répandre la provenance du catalogue dans tout le code.
2. Registre runtime explicite : à préserver. Les imports explicites sont plus sûrs et compatibles avec le modèle de bundling Next.js que des imports construits dynamiquement.
3. Séparation runtime/editorial : bonne idée ; elle permet de ne pas forcer les tools à partager une UI unique.
4. Route dynamique unique : bonne réduction du nombre de pages structurelles.
5. Contrat Tool centralisé : utile pour garantir un minimum commun sans imposer une implémentation identique à tous les tools.
6. Validation du catalogue : les invariants existants sur IDs, tags, aliases, processing, offline, sharing et relations sont utiles.
7. Architecture browser-first : cohérente avec la majorité actuelle des tools.
8. Pas de sur-abstraction mobile : aucun coût architectural majeur observé pour un client Android hypothétique.
9. Absence de DB-driven execution : à préserver tant que le code exécutable reste versionné dans Git.

## 7. Faiblesses ou sous-optimalités secondaires

### MESURÉ / DÉDUIT

- getToolByRoute réalise actuellement une recherche linéaire dans le registre. À 42 tools, le coût est négligeable. Une indexation par locale/category/slug deviendra pertinente seulement si le catalogue grossit fortement ou devient DB-backed.
- Plusieurs champs du contrat Tool ont actuellement la même valeur pour les 42 tools publiés : version 1, local, offline, anonymous, sharing disabled, relatedToolIds vide, contributor internal et quality standard. Cela montre que le contrat prépare des cas futurs, mais une partie de cette richesse n’est pas encore exercée par le produit.
- Il ne faut pas interpréter cette homogénéité comme une raison suffisante pour supprimer le contrat. Elle indique surtout quelles parties sont réellement actives aujourd’hui et lesquelles sont des extensions préparatoires.

## 8. Challenge from-scratch

### Si Loculary était construit aujourd’hui, qu’est-ce que nous changerions ?

Nous conserverions l’architecture générale, mais avec trois simplifications structurantes.

### 1. Un seul descripteur canonique pour les metadata tool

Nous éviterions de répartir l’identité publique d’un tool entre tools.ts, seo.ts, routes.ts et plusieurs maps auxiliaires.

Le descripteur canonique porterait les metadata nécessaires à la découverte et au contrat public.

Le registre exécutable resterait séparé et explicite.

### 2. Ownership par domaine

Le runtime d’un tool, son contenu spécifique et ses messages propres devraient être aussi proches que raisonnablement possible.

Les éléments réellement globaux resteraient centralisés.

Cela réduirait les conflits et rendrait l’ajout/suppression d’un tool plus local.

### 3. Deux sources de vérité clairement séparées

- Git : code, modules exécutables, contrats techniques, tests.
- Base éditoriale : seulement les metadata effectivement destinées à être administrées hors code.

Nous ne ferions pas une migration DB parce qu’une table existe.

### Ce que nous ne changerions pas

Nous ne remplacerions pas le registre explicite par un loader générique piloté par des chaînes issues du catalogue.

Nous ne créerions pas une abstraction universelle de UI qui force les 42 tools à utiliser le même rendu.

Nous ne déplacerions pas prématurément toute la logique dans Supabase.

## 9. Plan de remédiation proposé

### P0 — corriger les invariants silencieux

1. Rendre les slugs localisés exhaustifs.
2. Faire échouer le catalogue lorsqu’un tool publié manque d’un slug.
3. Ajouter un test couvrant les 42 tools et les deux locales.

### P1 — réduire la fragmentation du metadata contract

1. Identifier le descripteur canonique.
2. Déplacer progressivement SEO, slugs et processing metadata qui sont réellement propres au tool dans ce descripteur.
3. Conserver le registre d’exécution explicite.
4. Supprimer les sources parallèles uniquement lorsque leur remplacement est vérifié.

### P1 — renforcer la validation

1. Remplacer les tests source-text par des validations exécutables lorsque possible.
2. Vérifier réellement les modules runtime/editorial.
3. Vérifier les routes générées.
4. Ajouter une validation CI dédiée aux invariants du catalogue.

### P2 — améliorer ownership i18n

1. Mesurer le coût réel du fichier tool-messages.ts dans les bundles.
2. Si le bénéfice est confirmé, découper les messages par tool/domaine.
3. Conserver un agrégateur typé minimal.

### P2 — clarifier DB/Git

Documenter l’état actuel sans changer la vision :

- catalogue Git actif ;
- catalogue Supabase fondation ;
- pas de synchronisation ;
- conditions de passage à une source éditoriale DB.

### P3 — onboarding

Ajouter un README racine court et maintenable.

## 10. Tests et vérifications recommandés

Pour une future implémentation :

### Catalogue

- tous les ToolId ont une définition ;
- tous les tools publiés ont runtime + editorial ;
- tous les tools publiés ont SEO FR/EN ;
- tous les tools publiés ont slug FR/EN explicite ;
- aucun slug public dupliqué ;
- aucun module référencé par le registry n’est absent.

### Architecture

- la source canonique du metadata est unique ;
- aucune ancienne map parallèle ne subsiste après migration ;
- catalog.ts reste l’unique frontière de lecture du catalogue ;
- le registry ne devient pas DB-driven.

### i18n

- tous les messages requis sont présents pour chaque locale ;
- suppression/ajout d’un tool ne nécessite pas d’éditer plusieurs maps non liées si le nouveau contrat vise à les réduire.

### CI

Exécuter le pipeline prévu par AGENTS.md sur la PR :

- npm ci ;
- npm audit --audit-level=high ;
- lint ;
- typecheck ;
- test ;
- build.

L’audit n’a pas exécuté ces étapes avec succès dans cet environnement et ne prétend donc pas qu’elles passent.

## 13. Conclusion

### VERDICT

L’architecture actuelle est solide pour le stade du produit, mais elle commence à montrer une dette de coordination plutôt qu’une dette algorithmique.

Le point le plus important n’est pas une mauvaise abstraction isolée : c’est la multiplication des endroits où l’identité d’un tool doit être maintenue.

Le registre explicite, le routeur générique et la frontière catalog.ts sont de bonnes bases et doivent être conservés.

Les priorités réelles sont :

1. corriger les slugs localisés silencieusement incomplets ;
2. réduire les sources parallèles de metadata ;
3. rendre les tests architecturaux moins dépendants du texte source ;
4. clarifier la frontière Git/DB avant qu’un second catalogue ne devienne une source de dérive ;
5. préparer l’enforcement des capabilities uniquement au rythme des besoins réels.

Aucune recommandation de cet audit ne constitue une décision produit ou architecture.
