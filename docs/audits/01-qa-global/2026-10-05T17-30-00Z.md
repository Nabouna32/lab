## 6. Findings

### F01 — La porte CI ne protège pas réellement la qualité avant merge
HIGH — OBSERVÉ / MESURÉ

Preuves :
- .github/workflows/ci.yml conditionne le job audit avec github.event_name != 'pull_request'.
- le ruleset Protect main exige pourtant Dependency audit ;
- le commit audité a un Dependency audit en échec ;
- le même commit possède un déploiement production READY.

Impact : une vérification déclarée obligatoire n'est pas exécutée dans le contexte PR. Le contrôle arrive après intégration et peut rendre main rouge après coup.

DEDUIT : le problème vient du décalage entre workflow et ruleset, pas du principe d'un ruleset.

Challenge : le choix « audit uniquement après merge pour garder les PR rapides » est simple mais incohérent avec un check déclaré required.

PROPOSÉ : soit exécuter un audit HIGH/CRITICAL déterministe en PR puis garder un audit complet périodique sur main, soit assumer qu'il est post-merge et retirer son caractère de check obligatoire.

À VALIDER : seuil de vulnérabilité réellement bloquant avant merge.

### F02 — Le pipeline de dépendances est rouge
HIGH — OBSERVÉ / MESURÉ

npm audit --audit-level=high signale 5 HIGH. Le lockfile contient notamment braces 3.0.3. Une alerte GitHub actuelle classe les versions <=3.0.3 HIGH pour un problème de stack exhaustion sur des patterns imbriqués. Aucun correctif publié n’est indiqué pour cette branche.

Le contexte est important : cela provient de la chaîne de développement/linting ; npm audit ne prouve pas une exploitabilité distante du runtime public.

Impact : CI sécurité rouge et dette supply-chain. npm audit fix --force ne doit pas être appliqué aveuglément car il peut imposer des changements cassants.

PROPOSÉ : traiter chaque chaîne vulnérable séparément, déterminer runtime/dev-only, version compatible et éventuels overrides avant modification.

À VALIDER : politique pour les vulnérabilités transitives sans correctif compatible.

### F03 — Les parcours authentifiés/admin ne sont pas réellement testés de bout en bout
HIGH — OBSERVÉ

e2e/account.spec.mjs couvre les écrans anonymes, pages d’auth, validation HTML du reset, redirections protégées et rejet d’un callback externe.

Aucun scénario CI ne réalise réellement : inscription confirmée, connexion réussie, session authentifiée, profil, changement de mot de passe/e-mail, suppression réelle, accès admin autorisé, gestion d’utilisateur, rôles, suspension/réactivation, révocation de sessions ou lecture authentifiée du journal.

Impact : une régression Auth/RLS/Server Action peut passer CI sur les parcours les plus sensibles.

PROPOSÉ : un petit parcours d’acceptation authentifié avec compte de test isolé et données contrôlées.

À VALIDER : stratégie de compte de test, secrets et nettoyage.

### F04 — La couverture navigateur est en retard sur le catalogue
MEDIUM — OBSERVÉ / MESURÉ

42 outils publiés, 26 specs Playwright outil dédiées, mais seulement 15/26 exécutées par le workflow Browser E2E principal. 11 specs restent hors du chemin CI principal.

Le 57/57 actuel est donc un résultat valide mais ne signifie pas « tous les outils publiés sont validés par navigateur ».

PROPOSÉ : matrice ou groupes de specs déterministes, avec smoke rapide obligatoire et suite outil complète. Ajouter une vérification empêchant qu'une nouvelle spec outil reste silencieusement hors CI.

### F05 — Recherche et génération statique ne sont pas démontrées scalables à un très gros catalogue
MEDIUM — DEDUIT / OBSERVÉ

src/lib/tools/search-client.ts charge le catalogue complet côté client. searchTools() parcourt le catalogue et peut calculer une distance de Levenshtein. La route outil génère statiquement une entrée par outil et par locale via generateStaticParams().

À 42 outils, ce choix est raisonnable et le build actuel est rapide. À plusieurs centaines/milliers d’outils, la taille de l’index client et le nombre de pages pré-rendues augmentent linéairement.

Challenge from-scratch : pour une cible de plusieurs milliers d’outils, je ne conserverais pas implicitement tout le catalogue comme index de recherche client et je ne pré-rendrais pas nécessairement chaque outil dans chaque locale.

PROPOSÉ : conserver l’architecture actuelle tant que le volume reste modeste ; définir un seuil de bascule vers index compact client, recherche serveur/edge et/ou génération hybride.

À VALIDER : seuil de volume déclenchant cette évolution.

### F06 — Pas de stratégie App Router explicite pour loading/error
MEDIUM — OBSERVÉ / DEDUIT

Aucun error.tsx, loading.tsx ou ErrorBoundary dédié n’a été trouvé dans l’arbre App Router audité.

Les chemins nominaux passent, mais la récupération UX d’une erreur serveur/client ou d’un chargement lent n’est pas matérialisée globalement.

PROPOSÉ : ajouter des boundaries ciblées aux zones réellement dynamiques et tester leurs failure states plutôt qu’un écran générique partout.

### F07 — Protection contre les mots de passe compromis désactivée
MEDIUM — OBSERVÉ

Le Supabase Security Advisor du projet Loculary retourne auth_leaked_password_protection en WARN : protection désactivée.

Impact : possibilité de choisir un mot de passe déjà compromis, ce qui augmente le risque de credential stuffing.

PROPOSÉ : évaluer l’activation si le plan et les contraintes produit le permettent.

À VALIDER : activation effective et éventuelles contraintes de plan/coût.

### F08 — Catalogue Git et catalogue DB de tailles différentes, divergence actuellement intentionnelle
INFO — OBSERVÉ / DEDUIT

Le runtime utilise un catalogue Git-backed de 42 outils. Supabase contient actuellement 12 lignes dans public.tool_catalog.

docs/DATABASE.md et docs/STATUS.md indiquent que le catalogue DB est une fondation éditoriale initiale et que les lectures publiques n’ont pas encore basculé.

Conclusion : pas de défaut immédiat. La divergence est documentée.

Challenge : le risque futur est qu’un écran mélange 42 outils Git et 12 outils DB.

PROPOSÉ : préserver la frontière actuelle jusqu’à migration réelle, puis imposer une source de lecture unique par domaine ou des invariants de synchronisation.

## 13. Conclusion

CONCLUSION GLOBALE : MEDIUM/HIGH.

Loculary est fonctionnel sur le chemin nominal et la base QA est solide pour la taille actuelle : build, TypeScript, tests unitaires, 57 tests navigateur et validation production passent sur le commit audité.

Le problème principal n’est donc pas « le produit ne fonctionne pas ». C’est que la stratégie de qualité ne reflète plus complètement la maturité réelle du produit :

- le check sécurité obligatoire n’est pas réellement pré-merge ;
- la production peut être déployée sur un commit dont l’audit dépendances est rouge ;
- 11 specs outil ne participent pas au Browser E2E principal ;
- les parcours authentifiés/admin sensibles ne sont pas validés de bout en bout ;
- search/build sont adaptés à 42 outils mais pas démontrés scalables à plusieurs milliers ;
- un warning Supabase de sécurité reste ouvert.

Le point positif majeur est que les briques nécessaires existent déjà. L’objectif recommandé est donc de rendre la couverture et les portes de qualité cohérentes avec le produit réel, pas de reconstruire la QA.
