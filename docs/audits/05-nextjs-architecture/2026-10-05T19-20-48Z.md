## 6. A-01 — ToolRenderer fait entrer le registry et le catalogue dans le graphe client
STATUT : TOUJOURS PRÉSENT. Sévérité : MEDIUM.
OBSERVÉ — src/components/tools/ToolRenderer.tsx est un Client Component et importe src/lib/tools/registry.ts.
OBSERVÉ — registry.ts importe getPublishedTools(), construit le registry depuis le catalogue et déclare les dynamic imports des outils.
OBSERVÉ — La route serveur connaît déjà la même entrée du registry pour charger l'éditorial et le runtime.
MESURÉ — Le catalogue et SEO actuellement atteignables via cette chaîne représentent 53 185 octets de source brute.
DÉDUIT — La séparation des implémentations runtime reste bonne grâce aux dynamic imports, mais la frontière Client n'isole pas autant le catalogue que le runtime : le navigateur doit également charger le module registry et ses dépendances nécessaires à sa résolution.
DÉDUIT — À 42 outils, le coût est probablement acceptable. À plusieurs centaines, cette architecture crée un coût client structurel qui croît avec le catalogue.
CHALLENGE — Si le serveur a déjà résolu l'outil, le navigateur n'a pas besoin de refaire cette résolution.
PROPOSITION — Mesurer d'abord avec le Bundle Analyzer Next.js 16. Si le graphe confirme le coût, faire résoudre le runtime côté serveur et ne conserver côté client que le composant interactif réellement nécessaire.
À VALIDER — Toute refactorisation de cette frontière.
Reproduction proposée : npx next experimental-analyze --output, puis inspecter les import chains ToolRenderer → registry → catalog → tools/seo.

## 7. A-02 — Absence de loading/error/not-found
STATUT : TOUJOURS PRÉSENT. Sévérité : MEDIUM.
OBSERVÉ — Aucun loading.tsx, error.tsx, not-found.tsx ou global-error.tsx dans l'App Router.
OBSERVÉ — Plusieurs routes appellent notFound(), mais aucun composant Loculary ne personnalise le résultat.
IMPACT DÉDUIT — Les transitions lentes et erreurs runtime utilisent les fallbacks génériques de Next.js ; il n'existe pas de retry contextualisé ni de 404 explicitement localisée.
CHALLENGE — Pour une toolbox dont certains runtimes sont plus lourds que d'autres, loading UI et error boundary apportent une vraie frontière de résilience à faible coût.
PROPOSITION — Étudier src/app/[locale]/loading.tsx, error.tsx et not-found.tsx, avec éventuellement un boundary plus proche du runtime outil.
PROPOSITION — Ne pas activer global-not-found uniquement pour résoudre ce sujet sans besoin démontré : la solution est expérimentale et le root layout dynamique ajoute une contrainte particulière.
À VALIDER — emplacement, UX et journalisation des erreurs.

## 8. A-03 — generateStaticParams : excellent aujourd'hui, plafond structurel demain
STATUT : TOUJOURS PRÉSENT. Sévérité : MEDIUM.
OBSERVÉ — La route outil utilise generateStaticParams() sur le registry.
MESURÉ — 42 outils × 2 locales = 84 variantes outil/locale actuellement concernées.
DÉDUIT — Le coût de génération augmente approximativement avec locales × outils publiés, auquel s'ajoute le rendu et le chargement de l'éditorial.
CHALLENGE — Le modèle est excellent pour un catalogue Git-backed de taille modérée. Il devient moins adapté lorsque le catalogue éditorial migrera vers Supabase et pourra atteindre plusieurs centaines ou milliers d'entrées.
PROPOSITION — Ne rien changer maintenant. Lors de la migration DB, conserver le registry exécutable dans Git mais envisager un sous-ensemble pré-généré et des routes runtime/cache pour le reste.
PROPOSITION — Réévaluer Cache Components/PPR à ce moment-là plutôt que l'activer prématurément.
À VALIDER — stratégie future de rendu du catalogue DB.

## 9. A-04 — Recherche client : bonne aujourd'hui, plafond à surveiller
STATUT : TOUJOURS PRÉSENT. Sévérité : LOW/MEDIUM.
OBSERVÉ — ToolSearch est client et charge dynamiquement search-client.ts, qui importe le catalogue complet et l'algorithme search.ts.
POINT POSITIF — Le code de recherche n'est chargé qu'à la demande et évite un round-trip serveur.
CHALLENGE — À plusieurs centaines ou milliers d'entrées, envoyer et scorer tout le catalogue côté navigateur devient moins intéressant en taille, CPU et maintenance d'index.
PROPOSITION — Conserver ce modèle tant que les mesures restent bonnes. Lors de la migration DB ou d'une croissance importante, comparer index client compact et recherche serveur/indexée.
À VALIDER — aucune action immédiate.

## 11. Data fetching, caching et Proxy
OBSERVÉ — Les pages publiques sont largement déterministes et Git-backed ; aucune complexité de cache n'est actuellement nécessaire pour leur fonctionnement.
OBSERVÉ — next.config.ts n'active pas cacheComponents.
CHALLENGE — L'introduction de Cache Components maintenant augmenterait la surface conceptuelle sans résoudre un problème démontré.
PROPOSITION — Réévaluer Cache Components lors de la migration du catalogue éditorial vers Supabase ou lorsque des données publiques réellement dynamiques apparaîtront.
OBSERVÉ — src/proxy.ts négocie la locale, redirige les URLs sans locale et rafraîchit Supabase seulement pour compte/auth/admin.
CHALLENGE — Ce Proxy ciblé est préférable à un rafraîchissement Supabase sur toutes les pages publiques.
CONCLUSION — Proxy à préserver ; aucun défaut critique observé.

## 15. From-scratch challenge
QUESTION — Si Loculary était construit aujourd'hui, qu'est-ce que nous changerions ?
RÉPONSE — Nous conserverions App Router + root [locale] + route outil générique + registry Git + runtime isolé + Server Components par défaut.
Nous renforcerions en revanche dès le départ la séparation entre catalogue éditorial, résolution serveur de l'exécutable et runtime client.
Le principal changement serait d'éviter qu'un Client Component refasse côté navigateur une résolution du registry que le serveur vient déjà de faire.
Nous prévoirions aussi explicitement la transition 42 outils → centaines d'outils : prerender complet et index de recherche client sont de bonnes optimisations actuelles, pas des invariants éternels.
Enfin, nous ajouterions une stratégie minimale loading/error/not-found afin que l'App Router possède une vraie frontière de résilience.
