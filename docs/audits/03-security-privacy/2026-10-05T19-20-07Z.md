## 5. Architecture de confidentialité observée

### 5.1 Catalogue d'outils

**OBSERVÉ / MESURÉ**

Le catalogue publié est actuellement construit par un mapping commun qui déclare pour tous les outils :

- `processing.mode = local` ;
- aucun fournisseur externe ;
- aucun stockage Loculary ;
- `offline = true` ;
- accès anonyme ;
- aucun partage ;
- traitement directement dans le navigateur.

Le contrat de type et le validator imposent notamment la cohérence entre mode de traitement et capacités :

- local => `local-processing` ;
- un outil local ne peut pas déclarer `network` ;
- un outil local ne peut pas déclarer de fournisseur externe ;
- un outil local ne peut pas utiliser un stockage serveur/externe ;
- un outil offline ne peut pas demander le réseau.

**OBSERVÉ**

Une recherche statique GitHub ciblée sur `fetch(`, `XMLHttpRequest`, `navigator.sendBeacon`, `WebSocket` et `document.cookie` n'a pas révélé d'utilisation applicative de ces surfaces ; les résultats positifs étaient limités à la documentation pour les deux premiers termes.

**LIMITATION**

Cette recherche ne constitue pas une preuve formelle que chaque dépendance tierce ou chaque futur module restera sans réseau. La garantie actuelle repose encore principalement sur le code et le validator, pas sur une politique d'exécution capable d'empêcher techniquement tout appel réseau depuis un outil local.

### 5.2 Stockage

**OBSERVÉ**

Aucune utilisation applicative de `document.cookie`, `navigator.sendBeacon` ou `WebSocket` n'a été trouvée par la recherche ciblée. L'architecture documente localStorage/IndexedDB comme options futures, mais aucun flux de données utilisateur sensible n'est actuellement identifié comme stocké par les outils publiés.

### 5.4 RLS et privilèges

**OBSERVÉ**

Les données de profil sont protégées par RLS et liées à `auth.uid()`.

Le rôle `admin` ne reçoit pas `users.manage_roles`; cette capacité reste au `super_admin`.

**ÉLÉMENT À PRÉSERVER**

Cette séparation RLS + fonctions SQL privées + vérification de session est l'une des parties les plus solides de la base actuelle.

## 6. Findings et anomalies

### F01 — Absence de CSP HTTP globale

**HIGH — OBSERVÉ**

`next.config.ts` définit :

- `X-Content-Type-Options: nosniff` ;
- `Referrer-Policy: strict-origin-when-cross-origin` ;
- `X-Frame-Options: SAMEORIGIN` ;
- `Permissions-Policy` limitant camera/microphone/geolocation ;
- `Strict-Transport-Security`.

Mais aucune directive `Content-Security-Policy` globale n'est envoyée par cette configuration.

**Impact**

La protection contre XSS dépend donc davantage de l'échappement React, de l'absence actuelle de sinks dangereux et des composants individuels que d'une défense en profondeur navigateur.

**OBSERVÉ**

La recherche GitHub ciblée n'a pas trouvé `dangerouslySetInnerHTML` ni `innerHTML` dans le code applicatif audité.

**DÉDUIT**

L'absence de sink XSS connu réduit le risque immédiat mais ne remplace pas une CSP. Une future dépendance, un composant ou une erreur de rendu peut réintroduire une surface sans seconde ligne de défense.

**CHALLENGE**

Le choix actuel est raisonnable pour éviter de casser prématurément Next.js, mais pour un produit qui va ajouter publicité, analytics, fournisseurs externes et davantage de fonctionnalités, « pas de CSP » devient un choix difficile à défendre.

**PROPOSÉ**

Introduire progressivement une CSP réelle, idéalement après inventaire des scripts/styles/connectivités réellement nécessaires, avec une phase Report-Only avant enforcement si nécessaire. Éviter un simple `unsafe-eval`/wildcard qui donnerait une fausse impression de protection.

**À VALIDER**

Le niveau de CSP cible et la stratégie nonce/hash/domaine de confiance doivent être validés avant implémentation, car ils dépendent des futures intégrations.

- la CI reste vulnérable ;
- le gate sécurité est rouge ;
- un futur usage de cette chaîne dans un contexte exposé pourrait changer le niveau de risque ;

**PROPOSÉ**

Auditer le graphe exact dans `package-lock.json`, identifier si `braces` peut être remplacé par une version/branche corrigée compatible, un override ciblé ou une mise à jour de la chaîne Next/ESLint. Ajouter un test de compatibilité du caller avant toute résolution par override.

**À VALIDER**

Le choix entre upgrade de la chaîne Next/ESLint, override ciblé ou exception documentée si aucun correctif sûr n'est disponible.

### F03 — Le journal d'audit administratif est falsifiable par tout rôle disposant de audit.write

**HIGH — OBSERVÉ**

`public.record_admin_audit(...)` accepte directement :

- `audit_action` ;
- `audit_target_type` ;
- `audit_target_id` ;
- `audit_metadata`.

La fonction vérifie seulement que l'appelant possède `audit.write`.

Or le rôle `admin` possède actuellement `audit.write`.

Les Edge Functions d'administration utilisent ce RPC pour écrire leurs événements, mais le RPC public reste lui-même appelable par tout administrateur autorisé à écrire dans l'audit.

**Impact**

Un administrateur peut potentiellement créer un événement d'audit arbitraire avec une action, une cible et des métadonnées de son choix. Le journal peut donc contenir un événement qui ressemble à une preuve système alors qu'il a été fabriqué manuellement par un rôle opérationnel.

Cela affaiblit la valeur forensique du journal.

**DÉDUIT**

Ce n'est pas une élévation de privilège directe : l'appelant doit déjà être administrateur avec `audit.write`. C'est en revanche une faiblesse d'intégrité de la preuve de sécurité.

**CHALLENGE**

Le design actuel optimise la réutilisabilité d'un RPC unique, mais traite un journal de sécurité comme une table d'événements générique. Pour un audit trail fiable, les événements devraient être produits par des opérations métier déterminées, pas par un appelant qui choisit librement leur sémantique.

**PROPOSÉ**

Réduire l'API d'écriture :

- fonctions privées spécifiques à chaque opération sensible ;
- ou fonctions publiques dont l'action est imposée côté serveur ;
- métadonnées strictement validées par événement ;
- idéalement suppression de `audit.write` générique pour le rôle `admin`.

Le journal doit rester consultable par les rôles autorisés, mais sa génération doit être beaucoup plus contrainte.

**À VALIDER**

Le niveau d'intégrité forensique attendu pour l'audit administratif.

### F04 — La suspension n'est pas atomique avec la révocation de session et le journal d'audit

**HIGH — OBSERVÉ / DÉDUIT**

`supabase/functions/admin-user-suspension/index.ts` :

1. modifie l'état Auth avec `updateUserById(... ban_duration ...)` ;
2. tente ensuite de supprimer les sessions ;
3. tente ensuite d'écrire l'audit ;
4. retourne HTTP 500 si l'une des étapes suivantes échoue, alors que l'étape précédente a déjà réussi.

**Impact**

L'opération peut donc se terminer côté système par :

- compte suspendu mais sessions non révoquées ;
- compte suspendu mais événement d'audit absent ;
- réponse utilisateur en erreur alors que l'état métier a changé.

Supabase documente explicitement qu'un ban temporaire ne révoque pas les sessions existantes et qu'un JWT déjà émis reste valide jusqu'à son expiration. La révocation des sessions est donc une partie de la garantie de sécurité recherchée, pas seulement une optimisation. (source: Supabase User Management and Sign-out documentation)

**DÉDUIT**

Le risque dépend de la durée de vie du JWT et des surfaces accessibles avec un token déjà émis. Les contrôles RLS actuels qui vérifient une session vivante réduisent fortement le risque sur les données protégées, mais ils ne garantissent pas automatiquement la révocation de toutes les futures surfaces.

**CHALLENGE**

Une séquence « Auth → DB → audit » distribuée ne peut pas fournir une transaction unique. Retourner 500 après une modification partielle ne suffit pas à rendre l'opération fiable.

**PROPOSÉ**

Définir un protocole explicite de révocation :

- état de suspension confirmé ;
- révocation de session considérée comme exigence de sécurité ;
- stratégie de retry/compensation en cas d'échec ;
- journalisation d'un état partiel ;
- tests d'échec entre chaque étape.

Le futur protocole doit aussi décider quel état est considéré comme « succès » et quel état est considéré comme « échec récupérable ».

**À VALIDER**

La garantie attendue : révocation immédiate stricte, révocation au plus tard à l'expiration du JWT, ou modèle intermédiaire.

### F05 — Aucun MFA dédié aux comptes administrateurs

**MEDIUM — OBSERVÉ / PROPOSÉ**

Aucun parcours MFA/second facteur administrateur n'a été trouvé dans l'implémentation actuelle.

Le produit dispose pourtant de fonctions à fort impact :

- attribution/retrait de rôles ;
- suspension de comptes ;
- révocation de sessions ;
- consultation du journal d'audit.

**Impact**

La compromission du mot de passe/session d'un compte `super_admin` concentre une surface de contrôle importante dans une seule authentification.

**CHALLENGE**

Pour un MVP à très faible population administratrice, imposer immédiatement un système MFA complet peut être disproportionné. En revanche, conserver durablement une administration privilégiée sans second facteur serait difficile à justifier à mesure que le produit et sa communauté grandissent.

**PROPOSÉ**

Prévoir au minimum une exigence MFA pour `super_admin` avant une montée en charge significative ou l'ouverture de fonctionnalités communautaires/modération sensibles.

**À VALIDER**

Moment exact où le MFA devient une exigence de lancement ou de montée en puissance, et politique de récupération/contournement.

### F06 — La déclaration « local/offline » reste une garantie de convention, pas une capacité techniquement confinée

**MEDIUM — OBSERVÉ / DÉDUIT**

Le catalogue déclare tous les outils `local`, `offline`, sans réseau et sans stockage externe. Le validator interdit les métadonnées contradictoires.

Mais un composant client peut toujours appeler une API navigateur réseau sans que le type `ToolCapability` empêche techniquement cet appel.

La recherche statique actuelle n'a pas trouvé de surface réseau applicative évidente, ce qui est rassurant, mais le mécanisme ne fournit pas de sandbox d'exécution.

**Impact**

Une future contribution pourrait ajouter une requête réseau dans un outil déclaré local sans que le contrat de métadonnées soit, à lui seul, un mécanisme d'enforcement.

**CHALLENGE**

Le contrat de métadonnées est excellent pour la transparence et l'audit, mais il ne faut pas le confondre avec un contrôle de sécurité.

**PROPOSÉ**

Conserver la déclaration comme source éditoriale et ajouter progressivement des checks automatisés adaptés :

- analyse statique ciblée des imports/APIs réseau ;
- règle de lint ou test architectural interdisant les primitives réseau dans les modules locaux ;
- revue spécifique des dépendances de tool ;
- éventuellement séparation de packages/runtimes si le catalogue devient beaucoup plus extensible.

**À VALIDER**

Le niveau d'enforcement nécessaire avant d'autoriser des contributions externes au catalogue.

## 7. Éléments à préserver

**OBSERVÉ / DÉDUIT**

1. **Browser-first/local-first réel** : les outils publiés sont actuellement conçus comme locaux et aucun appel réseau applicatif évident n'a été trouvé par la recherche ciblée.
2. **Metadata validator** : la cohérence processing/capabilities/storage/offline est déjà contrôlée automatiquement.
3. **Supabase SSR + PKCE** : architecture adaptée au modèle Next.js actuel.
4. **Vérification d'identité côté serveur** : les opérations sensibles ne font pas confiance aux seuls champs de formulaire.
5. **RLS** : les profils et tables administratives sont protégés par politiques dédiées.
6. **Session vivante** : `private.has_valid_session()` apporte une protection supplémentaire contre l'utilisation d'un JWT dont la session DB a été révoquée.
7. **RBAC** : les permissions sensibles sont séparées et `users.manage_roles` reste réservé au niveau supérieur.
8. **Secret handling** : les clés secrètes sont lues depuis les variables d'environnement des Edge Functions et aucune clé service n'a été trouvée dans le frontend.
9. **Callback anti-open-redirect** : le paramètre `next` est explicitement borné à la locale.
10. **HTML previewer** : `iframe sandbox=""` + CSP locale + absence de `allow-scripts`/ `allow-same-origin` constituent un choix de défense en profondeur particulièrement pertinent pour du HTML fourni par l'utilisateur. Le modèle sandbox sans permissions est conforme au principe de moindre privilège du navigateur. (source: MDN iframe/sandbox documentation)
11. **CI** : la validation applicative et navigateur reste verte sur le commit audité malgré le gate dependency rouge.

## 8. Faiblesses et choix sous-optimaux transversaux

### 8.1 La sécurité est plus forte au niveau data/RLS qu'au niveau HTTP navigateur

**DEDUIT**

Le socle Supabase/RLS est plus mature que la couche HTTP de défense en profondeur : CSP absente, pas de politique explicite supplémentaire de cross-origin isolation, et protections globales limitées à quelques headers.

Ce n'est pas une vulnérabilité unique à exploiter immédiatement, mais un déséquilibre architectural.

### 8.2 Le journal d'audit est traité comme une API métier

**DEDUIT**

La réutilisabilité du RPC `record_admin_audit` est pratique mais sa surface publique est trop large pour un mécanisme censé établir des preuves de sécurité.

### 8.3 Le traitement local est déclaré, mais pas encore vérifié par une politique de build

**DEDUIT**

Le système de metadata est un excellent contrat documentaire ; il lui manque encore un enforcement technique si des contributeurs externes ou des outils plus complexes arrivent.

## 9. Challenges du design actuel

### Challenge A — « Les outils sont locaux, donc la privacy est déjà garantie »

**Conclusion : modifier**

Le constat actuel est bon, mais la déclaration n'est pas une barrière technique. Il faut préserver la simplicité du catalogue tout en ajoutant des contrôles automatisés au moment où la surface de contribution augmente.

### Challenge B — « Un RPC générique d'audit simplifie le système »

**Conclusion : rejeter pour les événements de sécurité critiques**

La simplicité de l'API d'écriture ne doit pas primer sur l'intégrité du journal. Une API générique reste acceptable pour des événements non critiques, mais les événements de sécurité/administration doivent être contraints.

### Challenge C — « Ajouter immédiatement une CSP stricte »

**Conclusion : modifier**

Une CSP stricte ajoutée sans inventaire des besoins peut casser Next.js ou de futures intégrations. La meilleure approche est progressive : inventaire → Report-Only → enforcement ciblé.

### Challenge D — « Corriger npm audit avec --force »

**Conclusion : rejeter**

Le log CI montre que le correctif automatique propose un changement majeur d'`eslint-config-next`. Il faut comprendre le graphe et choisir une remédiation compatible, pas supprimer le signal de sécurité.

### Challenge E — « Le ban suffit pour suspendre immédiatement un utilisateur »

**Conclusion : rejeter**

La documentation Supabase indique qu'un ban ne révoque pas les sessions existantes. Le système actuel a déjà identifié ce problème en essayant de supprimer les sessions ; il faut donc traiter cette révocation comme une étape de sécurité à part entière. (source: Supabase User Management documentation)

## 10. Question from-scratch

### Si Loculary était construit aujourd'hui, qu'est-ce que nous changerions ?

**PROPOSÉ**

Je repartirais sur les mêmes grandes fondations, mais avec quatre différences :

1. **CSP dès le socle HTTP**, d'abord en Report-Only, puis enforced.
2. **Audit log append-only sémantiquement**, avec événements déterminés par les opérations plutôt qu'un RPC générique capable de forger n'importe quelle action.
3. **Contrat local/offline vérifié par CI**, et pas uniquement déclaré par metadata.
4. **MFA pour les comptes privilégiés**, au moins pour `super_admin`, avant d'étendre fortement les capacités administratives/community.

Je conserverais en revanche le choix browser-first, RLS, session validation, RBAC séparé et HTML previewer sandboxé.

- ajouter MFA/step-up auth pour les opérations les plus sensibles ;

## 16. Conclusion

**ÉVALUATION GLOBALE : posture solide sur les données et l'authentification, mais incomplète sur la défense en profondeur HTTP et l'intégrité opérationnelle.**

Le socle actuel n'est pas fragile de manière générale : RLS, validation serveur, séparation des privilèges, sessions vivantes, PKCE et sandbox HTML sont de bons choix.

Les points qui empêchent de considérer la posture comme mature sont surtout :

1. le gate supply-chain rouge ;
2. l'absence de CSP globale ;
3. le journal d'audit trop générique ;
4. la séquence de suspension non atomique ;
5. l'absence d'enforcement technique du contrat local/offline ;
6. l'absence de MFA pour les comptes privilégiés.

Aucune correction n'a été appliquée pendant cet audit. Les éléments ci-dessus restent des constats, propositions ou décisions à valider selon leur étiquette.
