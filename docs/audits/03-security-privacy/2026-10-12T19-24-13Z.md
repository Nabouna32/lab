## 3. Observed results

### 3.1 Table access and RLS

**OBSERVED:** All six retained public foundation tables — `profiles`, `admin_roles`, `admin_permissions`, `admin_role_permissions`, `admin_user_roles`, and `admin_audit_log` — have RLS enabled in production.

**OBSERVED:** `anon` has no SELECT, INSERT, UPDATE, or DELETE table privilege on any of these six tables. The original broad `anon` table-grant condition on `profiles` was corrected by the clean baseline and is not a current table-grant exposure.

**OBSERVED:** `authenticated` retains the intended read boundary for the administrative tables. Direct INSERT/DELETE/UPDATE on `admin_user_roles` are denied after migration `20261009065000_revoke_direct_admin_user_role_dml`; guarded role changes use the RPCs covered by the completed [#464](https://github.com/Nabouna32/lab/issues/464) work. The current live Security Advisor reports only the existing leaked-password-protection warning.

**Assessment:** No current anonymous table-privilege bypass was demonstrated by these checks. Do not describe the historical `profiles` grant as an active exploit.

### 3.2 Profile INSERT privilege

**OBSERVED:** Production still grants `authenticated` INSERT on `public.profiles` and the baseline defines an owner-only, valid-session INSERT policy.

**OBSERVED:** Signup calls Supabase Auth; the database trigger `private.handle_new_user()` creates the profile. The inspected application account actions read and update profiles but contain no application INSERT path.

**DEDUCED:** The direct authenticated INSERT grant/policy appears redundant for the current in-repository application.

**LIMITATION:** Repository inspection cannot rule out a separately supported external consumer that inserts profiles directly. Confirm whether such a consumer is part of the supported product contract before revoking the grant and policy. If no such contract exists, the safer default is to make the Auth trigger the sole profile-creation path.

### 3.3 Public function ACLs and default privileges

**OBSERVED:** The eight current application-facing public RPCs returned by the live catalog query have explicit ACLs granting EXECUTE to the intended authenticated caller (and owner/service role) while excluding `anon` and `PUBLIC`. This is not evidence that those existing wrappers are anonymously callable.

**OBSERVED:** `public.set_profile_updated_at()` retains EXECUTE for `PUBLIC`, `anon`, and `authenticated`. It is a trigger-returning function, not an ordinary RPC entry point. PostgreSQL documents EXECUTE as a requirement for creating a trigger; the current ACL is a least-privilege hardening opportunity, not proof of an authorization bypass. Any ACL change should include a regression test that a profile UPDATE still fires the timestamp trigger.

**OBSERVED — CORRECTION TO THE PRIOR ISSUE TEXT:** Live `pg_default_acl` rows exist for functions in schema `public` for both `postgres` and `supabase_admin`. The schema-specific ACLs explicitly grant EXECUTE to `anon`, `authenticated`, and `service_role`. The query found no global default-privilege override removing PostgreSQL's normal PUBLIC EXECUTE default.

**VERIFIED DOCUMENTATION:** PostgreSQL states that schema-specific default privileges are added to global defaults and cannot revoke privileges granted globally. Therefore, a schema-only default revoke from PUBLIC would not remove the global default PUBLIC EXECUTE grant. See the [official ALTER DEFAULT PRIVILEGES documentation](https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html).

**DEDUCED:** The principal systemic weakness is the permissive default posture for future functions, not a demonstrated anonymous execution path in the current application RPC wrappers. A future function may be exposed if its author forgets to add explicit revocations.

**PROPOSED:** For application-created functions, use secure-by-default privileges for the actual migration owner: revoke global default EXECUTE from PUBLIC, remove schema-specific default EXECUTE grants to API roles in `public`, and grant EXECUTE explicitly to each intended caller in the migration that creates a function. Existing function ACLs are not changed by `ALTER DEFAULT PRIVILEGES`, so current wrappers must remain explicitly granted and regression-tested. The live application functions are owned by `postgres`; do not change `supabase_admin` defaults without evidence that application migrations run under that vendor-managed role.

### 3.4 Regression test coverage

**OBSERVED:** `supabase/tests/clean_application_foundation.sql` declares `plan(61)`. Its RLS-enabled assertions cover only `profiles` and `admin_user_roles`, and its `anon` table privilege assertion only checks SELECT on `profiles`. It does not encode the complete six-table RLS/no-anon-table-privileges invariant.

**OBSERVED:** The test already checks explicit PUBLIC EXECUTE absence for selected guarded RPCs and authenticated access to those RPCs. The separate #464 tests cover guarded role assignment/removal and their transactional invariants; broad grant tests must not replace those behavioral checks.

**Assessment:** Expand catalog-driven assertions across all six tables and all relevant anon table privileges. Add function ACL/default-privilege assertions that prove the intended current and future privilege boundary. Avoid relying only on string-presence checks where a database catalog assertion can test the actual contract.

### 3.5 Verification workflow

**OBSERVED:** `.github/workflows/supabase-database.yml` is manual-only by design. It starts local Supabase, replays migrations, runs database lint, executes pgTAP, and exercises account-deletion concurrency. Production release mode is gated on successful validation.

**Consequence:** Any implementation must explicitly run the Supabase Database CI workflow. Ordinary PR CI does not replace it. No database CI run or local test was performed as part of this read-only investigation.

## 5. Design challenge and recommendation

If designing this privilege boundary from zero today, the intended contract would be:

1. **Tables:** RLS enabled on every retained application table; grant only the operations required by the product; test the whole boundary, not just selected examples.
2. **Functions:** no implicit PUBLIC or API-role EXECUTE grants for newly created application functions; every public RPC receives explicit caller grants in the same migration that defines it. Keep private SECURITY DEFINER implementation functions inaccessible directly and retain explicit authorization/session checks in those functions.
3. **Profiles:** create profiles through the Auth trigger unless a documented, supported direct-insert use case requires another path.
4. **Trigger function:** revoke direct EXECUTE from API roles/PUBLIC only if the trigger behavior is explicitly covered by a test.
5. **Verification:** fresh migration replay, database lint, pgTAP, concurrency tests, then read-only production grant/ACL and advisor verification after an authorized release.

This recommendation intentionally does **not** propose `FORCE ROW LEVEL SECURITY`, an RBAC rewrite, or changing `supabase_admin` defaults without evidence. Those changes are not justified by the current findings and could add complexity or disturb platform-owned objects.

## 6. Decisions requiring explicit validation

- **Profile creation contract:** confirm whether any supported external consumer is expected to insert directly into `public.profiles`. If not, remove the authenticated INSERT grant and policy via a forward-only migration.
- **Function default model:** validate secure-by-default defaults for functions created by the application migration owner, with explicit per-function grants for intended callers. Do not alter the `supabase_admin` defaults absent evidence that it creates application functions.
- **Trigger-function hardening:** decide whether to revoke direct EXECUTE from `set_profile_updated_at()`; recommendation is to include it as low-cost defense-in-depth only alongside a test that the existing timestamp trigger still works.
- **Issue lifecycle:** `type:audit` describes the nature of the current phase and does not itself mandate a second Issue. Issue #431 already covers the least-privilege review and regression coverage. Reuse #431 for the bounded implementation unless the user chooses to separate a materially independent implementation lifecycle; if the primary outcome changes to implementation, update the type label to `type:maintenance` and align the state label with the actual phase. Do not create a duplicate issue solely because the audit phase ends.

## 8. Conclusion

The historical anonymous table-grant issue is corrected. The current six-table table-grant/RLS boundary is sound based on the observed catalog state, and the existing application RPC wrappers have explicit ACLs. The most material remaining structural issue is the permissive default privilege model for future functions, reinforced by a pgTAP coverage gap. Redundant profile INSERT and trigger-function EXECUTE are narrower hardening opportunities.

The next step is to validate the target privilege model and the profile INSERT assumption, then record the detailed operational implementation plan in [Issue #431](https://github.com/Nabouna32/lab/issues/431). This report does not authorize implementation or production privilege changes.
