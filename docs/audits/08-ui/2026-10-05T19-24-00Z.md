## 6. Observed results

### 6.1 Overall direction — OBSERVED / DEDUCED

The implementation is clearly no longer a conventional SaaS landing page or a card-heavy dashboard.

Evidence:

- homepage foregrounds search and quick links;
- discovery is rendered as a structured list rather than a large card grid;
- categories use restrained rows;
- tool pages place the tool surface immediately after the header;
- the shared shell uses typography, spacing and borders more than decorative gradients;
- `decorative-glow` and `decorative-glow-fuchsia` are explicitly disabled.

**Assessment:** the implementation is directionally coherent with the accepted Modern Utility decision.

**Challenge:** the current solution appears to have solved the "generic SaaS decoration" problem more strongly than the "distinctive, visual and pleasant toolbox" problem. The result risks becoming a restrained developer-utility aesthetic rather than a recognisable Loculary visual language.

### 6.2 Typography — OBSERVED

The platform uses Geist Sans/Geist Mono and consistently uses strong display weights for major headings. The homepage uses a large 4xl–6xl heading scale; tool/catalog headings use a smaller but still strong hierarchy.

This is a good foundation:

- high information density without relying on decorative cards;
- clear primary/secondary hierarchy;
- mono typography is reserved for technical content where appropriate.

**Potential issue:** repeated use of very heavy `font-black` headings across homepage, catalog, category and tool surfaces can flatten hierarchy if every important title has approximately the same visual weight.

**Status:** DEDUCED opportunity, not a confirmed rendering defect.

### 6.3 Color and contrast — MEASURED

The token system is compact and coherent:

- light background: `#f7f7f8`;
- foreground: `#18181b`;
- muted text: `#68686f`;
- accent: `#5b4de3`;
- dark background: `#101012`;
- dark muted text: `#a4a4ad`;
- dark accent: `#9b90ff`.

Representative calculated contrast ratios:

| Pair | Ratio |
|---|---:|
| foreground / light background | **16.55:1** |
| muted / light background | **5.16:1** |
| accent / white | **5.81:1** |
| dark foreground / dark background | **17.29:1** |
| dark muted / dark surface | **7.23:1** |
| dark accent / dark background | **7.08:1** |

These representative pairs are comfortably above common WCAG AA text thresholds.

**Assessment:** color contrast is a strength of the current foundation.

### 6.4 Surfaces, borders, radii and shadows — OBSERVED

The system relies heavily on:

- `surface` / `surface-soft`;
- 1px borders;
- `radius-md` and `radius-lg`;
- restrained `shadow-sm` / `shadow-md`.

This produces a calm, precise interface and avoids visual noise.

However, the same treatment is repeated across tool cards, result panels, search, selectors, menus and tool surfaces.

**Challenge:** this is coherent but risks visual sameness. A toolbox with many categories and tool types needs a small number of deliberate hierarchy-breaking patterns so users can distinguish:

- navigation;
- discovery;
- execution;
- result;
- secondary editorial information.

The current system has the primitives needed for this, but the composition rules do not yet appear differentiated enough.

### 6.5 Iconography — OBSERVED — MEDIUM

Tool and category metadata use a mixture of:

- emoji (for example `📊`, `💶`, `🎨`, `🔐`);
- Unicode symbols (for example `↔`, `±`, `◐`, `▦`);
- textual marks (for example `Aa`, `YAML`, `TS`, `</>`, `{ }`).

The shared header controls instead use SVG icons.

**Impact:**

- rendering varies with platform/font/OS;
- visual weight is inconsistent between tools;
- some icons read as consumer emoji while others read as technical glyphs;
- the mixed system weakens brand identity precisely where the catalog needs strong recognition.

**Assessment:** this is the clearest visual-language inconsistency found in the implementation.

**Challenge:** preserving the ability for a tool to have a distinctive visual identity does not require using arbitrary Unicode characters for platform-level catalog identity.

**PROPOSED:** introduce a semantic icon treatment/registry for platform-level tool/category identity, preferably using consistent SVG/icon primitives. Preserve custom visualizations inside individual tools when they improve comprehension or enjoyment.

This is a proposal, not a decision.

### 6.6 Homepage hierarchy — OBSERVED / DEDUCED

The homepage structure is strong:

1. need/search entry;
2. quick links;
3. discovery;
4. categories.

The discovery section deliberately avoids a dense card wall and uses rows with a clear title/description/action pattern.

This matches the current UX decision closely.

**Challenge:** the homepage is now structurally utility-first, but its visual signature remains relatively generic. There is room for a stronger Loculary-specific "toolbox" cue without returning to a marketing hero or decorative SaaS composition.

**PROPOSED:** explore one restrained signature device—such as a stronger tool-index motif, category glyph system, result-oriented motion or a more distinctive search treatment—rather than adding more sections or decoration.

### 6.7 Catalog/category pages — OBSERVED

The catalog page uses:

- search;
- intention chips;
- category rows;
- tool cards.

This is understandable and scalable.

The category cards/tool cards share almost the same visual language: border + surface + small icon + title + muted metadata + arrow.

**DEDUCED weakness:** as the catalog grows, this can become visually repetitive and reduce the ability to scan by meaning rather than by repeated component shape.

**PROPOSED:** establish composition variants by information role, not arbitrary styling. For example, intent entry can be lightweight; category navigation can be denser; individual tools can have stronger identity and capability cues.

### 6.8 Tool-page shell — OBSERVED

The shared tool page correctly prioritizes:

- breadcrumb;
- tool identity;
- processing disclosure;
- tool execution surface;
- editorial content later.

The shell intentionally does not force every tool into the same implementation component.

This is an important architectural/UI strength and should be preserved.

**Challenge:** the header currently consists of a small icon box plus title/description, which is efficient but relatively generic. The strongest visual identity is expected to happen inside the tool surface itself, but the shell provides little contextual distinction between a calculator, editor, generator or mini-application.

**PROPOSED:** keep the shell shared but allow a small number of semantic header variants driven by tool complexity/interaction class, without creating a per-tool design fork.

### 6.9 Global navigation — OBSERVED

Desktop:

- logo;
- centered search;
- Explore;
- account;
- language;
- theme.

Mobile collapses Explore into a menu and exposes icon controls.

The controls have consistent focus-visible rings and hover states.

**DEDUCED challenge:** on mobile, the header has a relatively high number of controls competing for limited horizontal space. Search, account, language, theme and menu are all represented as icon buttons.

This is not proven to be unusable without live rendering.

**À VALIDER:** verify the mobile header at 320–390px with actual browser rendering and test whether account/language/theme/menu remain discoverable without becoming visually cramped.

### 6.10 Search UI — OBSERVED

The search component is one of the strongest platform UI elements:

- explicit combobox semantics;
- keyboard ArrowUp/ArrowDown/Enter/Escape behavior;
- highlighted matches;
- category context;
- empty-result recovery suggestions;
- responsive compact mode.

**Weakness:** the search icon is rendered as the Unicode glyph `⌕`, while the rest of the global UI uses SVG icons.

**LOW / PROPOSED:** align search iconography with the shared SVG treatment.

### 6.11 Motion and reduced motion — OBSERVED

The design system defines fast/standard/slow motion tokens and uses transitions on controls, menus and discovery interactions.

The global stylesheet explicitly disables non-essential animation/transition duration under `prefers-reduced-motion: reduce` and disables smooth scrolling.

**Assessment:** the accessibility/motion foundation is good.

### 6.12 Theme system — OBSERVED

Light and dark tokens are explicitly defined. The theme selector supports:

- system;
- light;
- dark.

The implementation uses class-based theme switching and disables transition animation during theme changes.

**Coverage weakness:** the existing production screenshot workflow does not exercise dark mode. Therefore the dark theme is structurally implemented but not covered by the inspected production visual validation.

## 7. Findings and anomalies

### F-08-01 — Visual screenshot workflow does not perform visual regression
- **Severity:** HIGH
- **Status:** OBSERVED
- The production browser workflow creates full-page screenshots for three routes but does not compare them against baselines using Playwright visual assertions.
- The current test is therefore a screenshot-generation/smoke workflow, not a visual-regression gate.
- Coverage is limited to:
  - French homepage at 1440×1000;
  - French tools catalog at 1024×900;
  - French percentage tool at 390×844.
- It does not cover dark mode, English, intermediate mobile widths, desktop tool pages, category pages, menus, focus states or error/result states.

**Impact:** UI regressions can change spacing, hierarchy, color, responsive behavior or theme rendering without causing CI failure.

**Reproduction:** inspect `e2e/production-visual.spec.mjs`; assertions only verify HTTP success, `main`, `h1` and console errors before writing screenshots.

**PROPOSED:** evolve this into a small, deterministic visual-regression matrix with intentionally selected stable pages/states rather than snapshotting the entire product indiscriminately.

### F-08-02 — Platform iconography is visually inconsistent
- **Severity:** MEDIUM
- **Status:** OBSERVED
- Catalog/category/tool icons mix emoji, Unicode symbols and textual marks, while global controls use SVG.
- **Impact:** inconsistent rendering and visual weight; weaker brand identity; technical and consumer-oriented icon styles coexist without an explicit rule.
- **Evidence:** `src/lib/tools/tools.ts`, `src/lib/tools/categories.ts`, `src/components/layout/Header.tsx`, `src/components/tools/ToolPage/ToolPageHeader.tsx`.

**PROPOSED:** establish a platform icon registry/treatment while preserving custom tool-specific visuals where justified.

### F-08-03 — Modern Utility is coherent but visually close to a generic minimalist developer-tool aesthetic
- **Severity:** MEDIUM
- **Status:** DEDUCED from OBSERVED implementation
- The UI consistently uses borders, neutral surfaces, compact radii, muted metadata, arrows and small accent blocks.
- This is a good correction away from generic SaaS decoration, but the same vocabulary is repeated across almost every information role.
- **Impact:** Loculary may feel clean without yet feeling unmistakably Loculary; a growing catalog may become visually monotonous.

**PROPOSED:** add a restrained signature layer based on hierarchy and tool identity—not more decorative sections. Candidate directions include a distinctive catalog glyph system, semantic header variants, stronger result emphasis and purposeful micro-interactions.

### F-08-04 — Design tokens contain unused/disabled visual vocabulary
- **Severity:** LOW
- **Status:** OBSERVED
- `--shadow-lg` is defined in `globals.css` but no current component reference was found in the repository code search.
- `.decorative-glow` and `.decorative-glow-fuchsia` are explicitly forced to `display: none`.
- **Impact:** design-system drift and ambiguity about which visual primitives are actually supported.
- **PROPOSED:** periodically prune or explicitly classify dormant tokens after the visual direction stabilizes. Do not re-enable decorative glows merely to use the tokens.

### F-08-05 — Mobile/header visual density requires real-device/browser validation
- **Severity:** LOW / À VALIDER
- **Status:** DEDUCED
- Mobile exposes multiple icon-only global controls while the brand label is hidden.
- The structure is technically responsive, but pixel-level crowding/discoverability cannot be established from source alone.
- **À VALIDER:** test at 320, 360 and 390px, including open search, language, theme and menu states.

## 8. Weaknesses and suboptimal choices

The main weakness is not a broken component. It is **over-uniformity**.

The current design system is disciplined enough that almost everything can look like the same component family. That is valuable for maintainability, but Loculary's product model explicitly allows small tools, advanced tools and mini-applications to differ.

The current implementation already permits custom tool UIs technically. The next design challenge should therefore be composition rules:

- what makes a calculator feel like a calculator;
- what makes an editor feel like an editor;
- what makes a visual generator feel visual;
- what makes a result feel consequential;
- what makes discovery different from execution.

The answer should not be "give each tool a different color." It should be semantic hierarchy and interaction-specific composition.

## 9. Challenges to the current design

### Challenge A — Are we too conservative?

**Current:** restrained borders/surfaces/typography.

**Alternative:** a more expressive visual system with stronger color fields, richer cards and decorative hero elements.

**Decision for audit:** **PRESERVE current restraint.**

Reason: the alternative risks reversing the accepted Modern Utility direction and reintroducing the exact generic-SaaS/decorative problem that the UX reset was intended to solve.

### Challenge B — Should every tool share the same shell?

**Current:** shared ToolPage infrastructure with tool-specific execution UI.

**Alternative:** completely independent page compositions.

**Decision for audit:** **PRESERVE shared shell, MODIFY composition flexibility.**

Reason: shared trust/navigation/processing infrastructure is valuable, while the architecture explicitly supports custom tool experiences. The opportunity is semantic variants, not duplicated pages.

### Challenge C — Should catalog identity use arbitrary emoji?

**Current:** emoji/symbol/text mix.

**Alternative:** a consistent icon system.

**Decision for audit:** **PROPOSE adopting a consistent platform icon treatment.**

Reason: this is the most obvious visual inconsistency and is independent of whether individual tools remain visually expressive.

### Challenge D — Should the homepage become more decorative?

**Current:** search-first with restrained discovery.

**Alternative:** marketing-style hero and richer promotional sections.

**Decision for audit:** **REJECT as a default direction.**

Reason: it conflicts with the validated action/search-first journey. A distinctive identity should be achieved inside the existing information architecture.

## 10. Elements to preserve

- Search-first homepage structure.
- Tool-first page hierarchy.
- Shared ToolPage infrastructure with custom tool implementations.
- Strong typography and Geist foundation.
- Compact token system.
- Good light/dark contrast foundations.
- Keyboard/focus-visible treatment.
- Reduced-motion handling.
- Restrained use of borders/surfaces rather than decorative gradients.
- Explicit processing-status presentation.
- Responsive-first layout primitives.
- Ability for tools to diverge visually when the interaction warrants it.

## 11. Proposals

1. **Platform icon system:** introduce consistent SVG/icon metadata for catalog, category and shared tool identity.
2. **Semantic composition variants:** define a small set of layout variants based on interaction class/complexity, not per-tool bespoke styling.
3. **Visual signature:** identify one or two Loculary-specific visual motifs that strengthen identity without becoming decoration.
4. **Visual regression:** convert the existing screenshot smoke workflow into a small deterministic visual-regression gate.
5. **Responsive state matrix:** validate mobile header and tool surfaces at 320/360/390px plus desktop/tablet widths.
6. **Theme matrix:** add at least one dark-mode visual check and one English visual check to the stable browser matrix.
7. **Token cleanup:** remove or explicitly document dormant visual tokens after the next UI pass.

## 12. Decisions requiring explicit validation

No product decision is made by this audit.

The following should be explicitly validated before implementation:

- whether the platform should replace emoji/symbol tool icons with a consistent icon system;
- whether semantic ToolPage composition variants should be introduced;
- which single visual signature/motif best represents Loculary without violating the Modern Utility direction;
- how much visual-regression coverage is worth maintaining in CI versus artifact-only screenshots.

The audit recommends these directions but does not authorize them.

## 13. Implementation scope and plan

If the findings are accepted for implementation, the work should be split into small validated steps:

1. **Iconography foundation:** define the platform icon contract and migrate shared/catalog identity first.
2. **Composition rules:** identify 2–4 semantic ToolPage variants and apply them only where current tools clearly benefit.
3. **Signature exploration:** prototype one restrained visual signature and compare it against the current UI.
4. **Validation matrix:** extend Playwright visual checks for stable routes/states and add actual screenshot comparison only where deterministic.
5. **Cleanup:** prune or classify unused visual tokens after the new direction is validated.

No step above is authorized by this report.

## 16. Conclusion

**Overall assessment: GOOD FOUNDATION / MEDIUM VISUAL DISTINCTIVENESS RISK.**

Loculary's current UI is substantially aligned with the validated Modern Utility direction. The strongest choices are the search-first information architecture, restrained surfaces, strong typography, shared tool infrastructure, responsive primitives and accessibility-conscious interaction states.

The main opportunity is not to add more decoration. It is to make the restrained system **more recognisably Loculary** and less uniformly "generic modern developer utility".

The highest-value next challenge is therefore:

> **How do we increase identity and visual richness without giving back the clarity, speed and restraint that the UX reset intentionally established?**

The audit recommends solving that through iconography, semantic composition and purposeful interaction—not through a return to decorative SaaS patterns.
