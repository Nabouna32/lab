## 4. Findings

### F01 — Homepage composition still risks looking like a decorated landing-page hero rather than a focused utility app

**Status:** OBSERVED (structure) / DEDUCED (visual impact)  
**Severity:** MEDIUM–HIGH

**Evidence**
- `src/app/[locale]/page.tsx` wraps the hero in a large rainbow-gradient frame with 2rem/2.5rem corners, a second rounded surface, a decorative primary-color line, a badge, a very large heading and a search field.
- The heading uses `text-[clamp(2.6rem,6.5vw,5.4rem)]`, `font-black`, line-height `.96` and strongly negative tracking.
- The hero is followed by `HomeDiscovery`; there is no evidence in the current source of the previous sequence of four ecosystem diagrams. That earlier issue is corrected.
- `src/components/home/HomeDiscovery.tsx` now renders category links as bordered surfaces/cards, with a 1-column mobile grid, 2 columns at `sm`, 3 at `lg`, and 4 at `xl`.
- The current design-system contract says not to turn every region into a card and says the homepage should foreground action/search, with discovery depth following. DEC-048 makes Material 3 Expressive a structural and interaction direction, not only a palette.

**Impact**
The source puts several expressive devices in the same small hierarchy: a gradient frame, a large enclosed surface, a decorative line, a badge, a very heavy display heading and a card grid. That may work visually, but the available evidence cannot establish that these devices reinforce one another rather than compete. The category grid's desktop density and rhythm also remain a user-reported concern; its current breakpoints are measurable in source, but its actual visual quality was not rendered here.

**Challenge**
Do not fix this by only shrinking the hero or changing border radii. Reconsider the hierarchy from first principles: one clear promise, one highly usable search action, one intentional path to the full catalog, and category discovery that is expressive without turning every destination into a panel.

**PROPOSED**
Create a deliberately composed homepage with fewer competing containers. Keep the search primary. Compare compact category navigation with the current card grid at 320, 390, 768, 1024 and 1440 px before choosing the final desktop/tablet composition. Preserve the validated Rainbow accent roles, but make the rainbow frame earn its place rather than treating it as mandatory decoration.

### F02 — Typography is not yet a coherent role-based system, despite Roboto now being loaded

**Status:** OBSERVED  
**Severity:** MEDIUM

**Evidence**
- `src/app/[locale]/layout.tsx` loads Roboto with weights `400` and `700`.
- Multiple major headings across the homepage, catalog, category and tool surfaces request Tailwind `font-black` (weight 900), alongside individually chosen font sizes and strongly negative tracking.
- `docs/DESIGN-SYSTEM.md` requires an M3 role-based display/headline/title/body/label hierarchy and says repeated stable values should be consolidated into semantic roles.

**Impact**
The requested 900 weight is not among the explicitly loaded weights; the browser may synthesize a heavier face. More importantly, repeated near-black headings and custom tracking can flatten hierarchy: a hero, page title, card title and section heading do not have distinct semantic jobs merely because their sizes differ.

**Challenge**
Roboto and the validated seed are necessary foundations, not proof that the design system is implemented. Do not add more font weights or tune individual headings independently without defining the role system first.

**PROPOSED**
Define and apply a small semantic type scale for display, headline, title, body and label roles, including responsive behavior and supported weights. Remove ad hoc weight/tracking overrides where they undermine the scale. Verify French/English line wrapping instead of encoding one viewport's line break as the design.

### F03 — Shared controls are too limited and inconsistent to carry the full M3 Expressive language

**Status:** OBSERVED  
**Severity:** HIGH

**Evidence**
- `src/components/ui/Button.tsx` offers only `primary`, `secondary` and `ghost`.
- `src/components/ui/IconButton.tsx` uses a filled primary background and a shadow by default; its dimensions are 40 px, or 40–44 px with responsive styling.
- The main search action uses that 40 px circular icon button. The mobile menu trigger is 48 px but changes to 40 px at the desktop breakpoint. Common text fields and selects use minimum heights of 44 px.
- `docs/UX.md` asks for touch targets around 48 CSS px on mobile. `docs/DESIGN-SYSTEM.md` requires coherent component variants and enabled, hover, focus, pressed, selected, disabled, loading and error states where applicable.

**Impact**
The primitives currently provide basic styling but not a complete shared interaction language. Components set their own radii, sizes and state treatments; a visual redesign can easily devolve into one-off Tailwind classes. The 40 px search action is also smaller than the project's own preferred mobile target.

**Challenge**
Do not blindly implement every M3 component variant. Define the variants that Loculary actually needs and their semantic roles, then use them consistently. The search arrow should not automatically be a shadowed, filled-primary button if that makes it visually compete with the input or other primary actions.

**PROPOSED**
Create a shared control contract for filled/tonal/outlined/text actions as appropriate, icon buttons, text fields, selection controls, chips and disclosure surfaces. Standardize mobile touch targets, state colors, focus indicators, shape and disabled/loading behavior. Use the same primitives across homepage, catalog, search results, account and tool interfaces.

### F04 — Surface and elevation usage is repetitive and partly contradicts the design-system contract

**Status:** OBSERVED (source) / DEDUCED (visual effect)  
**Severity:** MEDIUM

**Evidence**
- The homepage hero has a gradient frame and enclosed surface.
- The catalog and search-results heroes use a large rounded bordered surface with `shadow-lg` and a blurred accent glow.
- `ToolPage.tsx` renders a shadowed, rounded header surface and then a second shadowed, rounded tool surface; editorial content is placed in a further surface-soft region within that container.
- `ToolCard`, `Panel`, category links and account sections use a mixture of CSS radius tokens and hard-coded Tailwind radii (`rounded-xl`, `rounded-2xl`, `rounded-[1.5rem]`, `rounded-[2rem]`, `rounded-[2.5rem]`).
- The design-system contract explicitly says not to round every element, not to make every region a card, and to use elevation only when it communicates meaningful depth or transient interaction.

**Impact**
The repeated card/border/shadow grammar may make distinct page roles—discovery, execution, result and editorial content—feel like variations of one generic catalog template. It also makes global refinement harder because shape and elevation values are distributed through page classes.

**Challenge**
Do not simply reduce all shadows. Decide where containment genuinely improves grouping, where open composition is clearer, and where the tool itself should be the dominant surface. The shared shell must allow tools to differ when their task requires it.

**PROPOSED**
Consolidate repeated radii and elevation into semantic roles, then remove containers that do not add hierarchy. For tool pages, preserve the task-first order and privacy/status disclosure, but validate whether the header and execution surface need two separate elevated cards on every tool.

### F05 — The catalog's “intent” navigation still misrepresents category links as goal-based discovery

**Status:** OBSERVED / TOUJOURS PRÉSENT depuis le rapport du 2026-10-10T06:47:06Z  
**Severity:** HIGH

**Evidence**
- `src/app/[locale]/[section]/page.tsx` defines `intentCategoryMap`: `calculate → calculations`, `convert → computing`, `generate → development`, `analyze → files/video`, `measure → dates/calculations`.
- Each intent renders a link to one available category, selected by finding the first mapped category with tools.
- `docs/UX.md` explicitly says an intent represents what the user wants to accomplish, may span multiple categories, and must never imply that one category fully represents an intent.
- The earlier Audit 08 report found this discrepancy. Current source confirms it remains.

**Impact**
This is not merely a label or styling issue. The product promises a goal-based route but sends users to a domain/category page. For a catalog expected to grow, the mapping will become less accurate rather than more useful.

**Challenge**
Do not build an AI intent engine to repair this. A small curated intent-to-tool mapping is enough to make the first version honest and useful. If that model is not ready, label these as category shortcuts or remove the intent block rather than retaining misleading semantics.

**PROPOSED**
Replace `intentCategoryMap` with curated, localized intent entries mapped to relevant tool IDs across categories, or honestly present category navigation. This is a product/IA correction, not a cosmetic refactor.

### F06 — Search suggestion accessibility state is not synchronized with the visible popup

**Status:** OBSERVED (source) / DÉDUIT (assistive-technology impact)  
**Severity:** HIGH

**Evidence**
- `src/components/tools/ToolSearch.tsx` renders its portal when `showResults && overlayPosition`, including loading, error and no-result content.
- The input sets `aria-expanded` and `aria-controls` only when `visibleResults.length > 0`. Thus a visible loading/error/no-result popup can coexist with `aria-expanded="false"` and no controlled list ID.
- The suggestions container is `role="listbox"`, but each option is an anchor with `role="option"`. The input implements custom ArrowUp/ArrowDown/Enter behavior and `aria-activedescendant`.
- The previous accessibility audit also identified the need to verify the combobox/listbox model with real keyboard and assistive-technology interaction.

**Impact**
The declared state may not describe the UI that is actually visible. The mix of interactive links and listbox options is a semantic mismatch risk; source inspection alone cannot establish exactly what every screen reader announces.

**Challenge**
Do not add a large combobox library or turn this into a modal by default. First choose a correct interaction model for this web search field and implement the simplest semantic pattern that supports it.

**PROPOSED**
Choose either:
1. a genuine combobox/listbox pattern with non-focusable options and active-descendant keyboard navigation; or
2. a search field followed by an ordinary list of links, with native link/tab behavior and no false listbox semantics.

Keep loading/error/no-result feedback as status content and synchronize `aria-expanded`, `aria-controls`, active descendant and visibility. Verify with keyboard and a screen reader before declaring the issue resolved.

### F07 — Reported search-overlay visual defects are not confirmed or disproved by source alone

**Status:** NON RECHECKED visually; source-level evidence only  
**Severity:** MEDIUM

**Evidence**
- The current search suggestions render through `createPortal(..., document.body)`, use fixed positioning and `zIndex: 1000`, and recalculate position on scroll, resize and `visualViewport` changes. This makes clipping by an ordinary ancestor less likely than in a nested absolute-positioned popup.
- The input is `type="text"` and the current source renders one custom clear button when the query is non-empty. The source does not show a second native clear button.
- The existing Playwright smoke test checks responsive overflow, search centering, placeholder fit, category-grid column counts, header search availability, outside dismissal and absence of a redundant close button. It does not prove visual polish at every breakpoint.

**Impact**
The previously reported “dropdown behind blocks/clipped” and duplicate-X symptoms cannot be honestly called fixed based only on this source. Conversely, they are not demonstrated by the current code. Portal positioning can still fail near a small visual viewport, and a 40 px minimum popup height can exceed the available space when the viewport is extremely constrained.

**PROPOSED**
During implementation, manually inspect the real production UI at mobile, tablet and desktop sizes, in French/English and light/dark themes. Test long queries, zero results, loading, error/retry, outside click, Escape, route changes and language switching. Keep the single clear action and avoid reintroducing a close icon that duplicates outside/Escape dismissal. Respect the project policy: browser E2E and screenshots remain manual-only; they must not become PR gates.

### F08 — The header and footer are functional shells, but their composition is not yet proven to express a finished M3 application

**Status:** OBSERVED (structure) / PROPOSED (redesign direction)  
**Severity:** MEDIUM

**Evidence**
- `Header.tsx` is a sticky, 56–64 px high bar with a border, logo, centered search at large breakpoints, a catalog link and a hamburger disclosure.
- `DesktopHeaderMenu.tsx` uses an anchored popover-like panel for account, language and theme. Theme selection keeps it open; ordinary navigation closes it; outside pointer and Escape dismiss it. Language switching preserves open state across a root-layout recreation.
- `MobileHeaderSearch.tsx` focuses the field on open and closes on outside pointer, Escape or route change, with focus restoration on explicit close/Escape.
- `Footer.tsx` is a compact logo/tagline row plus tools/account links and copyright.
- Header/menu controls use local inline SVGs; tool cards use the Unicode diagonal arrow `↗` for internal links. The design-system contract calls for consistent Material Symbols-style platform iconography and explicitly says not to use arbitrary Unicode glyphs as substitutes for platform action icons.
- The current canonical UX says the menu panel is a disclosure/popover, not an ARIA menu, because it combines navigation and settings. That decision governs semantics but does not prove the chosen mobile visual pattern is the best M3 composition.

**Impact**
The code has working interaction logic and a shared brand component, which are worth preserving. However, a small anchored popover is not automatically the right mobile navigation composition, and the footer's simplicity may or may not provide enough structure for the product's public information. The source does not prove a visual failure; the remaining issue is whether these shells feel deliberately designed with the rest of the application.

**Challenge**
Do not preserve the current dropdown solely because its dismissal behavior is now correct. Separate behavior correctness from visual/product fit. Challenge whether mobile needs a dedicated navigation drawer/sheet while desktop retains an anchored disclosure. This would be a meaningful UX decision, not just a styling patch.

**PROPOSED**
Unify the functional icon language and replace internal `↗` arrows with an appropriate internal-navigation affordance or no icon. Redesign header/footer composition alongside the homepage and shared controls, not as isolated decorations. Evaluate mobile drawer/sheet versus anchored popover before implementation.

### F09 — Category and tool discovery still use a generic card language and mixed icon conventions

**Status:** OBSERVED  
**Severity:** MEDIUM

**Evidence**
- `ToolCard.tsx` renders each tool in a bordered card with a 40 px icon tile, bold title, uppercase category label, description and Unicode `↗` arrow.
- Category pages in `src/app/[locale]/[section]/[slug]/page.tsx` use a category emoji, a large title/description, divider and a grid of tool cards.
- Search results reuse the same `ToolCard` component.
- The catalog page combines a large shadowed hero, a sticky intent sidebar on desktop, horizontally scrollable intent shortcuts on narrow screens, and the tool-card catalog below.
- `docs/DESIGN-SYSTEM.md` allows tool-specific identity but requires coherent shared iconography and says shared consistency should not force identical compositions on every tool.

**Impact**
Reuse is useful, but the same card component now carries several distinct contexts: browse catalog, category contents and search results. It may be appropriate for some, but there is no evidence that identical density and metadata are best in all three. The mix of emoji, hand-drawn SVGs and Unicode arrows also lacks a fully demonstrated platform-wide icon contract.

**Challenge**
Do not replace cards everywhere with another universal component. Keep cards when they improve scanning, but allow compact list rows, grouped result lists or more task-specific layouts where they reduce cognitive load. Category labels should use the validated palette roles, not compete with the primary action.

**PROPOSED**
Define composition patterns by user job—browse, search results, category, tool execution—then reuse primitives within them. Standardize platform icons and internal/external navigation semantics; keep tool-specific icons only where they help identify the tool.

### F10 — Public French voice is inconsistent between the homepage and account entry points

**Status:** OBSERVED  
**Severity:** LOW–MEDIUM

**Evidence**
- Homepage copy uses informal French: “Une boîte à outils pour tes idées”, “Que veux-tu faire ?”, “trouve l’outil qu’il te faut”.
- Shared navigation/footer includes “Ton espace” and “Des outils utiles, directement dans ton navigateur.”
- Account strings in `src/lib/i18n/messages.ts` switch to formal language: “Créez un compte”, “Vos données…”, “Vous êtes déjà connecté”, “Votre profil”.
- Issue #425 records informal “tu” as the validated French public voice.

**Impact**
The switch is visible across adjacent public journeys and weakens the sense of one product voice. This is editorial inconsistency, not a claim that formal French is intrinsically wrong.

**PROPOSED**
Apply the already validated “tu” voice consistently across public account entry, account forms and public feedback strings, while keeping security-sensitive instructions precise and respectful. Review French and English strings together; do not translate idioms word-for-word.

### F11 — Responsive smoke coverage checks geometry, not design quality

**Status:** OBSERVED  
**Severity:** INFO–MEDIUM

**Evidence**
- `e2e/smoke.spec.mjs` checks widths 320, 390, 768, 1024 and 1440 px for FR/EN, including horizontal overflow, search centering, placeholder fit, title line grouping and expected category-grid column counts.

## 7. From-scratch challenge

If Loculary were built today, I would not start by adding more rounded cards or changing button colors. I would define the experience around the jobs a user is doing:

1. **Arrive:** one clear promise and an immediately usable search action.
2. **Find:** honest search suggestions and goal-based discovery that actually leads to relevant tools.
3. **Browse:** compact, well-composed catalog/category navigation without unnecessary containers.
4. **Use:** the tool and its inputs/result are the visual center; privacy status is clear but secondary.
5. **Understand and continue:** result actions and relevant next steps come before long editorial content.
6. **Navigate/settings:** one coherent responsive navigation model, with correct focus and dismissal behavior.
7. **Trust:** consistent language, semantic status colors, predictable components and accessible states.

M3 Expressive should be visible in the component behavior, typography roles, shape, semantic surfaces, iconography, motion and state transitions—not just the purple seed, round corners or gradient frame. ChatGPT and other modern apps are useful references for clarity and interaction familiarity, not templates to copy. Loculary still needs its own identity as a utility toolbox.

## 8. Decisions requiring explicit validation

### D1 — Mobile navigation composition

**Options**
1. Keep the current anchored disclosure on mobile and improve its visual hierarchy.
2. Use a mobile navigation drawer/sheet, while keeping an anchored menu on desktop.

**Recommendation:** Option 2 is worth prototyping because mobile navigation is a different spatial context and the menu combines destinations with persistent settings. It is a meaningful UX change, not an automatic implementation detail. Preserve the already validated rules: outside click and Escape dismiss; language/theme choices do not immediately close the settings surface; ordinary navigation closes it; focus is handled correctly.

### D2 — Homepage category composition

**Options**
1. Keep the current responsive card grid and refine typography, density and spacing.
2. Replace it with compact expressive navigation rows/pills, reserving larger surfaces for content that needs containment.

**Recommendation:** Prototype option 2 alongside the current version. The homepage's job is to help people act or find a tool; categories are destinations, not explanatory content cards. Final choice requires actual desktop/tablet/mobile rendering, which this audit environment could not provide.

### D3 — Public/account scope versus admin

The public experience and public account flows are included in the recommended redesign. The authenticated administration redesign remains separate under [Issue #518](https://github.com/Nabouna32/lab/issues/518). Do not expand this phase to all admin subpages without a separate decision.

## 9. Recommended implementation plan

This is a proposed sequence, not authorization to implement the full plan automatically.

1. **Foundation and controls:** establish semantic typography roles, shared radii/elevation, relevant M3 button/icon-button variants, touch targets and one consistent functional icon language.
2. **Navigation shell:** redesign header/menu/footer as one responsive composition; decide D1 first. Preserve the existing language/theme/outside/Escape behaviors.
3. **Homepage:** redesign hero and category discovery from first principles; decide D2 using rendered comparisons, not source-only judgement.
4. **Discovery pages:** correct the intent/category semantic mismatch; align catalog, category and search-result composition to their distinct user jobs.
5. **Tool shell:** remove redundant containment/elevation and improve hierarchy while preserving the task-first tool/result/privacy contract and allowing specialized tool compositions.
6. **Copy and localization:** make the validated informal French voice consistent, review English idiomatically, and remove repeated or non-informative copy.
7. **Verification:** run required PR CI; inspect diff and localization; manually review actual production rendering in both themes and at representative mobile/tablet/desktop widths. Run browser E2E/screenshot workflows only manually, in line with Issue #437. Do not report visual verification unless a real rendered page was inspected.

## 12. Conclusion

**The code is not devoid of good foundations, but the M3 Expressive direction is not yet demonstrated as a coherent end-to-end experience.** The most important problems are not just visual polish: false intent semantics, an incomplete shared control system, inconsistent typography roles, repeated card/elevation patterns and a search accessibility state mismatch.

The source supports concrete recommendations, but it does not support a claim that the current interface was visually audited at real viewport sizes. The next step is to validate the consequential navigation and homepage-composition decisions, then implement the redesign in coherent slices with real rendered review—not to patch each symptom independently.
