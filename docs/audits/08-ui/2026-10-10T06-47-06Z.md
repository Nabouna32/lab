## 6. Observed results and findings

### F01 — Production tokens and font do not implement the validated design direction

**Status:** OBSERVED  
**Severity:** HIGH  
**Evidence:**
- `docs/DESIGN-SYSTEM.md`, `docs/UX.md`, `docs/VISION.md` and DEC-048 validate Material Purple seed `#6750A4` and Roboto as the default interface typeface.
- `src/app/globals.css` still comments that the default is indigo seed `#3F51B5`; `--primary` is hard-coded as `#3f51b5`, and dark `--inverse-primary` also uses `#3f51b5`.
- `src/app/[locale]/layout.tsx` imports `Geist` and `Geist_Mono` from `next/font/google`, and applies Geist Sans to the body.
- `src/app/globals.css` exposes Geist through Tailwind's `--font-sans` and the body `font-family`.
- The design lab has a separate Material Color Utilities implementation, but production tokens are currently hand-authored CSS values rather than a generated/verified mapping from the validated seed.
- The design lab starts from `#1E88E5` with a `vibrant` scheme variant, and its copy still says the final palette/style remain open. This is inconsistent with the already validated seed, font and complementary rainbow roles.

**Impact:** The approved direction currently exists in documentation and an isolated lab, not in the production theme. New page styling layered on these foundations would compound the divergence.

**Challenge:** Do not simply replace every `#3F51B5` literal with `#6750A4`. The validated value is a **seed** for deliberate semantic tonal roles, not a mandate to paint every primary surface with the same hex value.

**PROPOSED:** Build a complete, explicit light/dark semantic token mapping from `#6750A4`, verify actual foreground/background pairs, load Roboto as the shared default, and keep the MCU Rainbow surface treatment and saturated category palette as separate semantic roles. Prefer precomputed/committed production tokens unless a real runtime dynamic-color requirement justifies generating schemes in the browser. Align the design lab's defaults and explanatory copy with decisions already made while leaving genuinely unresolved details marked as open.

### F02 — The explorer labels category shortcuts as user intents

**Status:** OBSERVED  
**Severity:** HIGH  
**Evidence:**
- DEC-045 says an intent is a first-class discovery object, distinct from category navigation, and may lead to multiple tools across categories.
- In `src/app/[locale]/[section]/page.tsx`, `intentCategoryMap` maps `calculate` to `calculations`, `convert` to `computing`, `generate` to `development`, `analyze` to `files/video`, and `measure` to `dates/calculations`.
- Each displayed intent link selects the first mapped category with any tools and navigates directly to that category.

**Impact:** The labels imply goal-based discovery, but the destination is only one category. Several mappings are not a reliable representation of the action—for example, “convert” does not mean “computing,” and “generate” is not limited to development. This undermines the documented information architecture and can mislead users who know their goal but not the tool name.

**PROPOSED:** Implement the smallest honest intent model: curated intent entries mapped to relevant tool IDs (potentially spanning categories), with localized labels and stable routes. Until that model is ready, present the entry points honestly as category shortcuts or omit the mislabeled intent block. Do not add a large inference engine merely to fix the current editorial mapping.

### F03 — The homepage repeats copy and gives four ecosystem visualizations equal, sequential weight

**Status:** OBSERVED / DEDUCED  
**Severity:** MEDIUM  
**Evidence:**
- `src/app/[locale]/page.tsx` presents a large search-led hero and a right-side aside.
- The aside's second surface repeats `t.home.description`, which already appears as the hero description.
- `src/components/home/EcosystemShowcase.tsx` renders four separate visualizations—constellation, radial, network and surfaces—one after another. Each visualization repeats the same category-link list.
- The four views show the same catalog data; the current production component does not make the user choose one view before rendering the next.
- The design lab contains a more compact illustrative homepage composition, but explicitly says its compositions are illustrative and are not screenshots of production.

**Impact:** The homepage is directionally search-first, but the repeated diagrams and repeated links create a long, redundant second half. The count/description aside also spends space repeating information rather than answering a new user question.

**PROPOSED:** Keep one strong, expressive overview of the catalog and a direct path to browse/search. If alternative visualizations genuinely help users, make them an intentional switcher or progressive enhancement instead of four mandatory consecutive sections. Remove duplicated copy and give each section a distinct user job. Validate the composition at mobile and desktop before choosing the final arrangement.

### F04 — Homepage copy and metadata need a coordinated editorial pass

**Status:** OBSERVED  
**Severity:** MEDIUM  
**Evidence:**
- Current French homepage copy in `src/lib/i18n/messages.ts` uses “Des outils pour passer à l’action”, “Que voulez-vous faire ?” and “Décrivez votre besoin, trouvez l’outil et faites-le maintenant.”
- The design-lab example uses “Une boîte à outils pour tes idées” and “Des tâches simples, des outils utiles, moins de friction.” The user explicitly said they prefer the lab's example text; this is a strong candidate, but not a complete validated homepage copy set.
- The lab copy uses informal “tu” (“De quoi as-tu besoin ?”, “Utilise…”), while the production French homepage uses formal “vous”.
- The English lab equivalent is “A toolbox for your next idea” / “Small tasks, useful tools, less friction.”
- In the English locale, `home.metaTitle` is still `Loculary — Outils en ligne gratuits`, a French title.

**Impact:** The current promise, supporting line, action labels, tone and metadata have not been designed as one editorial system. Changing only the hero headline would leave inconsistent voice and SEO copy.

**PROPOSED:** Treat the lab text as the starting candidate for a coherent French/English editorial system: positioning, headline, supporting sentence, search prompt, CTA, discovery headings, footer tagline and localized metadata. Decide one French voice (tu or vous) and apply it consistently. Keep search/action immediate and make claims such as “free” only where the product can substantiate them.

### F05 — Shared page shells over-standardize composition

**Status:** OBSERVED / DEDUCED  
**Severity:** MEDIUM  
**Evidence:**
- `src/components/tools/ToolPage/ToolPage.tsx` wraps each tool in a bordered/shadowed header surface and a second large bordered/shadowed tool surface.
- `src/app/[locale]/[section]/page.tsx` uses a boxed hero and boxed catalog region; category entries use a repeated border/surface/icon/title/count/arrow pattern.
- The homepage uses a large rounded surface and similarly styled side panels.
- Major headings repeatedly use very heavy `font-black` weights.
- Category identity in `src/lib/tools/categories.ts` uses platform-rendered emoji, while other parts of the interface use custom SVG icons and other tool metadata uses varied glyphs/textual marks.
- DEC-004 and DEC-048 explicitly permit tool-specific composition; they require coherent foundations, not identical layouts.

**Impact:** A consistent token system is useful, but repeated card wrappers and a single visual grammar can make discovery, tool execution, results and secondary editorial content feel like variations of the same box. Mixed platform-dependent emoji/glyphs can also weaken catalog identity. These are structural risks inferred from source; pixel-level rendering was not checked.

**PROPOSED:** Preserve reusable semantic foundations and controls, but define composition patterns by purpose: search/entry, intent discovery, category navigation, tool execution, result/feedback and secondary documentation. Let small tools stay compact and advanced/visual tools use richer layouts. Establish a deliberate icon policy for platform-level categories/tools while retaining meaningful custom visuals inside specialized tools.

### F06 — The current account action danger styling references an undefined token

**Status:** OBSERVED  
**Severity:** MEDIUM  
**Evidence:**
- `src/components/account/SubmitButton.tsx` applies `var(--danger-foreground)` as border/background for its `danger` variant.
- The inspected `src/app/globals.css` defines `--danger` and `--danger-soft`, but not `--danger-foreground`.

**Impact:** The declarations using the undefined custom property are invalid, so the danger variant may fail to produce its intended styling. This is a current shared-account UI defect visible directly in source; it was also discussed in the older design-system audit, but it was rechecked here against current main.

**PROPOSED:** During the implementation stage, use the actual semantic error/danger roles and a valid foreground mapping, then add a focused regression check. Do not solve this by adding an alias without first checking all existing danger-state semantics and contrast.

### F07 — Existing contrast tokens need boundary-specific verification

**Status:** MEASURED / INFO  
**Evidence:** Representative contrast ratios calculated from current CSS values:
- Light primary `#3F51B5` / on-primary white: **6.87:1**.
- Light primary container `#E0E5FF` / on-primary-container `#151F55`: **12.38:1**.
- Light muted text `#626473` / background `#F7F7FB`: **5.47:1**.
- Light border `#C7C6D2` / background `#F7F7FB`: **1.58:1**.
- Dark primary `#BAC3FF` / on-primary `#202B70`: **7.52:1**.
- Dark primary container `#37469D` / on-primary-container `#E0E5FF`: **6.66:1**.
- Dark muted text `#C0BFCE` / surface `#181A22`: **9.58:1**.

**Interpretation:** These representative text pairs pass common WCAG AA text contrast thresholds. The light border/background ratio is low; that is not automatically a WCAG failure, because not every border must independently meet 3:1, but controls or boundaries identifiable only through that border need a specific check. The calculations are not a full theme/component accessibility audit.

**PROPOSED:** Validate actual rendered text, icons, focus indicators, disabled states, controls and meaningful boundaries in both themes. Include real component-level checks rather than relying on a palette swatch or a small set of token pairs.

## 9. From-scratch challenge

If Loculary were designed today, we would **not** start by migrating every existing card to a new color. We would first design the journey and page roles, then choose a shared visual grammar that expresses them:

1. **Arrive:** communicate what Loculary is and make the next action obvious.
2. **Find:** search by a task or discover through honest, meaningful intent/category entry points.
3. **Use:** place the tool and its inputs immediately in the foreground.
4. **Understand:** present the result and relevant status/next action clearly.
5. **Continue:** show documentation or further discovery only where it helps.

The visual system should express these differences with M3 Expressive foundations, not erase them behind identical cards. The homepage should be memorable and welcoming without pushing search below the fold or adding repetitive decoration. The current code is a starting point, not a layout contract.

## 10. Decisions requiring explicit validation

These are proposals, not decisions already made:

1. **French brand voice:** use “tu” throughout public French copy, use “vous”, or define a context-sensitive policy? Recommendation: choose one default voice for the public experience; avoid the current mixture between lab and production.
2. **Homepage composition:** keep search/action primary with one strong catalog visualization and deeper discovery below, rather than four consecutive diagrams? Recommendation: yes; provide alternate views only as an intentional interaction if user value is demonstrated.
3. **Administrative console scope:** include all admin subpages in the same redesign delivery, or redesign the public site and account experience first and treat the operational admin console as a separate visual scope? Recommendation: redesign public site + account as the primary experience; audit and migrate admin surfaces after shared foundations stabilize, unless there is a specific reason to include them in the first delivery.
4. **Intent model:** implement real curated intent-to-tool associations in line with DEC-045, rather than category proxies? Recommendation: yes; this is needed to comply with an already accepted decision, not a new vision decision.
5. **Palette implementation:** precompute a verified light/dark semantic token set from the validated seed, rather than generate colors dynamically at runtime? Recommendation: precomputed tokens initially, unless future user-selectable palette requirements justify a runtime engine.

The user has already validated `#6750A4`, Roboto and the complementary roles of both rainbow treatments. Those decisions do not need to be reopened during the implementation unless new evidence reveals a concrete problem.

## 11. Proposed implementation plan

This is a recommendation, not authorization to implement all stages at once.

### Stage A — Validate the redesign brief
- Agree on homepage promise, copy tone and the information hierarchy.
- Confirm the admin-scope boundary.
- Treat current lab copy as a candidate, not as a finished full-site editorial system.
- Keep the validated color/font/rainbow choices fixed unless evidence requires revisiting them.

### Stage B — Correct the design foundation
- Align production font loading and semantic tokens with the validated direction.
- Produce and verify light/dark semantic roles from `#6750A4`; verify status colors and category palettes remain separate.
- Review border/focus/disabled/error states and ensure reduced-motion behavior remains correct.
- Update the lab defaults/explanatory text so the decision aid reflects what is already decided.

### Stage C — Recompose the shared shell and discovery
- Refactor shared navigation/header/footer and primitives only where they constrain the new direction.
- Replace category-proxy intent navigation with the accepted intent-to-tool model.
- Redesign the explorer/category page hierarchy with clear distinctions between intent, category and individual tool.
- Keep navigation responsive and localized.

### Stage D — Rebuild the homepage and editorial system
- Develop a clear headline, supporting copy, search prompt, CTA and discovery sequence in French and English.
- Remove repeated description and repetitive sequential diagrams.
- Use one distinctive catalog overview and meaningful pathways into search/browse.
- Localize page metadata and fix the French English-locale `metaTitle`.

### Stage E — Apply foundations to tool/account surfaces
- Establish a small set of page composition patterns rather than forcing identical cards on all tools.
- Keep task/input/result priority, processing/privacy transparency and useful actions.
- Correct the account danger-token issue and verify account status/error presentation.
- Preserve specialized tool layouts where they improve the task.

### Stage F — Verify before expanding
- Run lint, typecheck, unit tests and build via the repository's required CI.
- Use targeted browser checks for homepage, explorer/category, representative simple/advanced tools and account flows.
- Validate French/English, desktop/tablet/mobile, light/dark, keyboard/focus, reduced motion, contrast, metadata/SEO, loading and hydration.
- Inspect screenshots from real browser runs when the environment supports them; do not substitute source inspection for visual verification.
- Keep E2E off PR triggers per the current validated workflow and verify the required post-merge/manual checks according to the existing policy.
